Part V · Chapter 28

User-facing settings: notifications, onboarding, preferences

Three small modules, each answering a slightly different question about what a specific user has configured.

notifications/emit.pyonboarding/checklist.pypreferences/*.py

notifications/emit.py is the in-app inbox writer — distinct from Chapter 27's outbound webhooks, this is purely internal: watchlist hits, detection-backlog gaps, background job errors, and unhealthy API keys all land here as dismissable, deduplicated notifications a user sees inside the app itself, scoped to either the analyst or operator cohort depending on relevance, and deduplicated by a stable key so a repeatedly-failing job doesn't spam the same notification into existence a hundred times over. onboarding/checklist.py computes a first-hour operator checklist entirely live, from real database and environment state — has CVE ingest actually started producing data, are stack terms configured, are backups enabled and recent, is feed health good, are there any production-posture warnings (Chapter 7's production_posture_warnings()) — with no persistence beyond a simple dismiss timestamp; there's no separate "onboarding progress" table to keep in sync with reality, because the checklist simply re-derives its own state from the same live facts every time it's viewed.

preferences/{repo,validate,display_validate}.py is the server-persisted counterpart to Chapter 4's frontend Context discussion — an analyst's declared stack terms and asset profile, plus display preferences (font scale, density, timezone, reduced motion), stored per user rather than per browser. The validators here are worth noting specifically because they use strict allowlists of exact permitted values, rather than loose type-checking (accepting "any number" for font scale, for instance). This is a deliberate defensive posture: type-checking alone would happily accept a technically-valid-but-nonsensical value — a font scale of 500, a density setting that doesn't correspond to any actual CSS class the frontend knows how to render — that could produce a genuinely broken UI for that user with no clear error message pointing at the cause. An enumerated allowlist rejects anything outside the specific, known-good set of values the frontend was actually built to handle.

Concretely, preferences/display_validate.py enumerates the exact permitted sets — font scales from extra-small to extra-large, density modes (compact/comfortable/spacious), a fixed set of allowed poll intervals (15/30/60/120 seconds), and per-role typography sizes clamped to a 9–20px range — and its sanitize_display_prefs() raises rather than silently clamping an out-of-range value, so a bad write fails loudly at the API boundary instead of quietly storing something the frontend was never built to render. preferences/validate.py is the separate validator for the "My Stack" feature's actual input — it normalizes comma-separated stack terms and enforces a 4096-character cap, and its sanitize_profile() whitelists the shape of a declared asset profile (operating systems, applications, AI systems, plus an environment sub-object for internet-facing/industry/criticality) — but defaults missing fields rather than rejecting the whole submission, a deliberately more forgiving posture than the display-preferences validator, appropriate because a partially-filled stack profile is still useful, whereas a partially-valid display preference risks actually breaking the UI.

Self-check

  1. Why does the display-preferences validator use an allowlist of exact permitted values instead of simply checking that a submitted value is the right data type?
  2. Why doesn't onboarding/checklist.py need a separate "onboarding progress" database table to track completion state?
  3. What's the practical difference between an in-app notification (notifications/emit.py) and an outbound webhook (Chapter 27) — when would a system use one instead of the other for the same underlying event?
  4. Why does preferences/validate.py's stack-profile validator default missing fields rather than rejecting an incomplete submission, while display_validate.py raises on anything invalid instead of defaulting it?
