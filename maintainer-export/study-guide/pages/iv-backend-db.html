Backend & database

asyncpg, Alembic, Postgres production path, SQLite test fallback, and data model.

What it does

Q: What is <code>db/pg_adapt.py</code>?

A: It adapts Postgres-native SQL for SQLite compatibility in the test suite—parallel _SQLITE / _PG query constants where needed. Production path is Postgres-only; do not reintroduce a generic dialect translation layer.

Q: Explain <code>sync_state</code> usage.

A: Key-value store for job watermarks: NVD cursor, EPSS file SHA256, SigmaHQ commit hash, rate-limit buckets when using DB store, and feature checkpoints. Lets incremental syncs skip unchanged work—e.g., EPSS identity skip when CSV hash unchanged.

Q: What integrity checks exist?

A: SQLite: PRAGMA integrity_check. Postgres: real pg_catalog probes for invalid indexes, unvalidated constraints, and FK orphans. Admin Overview runs Check DB integrity with method + backend reported.

Q: What is the Procrastinate schema?

A: Alembic revision 028 applies Procrastinate tables when enabled. Jobs like jobs:llm_product_extraction use queueing locks for singleton execution across workers.

Core implementation

Q: How are migrations managed?

A: Alembic revisions in backend/alembic/versions/ are forward-only. Never edit applied migrations; add a new revision. Reserved words like references caused real bugs—prefer renamed columns over quoted identifiers.

Q: How are user preferences persisted?

A: user_preferences stores display settings, timezone, and optional asset profile JSON. Stack terms use GET/PUT /api/me/stack with legacy localStorage migration on login.

Q: How are embeddings stored?

A: pgvector extension on Postgres 16 (pgvector/pgvector:pg16 image). Entity embeddings for CVEs, techniques, and campaigns with content_hash drift re-embed on backfill. SQLite tests skip vector-specific paths.

Failure modes & edge cases

Q: When does SQLite still appear?

A: SQLite is the zero-config test/dev fallback when DATABASE_URL is empty and Postgres is not required. CI default pytest uses SQLite; operators must run Postgres-backed tests before merging db/ changes. Health reports backend: sqlite vs postgresql.

Q: What happens on first boot with an empty database?

A: If fewer than 10 CVE rows exist, startup triggers full NVD→KEV→EPSS ingest (network-heavy). Operators can seed via scripts/seed_screenshot_data.py for instant demo data.

Performance

Q: How does the asyncpg pool work?

A: DATABASE_POOL_SIZE configures concurrent connections. Drawer bundle assembly intentionally uses separate connections per sub-fetch for safe parallelism. DATABASE_POOL_COMMAND_TIMEOUT_SECONDS caps SQL wait time separately from per-feed HTTP timeouts.

Q: What tables anchor CVE data?

A: cves holds core NVD fields; satellite tables cover KEV deadlines, EPSS history, OTX mirrors, embeddings, Sigma rules index, and correlation artifacts. Ingest jobs upsert idempotently with watermarks in sync_state.

Q: What is <code>feed_cache</code>?

A: TTL JSON blobs for expensive or slow paths: OTX pulses, detection context, LLM outputs, and more. Distinct from canonical tables—read paths may serve stale mirror rows on upstream 4xx/5xx without deleting cached intel.

Q: How does transaction boundary discipline work?

A: db/txn_boundaries.py ensures NVD ingest commits before CIRCL/Sploitus enrich so slow sources cannot exhaust the writer pool. Long-running jobs batch commits; request handlers keep transactions short.

Q: What indexing supports feed performance?

A: KEV JOIN optimizations, count caches, pg_trgm for search, and keyset pagination on /api/cves (pagination=keyset). ORJSON accelerates default JSON responses.

Q: How would you debug a slow query?

A: Check DATABASE_POOL_COMMAND_TIMEOUT_SECONDS, inspect structured logs with request_id, use admin DB explorer with filtered cve_id, and run pytest both SQLite and Postgres for regression. EXPLAIN on production is operator-driven outside the app.

Security

Q: What is <code>app_settings</code>?

A: Writable operator config survives deploys when env vars are unset. Precedence: process env → DB → .env. Secret fields encrypt with BRIEFR_SETTINGS_KEY. Admin Save can mirror to .env for compatibility.

Q: How does the database shim relate to ARCH?

A: PM-3 security architecture graph uses database shim helpers for one-hop SQL edges in the corpus view. Runtime product data still flows through the main db/ package—not the shim—for CVE operations.

Architecture tradeoffs

Q: Why PostgreSQL in production?

A: Production requires Postgres 16 with asyncpg pooling (BRIEFR_REQUIRE_POSTGRES=1). Features like pgvector embeddings, pg_trgm search, and native JSON operators need Postgres. Alembic migrations are forward-only and tested against both backends where dual SQL exists.

Q: Why no ORM?

A: Explicit SQL in the db/ package keeps query shapes visible for performance tuning and dual-backend tests. FastAPI Pydantic models validate API boundaries; SQL stays close to Postgres features.
