Campaign, IOC & graph logic

OTX pulses, correlation campaigns, IOC enrichment, shared infrastructure, and analyst IOC tab.

What it does

Q: What is the campaign layer in BRIEFR?

A: Nightly/on-demand correlation clusters OTX pulses and related intel into correlation_campaigns and lane artifacts—temporal, actor/sector, infrastructure. Intel tab and semantic search surface campaigns; OP may escalate one band when linkage is HIGH/MED after client merge.

Q: What is the IOC tab vs campaign graph?

A: IOC tab is live operator lookup (IP/domain/hash) against VT, AbuseIPDB, GreyNoise with rate limits and ioc_cache. Campaign graph is persisted correlation over pulses/IOCs—no live external call inside the correlation engine run itself.

Core implementation

Q: How are pulse titles normalized for clustering?

A: normalize_pulse_name (stronger than display formatIntelLabel) collapses vendor noise so related OTX pulses group. Active Campaigns UI shows humanized titles but matching uses the normalized base title.

Q: What does find_shared_infrastructure_v2 do?

A: In correlation/ioc_graph.py, it finds shared IOCs across pulses/CVEs for infrastructure lanes—used in corroboration tests with ThreatFox and OTX fixtures. Outputs structured lane factors for explainability, not opaque scores.

Q: How is OTX data stored?

A: Pulses mirror into Postgres tables plus TTL feed_cache JSON. otx_continuous_sync is registration-gated. Upstream errors serve stale mirror rows without deleting cached intel.

Q: How does the IOC lookup API work?

A: Authenticated analyst POST/GET routes call outbound providers through resilient client + dedicated IOC rate bucket. Results cache in ioc_cache with retention cleanup job. Missing API keys return honest empty states, not fake scores.

Q: What is ThreatFox corroboration?

A: Tests and ingest paths can corroborate OTX IOCs with ThreatFox mirrors—shared infrastructure lane gets stronger evidence when both sources agree on domain/hash overlap.

Q: How does wallboard use campaigns?

A: Campaign counts and intel tiles read correlation_campaigns with active filters—kiosk token auth, ranked CVE tiles still use OP then Threat, not campaign score alone.

Q: What YARA generator inputs use IOCs?

A: test_yara_generator.py shows IOC structs (type/value) feeding detection emit paths—deterministic from structured intel, not LLM guesses.

Q: How are retracted campaigns filtered?

A: Embedding backfill and semantic search skip retracted correlation_campaigns rows (E8). UI must not show stale campaign cards after retraction—tests guard empty vs active states.

Integration

Q: How do campaigns appear in the DetailDrawer?

A: Intel tab loads campaign clusters from correlation tables—primary card plus related count, collapsed by default. Drawer bundle may parallel-fetch intel slice; OP hero can render before correlation finishes loading.

Q: How does semantic search include campaigns?

A: /api/search/semantic embeds non-retracted correlation_campaigns (E8) and returns a Campaigns section alongside CVEs and techniques when embeddings enabled.

Q: What webhooks fire on IOC/watchlist events?

A: ioc_watchlist_hit, watchlist KEV/EPSS change alerts, and KEV backlog events use database-backed destinations with dedupe keys and delivery logs—configured in admin Webhooks.

Q: How does Forge overlay campaigns?

A: When enabled, navigator/hunt context can reference correlated campaigns for technique selection—must not claim 'ranked for your stack' without stack pins (honesty PRs).

Q: How do watchlist pins interact with IOC graph?

A: Pins drive watchlist_monitor_alerts on KEV/EPSS changes—not continuous IOC graph polling. Snooze removed; pin/watchlist remains.

Failure modes & edge cases

Q: What happens when OTX is down?

A: Serve any-age stale pulses from mirror/cache; Feed Health shows freshness vs circuit separately. Correlation job uses persisted data only—no live OTX inside engine run.

Q: How does IOC rate limiting behave?

A: Token bucket per minute; drained bucket returns 429 with Retry-After. Tests in test_rate_limit.py cover IOC path. BRIEFR_RATE_LIMIT_STORE=db needed for multi-worker consistency.

Q: What if correlation precompute is disabled?

A: CORRELATION_PRECOMPUTE_ENABLED=0 (default): /risk does not block on correlation snapshot; escalation merges when correlation API data arrives. Avoids drawer open latency regression.

Q: Empty Active Campaigns—what does UI show?

A: Distinct empty state: never-synced OTX vs no matches vs retracted campaigns filtered. No fabricated campaign cards.

Q: What if GreyNoise/VT keys are missing?

A: Routes return structured empty/missing-key states; UI explains which provider is unconfigured. Core CVE workflows unaffected—IOC is enrichment, not gate.

Performance

Q: Why no live API inside nightly_correlation?

A: Engine run reads Postgres only—bounded runtime, no external rate-limit coupling. Fresh OTX is the ingest job's responsibility; correlation consumes stable snapshots.

Q: How is ioc_cache retention managed?

A: cache_retention_cleanup sweeps stale IOC cache entries alongside feed_cache and aged mirrors—prevents unbounded disk growth on busy IOC tabs.

Q: How are pulse families tested?

A: test_pulse_families.py exercises normalize_pulse_name edge cases—vendor suffix stripping, unicode, duplicate collapse—guarding clustering stability.

Q: Does IOC tab block the feed thread?

A: No—IOC lookups are async API calls with loading/error states per lookup. Rate limits bound concurrent external queries; cache hits avoid repeat provider calls.

Security

Q: What data leaves the network on IOC lookup?

A: Operator-typed IOC values go to configured third-party APIs (VT, etc.) over HTTPS. Keys are env/encrypted settings; responses are cached locally. No anonymous public IOC proxy endpoint.

Q: How are webhook IOC events scoped?

A: Admin configures destinations and subscribed events; delivery errors masked on read. Test POST allowed on disabled destinations for validation without enabling production spam.

Q: Can IOC lookup be abused for scanning?

A: Session auth + per-user rate limits + operator-only keys. Not a public DNS walker; each lookup is user-initiated with audit-friendly logging metadata.

Architecture tradeoffs

Q: Why client-side OP escalation from correlation?

A: Temporary documented compromise: hero OP renders from cheap signals immediately; campaign linkage may arrive later. Server-side merge in /risk is the future hardening—today honesty prefers fast shell over blocking drawer.

Q: Why persist campaigns instead of query OTX per CVE?

A: Same rationale as NVD: predictable latency, explainable factors, offline degradation. Clustering is compute-heavy—belongs in scheduler, not request path.
