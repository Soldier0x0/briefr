Correlation & scoring

Operational Priority, Threat Score, environment relevance, and explainable correlation.

What it does

Q: What is Operational Priority (OP)?

A: OP is the primary analyst-facing band (P1–P4) for triage. It combines KEV status, severity, EPSS exploitation signals, environment relevance to the user's stack, and optional profile toggles (internet_facing, criticality). OP can escalate one band under documented rules without changing Threat Score.

Q: Describe correlation v3 at a glance.

A: Nightly and on-demand correlation clusters OTX pulses into campaigns, infrastructure lanes, actor/sector signals, and temporal patterns—persisted in Postgres, served over REST. OP hero renders from cheap signals immediately; campaign escalation merges when correlation loads client-side.

Q: What inputs feed the scoring engine?

A: KEV flags, CVSS, EPSS score and percentile, CWE, affected products, Vulnrichment SSVC, stack terms, and optional user profile JSON. Legacy v1.1b blend remains as legacy_risk_v11b API field only.

Q: What is the Investigation Score route status?

A: Removed. Overview uses OP + Threat + Environment Relevance per ADR-002. Interview answer: do not describe Investigation Score as current—it is historical.

Q: What is environment UNKNOWN honesty?

A: UNKNOWN tier means insufficient stack evidence—scoring does not invent relevance points. Asset wizard optional toggles affect OP/SSVC only when set.

Q: What lanes does correlation v3 expose?

A: Campaign clusters, infrastructure/shared IOC, actor/sector signals, temporal patterns—each with structured factors in Postgres, served over REST to Intel tab and semantic search (campaign embeddings E8).

Core implementation

Q: How does Environment Relevance work?

A: Tier reflects stack term matching against affected products/CPEs. UNKNOWN is provisional—no phantom points. Server-side stack relevance sort (I16) can order the feed when configured. My Stack persists via /api/me/stack.

Q: Where is scoring code?

A: backend/scoring/ is the sole engine—priority.py, threat modules, and SSVC helpers. DetailDrawer and wallboard consume API output; duplicated FE scoring was explicitly removed (W2).

Q: How does KEV affect prioritization?

A: KEV is a strong P1 signal with Threat floor 80 for CISA KEV. KEV due-date histograms and backlog views in Forge use unified UTC math. KEV-on-stack webhooks use BRIEFR_STACK_TERMS or saved user stack.

Q: How does feed ranking use scores?

A: Server-side stack relevance sort option; wallboard top-risk orders by OP then Threat. Feed cards show KEV ransomware badge and EPSS context without recomputing Threat client-side.

Q: What is correlation v3 Phase 4 and when did it ship?

A: CORR-PR-6…13 (#501–#513) added observation-time semantics, read-time freshness decay, pulse families, ThreatFox corroboration, alias-aware attribution conflicts, analyst confirm feedback, correlation_metrics snapshots, and feed-boost gating for watchlist campaign peers. Nightly engine still reads Postgres only—no live OTX in the correlation run.

Q: Why capture observed_at on OTX pulse IOCs?

A: CORR-PR-6 stores when an IOC was observed on a pulse so lifecycle, momentum, and freshness decay use observation time—not just ingest time. Prevents stale intel from looking newly active after a re-sync.

Q: What are pulse families?

A: pulse_families table + rebuild_pulse_families clusters pulses by Jaccard similarity on IOC sets (CORR-PR-9). Reduces duplicate campaign cards and powers dedup in Active Campaigns UI.

Q: What does correlation_metrics store?

A: Daily snapshot rows via snapshot_correlation_metrics—counts of campaigns, lanes, stale factors—used for admin/ops visibility and CORR-PR-13 feed-boost gating decisions.

Integration

Q: What is Threat Score?

A: A 0–100 asset-independent score from the backend scoring/ engine. CISA KEV sets a floor of 80 when is_kev. VulnCheck-only KEV has no floor. The frontend displays POST /api/cves/{id}/risk fields only—no live Threat recompute in the browser.

Q: How does OP escalation interact with correlation?

A: Client-side merge may raise OP one band when correlation shows HIGH/MED campaign linkage—temporary documented behavior in SYSTEM_DESIGN. Threat formula stays unchanged; low EPSS never de-escalates KEV/CRIT P1.

Q: What is <code>nightly_correlation</code> job?

A: Scheduled correlation pass over OTX and related intel tables—no live external API inside the engine run. Results feed Intel tab campaigns and Forge overlays when enabled.

Q: How are campaigns displayed in the drawer?

A: Active Campaigns clusters related pulses by normalized base title; default collapsed section; humanized titles via formatIntelLabel. Matching uses stronger normalize_pulse_name than display formatting.

Q: How does semantic search relate to scoring?

A: Hybrid search (/api/search/semantic) retrieves CVEs, techniques, and campaigns via embeddings—retrieval only, not a replacement for OP/Threat. Results render in sectioned FEED UI.

Q: What regression tests guard scoring?

A: Backend pytest covers priority bands, KEV floors, SSVC paths, and API /risk contracts. Frontend unit tests cover display helpers. Golden query contracts exist for embeddings—not for OP math duplication in FE.

Q: How does ThreatFox corroboration strengthen IOC edges?

A: CORR-PR-10: when ThreatFox and OTX agree on infrastructure IOCs, shared-infrastructure lanes get stronger evidence in find_shared_infrastructure_v2. Tests in test_threatfox_corroboration.py lock the behavior.

Q: What is the analyst confirm feedback API?

A: CORR-PR-12 exposes authenticated endpoints for analysts to confirm or reject correlation suggestions—feedback persisted for tuning and UI honesty (Confirm controls in drawer/Intel).

Q: How does feed-boost gating interact with watchlist?

A: CORR-PR-13 boosts CVEs linked to pinned campaign peers in feed sort when metrics + confirm state allow—tested in test_feed_watchlist_campaign_sort.py. Does not invent relevance without stack/pin context.

Failure modes & edge cases

Q: How does read-time freshness decay work?

A: CORR-PR-8 computes decay at read time so drawer staleness badges reflect age of observations. Postgres GROUP BY for freshness columns is tested—bad SQL here broke production reads before the str() guard fix.

Q: What is alias-aware attribution conflict?

A: CORR-PR-11 resolves conflicting actor/alias labels on merged campaigns so analysts do not see contradictory attribution strings on related pulses. Explainable merge—not silent overwrite.

Performance

Q: What is <code>CORRELATION_PRECOMPUTE_ENABLED</code>?

A: Optional snapshot precompute behind a flag (default off). When off, POST /api/cves/{id}/risk no longer blocks on correlation—improving drawer open latency. Escalation merges when correlation data arrives.

Q: Does correlation block drawer open?

A: Not when precompute is off—POST /api/cves/{id}/risk avoids blocking on correlation snapshot. Intel/campaign sections load asynchronously with staleness callouts.

Security

Q: What is SSVC's role?

A: Parallel annotation on /risk: outcomes Act, Attend, Track*, Track with explainability path. SSVC does not replace OP; crosswalk P1↔Act, P2↔Attend, etc. Profile fields may modify SSVC without touching Threat.

Q: How would you explain scoring to a non-security hiring manager?

A: BRIEFR translates CVE noise into three numbers analysts already use: how urgent (P1–P4), how dangerous in general (Threat 0–100), and whether it hits our stack (Environment). All computed server-side so every UI surface agrees.

Architecture tradeoffs

Q: Why is correlation explainable?

A: Lanes surface structured factors and matching rationale—not a black-box model score. Campaign clustering uses normalized pulse titles; Active Campaigns UI shows primary card plus related count with honest empty states.

Q: Why client-side OP escalation if correlation is server-side?

A: Historical latency compromise: OP hero uses cheap signals immediately; campaign escalation merges when correlation loads (CORRELATION_PRECOMPUTE_ENABLED default off). Server-side merge in /risk is the documented future hardening.
