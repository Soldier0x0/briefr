Part IV · Chapter 23

Threat modeling, provenance, and IOC retro-matching

Three small, cheap, read-only layers that share one job: being honest about what BRIEFR does and doesn't actually know right now.

threat_model/scenarios.pyintel/provenance.pyioc/retro_match.py

Threat scenarios (build_threat_scenarios) generate stack-scoped, plain-English ATT&CK narratives — "an adversary may use T1190, Exploit Public-Facing Application, against systems running nginx" — paired with the actual CVE evidence backing that claim and concrete mitigation actions (patch this, deploy this hunt pack, close this coverage gap). Provenance is a meta-layer sitting over the exploit, detection, and correlation sections of a CVE's detail view, computing a per-section "as of / source / status" line — checked, pending, or source-unavailable — by checking each upstream feed's circuit-breaker health (Chapter 16) and cache timestamps. IOC retro-matching joins an analyst's saved IOC watchlist against the locally mirrored OTX and ThreatFox tables, surfacing "has anything I'm personally watching shown up in threat intel since I saved it" — retroactively, on a schedule, not the moment it happens.

All three share the same underlying justification: each is a cheap, DB-local, read-only layer built entirely on data other subsystems already ingested — none makes a live external call on the request path, keeping them consistent with the heavy-work rule you've now seen enforced repeatedly. Provenance specifically exists because of a project-wide error-handling convention: every async view needs honest loading, empty, error, and data states, and exploit/detection/correlation data specifically depends on flaky third parties (OTX, GitHub, Sploitus) whose outages must be visible to an analyst as "this section is stale because a feed is down," never silently rendered as an indistinguishable, misleading "nothing found here."

The retro-match query is implemented as a UNION ALL of two structurally separate joins — one against OTX's tables, one against ThreatFox's — rather than one generalized "IOC sources" table both feeds write into. This is a deliberate tradeoff: OTX carries pulse and campaign context ThreatFox doesn't have, and ThreatFox carries confidence and malware-family fields OTX doesn't structure the same way. Forcing both into one common schema would mean either dropping source-specific fields the UI genuinely wants to show, or padding a shared schema with a pile of nullable columns that are only ever populated by one source — the two-query union keeps each source's native shape intact at the small cost of writing two similar-looking queries instead of one.

Self-check

  1. Why is IOC retro-match implemented as a UNION ALL of two separate joins instead of one generalized "IOC sources" table — what would be lost by unifying the schema?
  2. Construct a concrete scenario where the provenance layer's "source unavailable" state prevents an analyst from being misled, versus what they'd see without it.
  3. Why do none of these three subsystems make a live external API call, and how does that connect back to the heavy-work rule from earlier chapters?
