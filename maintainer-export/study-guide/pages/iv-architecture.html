Architecture & system design

Monolith boundaries, asyncio, single-worker defaults, and request vs background work.

What it does

Q: What are intentional non-goals in the current architecture?

A: Full multi-tenant SaaS, a shipped all-in-one docker-compose platform (Postgres compose exists), STIX export in the current loop, and heavy ML on the request path. Detection composer beyond deterministic templates remains parked; the product optimizes analyst time on a single server.

Q: What is the graphify knowledge graph used for?

A: AST-derived graphify-out/ maps modules, jobs, and inferred edges for onboarding. Agents run graphify query before broad code exploration; after code edits, graphify update . keeps the graph current.

Q: What analyst tabs exist in the main shell?

A: BRIEF (summary), FEED (CVE list), IOC (live lookup), Incidents/News (RSS + case studies), Forge (ATT&CK/hunt). Tabs use hidden panels—not unmount—to preserve scroll/filters. URL syncs ?tab=.

Core implementation

Q: How does BRIEFR document architectural truth?

A: docs/PRODUCT_STATUS.md is the living runtime truth; docs/SYSTEM_DESIGN.md describes structure. When docs disagree with code, code and PRODUCT_STATUS win. The maintainer-export study guide and graphify knowledge graph support onboarding.

Q: How would you diagram BRIEFR for an interviewer?

A: Draw external feeds on the left, APScheduler ingest jobs writing Postgres in the middle, FastAPI serving JSON to React on the right, and call out the scheduler owner + single-worker default. Mention session-gated /api/*, job locks, and that correlation/scoring are server-side—not recomputed in the browser.

Q: How does ORJSON fit the API layer?

A: FastAPI default response class uses ORJSON for faster serialization on large CVE list payloads. It is an implementation detail behind routers—clients still see standard JSON.

Q: What is the BRIEF tab?

A: Executive summary surface for prioritized intel—uses same session auth and scoring API as FEED; auth refresh race (#731) specifically broke BRIEF with concurrent 401s before shared refreshAccessToken() dedupe.

Integration

Q: What is BRIEFR at a high level?

A: BRIEFR is a self-hosted CVE intelligence and detection-engineering platform. It ingests NVD, KEV, EPSS, and enrichment feeds into PostgreSQL, scores and correlates them server-side, and exposes everything through a React analyst UI with Forge detection workflows and an operator Admin console.

Q: What frontend build stack is used?

A: React 19 with Vite, React Router 7, plain JSX/CSS with semantic design tokens—no Tailwind runtime. Chart.js was removed; charts use Recharts behind ChartShell. Radix primitives provide accessible dialogs, selects, and menus styled with BRIEFR tokens.

Q: How is state preserved across tab switches?

A: Main analyst tabs use hidden panels instead of unmounting so FEED scroll position and filters survive. DetailDrawer Intel/Detect/Related tabs stay mounted after first visit for the same reason. URL query params (?tab=, ?cve=) sync navigation for back-button behavior.

Q: How does RSS link to CVEs?

A: Incidents ingest parses cve_ids from title/body; cards chip to open drawer; drawer RELATED tab includes related_news on bundle endpoint—bidirectional news↔CVE navigation.

Q: How does MITRE ATLAS appear?

A: GET /api/case-studies/feed alongside RSS sources in Incidents—separate from ATT&CK Forge navigator corpora refreshed by weekly_mitre_refresh.

Failure modes & edge cases

Q: How does BRIEFR handle optional external API keys?

A: No keys are required for core CVE feed, search, and RSS. IOC enrichment (VirusTotal, AbuseIPDB, GreyNoise) and LLM PDF summaries stay empty until operators add keys. Process environment wins over backend/.env because load_dotenv() does not override existing env vars.

Performance

Q: Describe the four-layer architecture.

A: The pipeline is Feed Ingestion (APScheduler jobs in scheduler.py) → PostgreSQL (asyncpg pool) → FastAPI API (main.py + routers) → React UI (frontend/src). Heavy work never runs on the HTTP request path; schedulers and background jobs own sync, correlation, and ML.

Q: How does asyncio fit into the backend?

A: FastAPI handlers are async def; database I/O uses asyncpg. Scheduled jobs are async coroutines registered with APScheduler. The outbound api_queue serializes external HTTP per source so NVD pacing and circuit breakers stay predictable under concurrent requests.

Q: What is the outbound API queue?

A: api_queue serializes outbound calls to rate-limited sources (NVD, OTX, LLM providers). /api/health exposes per-source queue depth so operators see waiting vs active work. Feed sync paths pass human-readable operation labels for the header Background sync indicator.

Q: How does the platform separate read and write paths?

A: Analyst GET endpoints read from Postgres and caches (feed_cache, ioc_cache). Writes flow through ingest jobs, admin config apply, or authenticated POST/PATCH routes. NVD ingest uses explicit transaction boundaries so slow enrichments cannot hold writer connections.

Q: What is the request-path vs background-work rule?

A: ML, enrichment sweeps, and external syncs belong in scheduler.py jobs. Request handlers do DB reads and cached lookups only. Violating this exhausts pools and couples analyst latency to NVD/LLM outages—danger zone #6.

Security

Q: What is the role of <code>main.py</code> lifespan?

A: Lifespan opens the asyncpg pool, optionally starts APScheduler when BRIEFR_SCHEDULER_ENABLED=1, may start an in-process Procrastinate worker when enabled, runs startup hygiene (session cleanup, integrity probes), and shuts everything down cleanly on exit.

Q: How do analyst and admin surfaces split?

A: Analyst routes live under the main shell (BRIEF, FEED, IOC, Incidents, Forge) behind session auth. Admin is a separate sidebar shell with operator tools: scheduler, feed health, backups, config, AI operations, and security posture. Both share the same FastAPI app and Postgres backend.

Q: What is Procrastinate's role relative to APScheduler?

A: APScheduler remains the in-process cron owner for ~27 recurring jobs. Procrastinate (optional, PROCRASTINATE_ENABLED) adds durable outbound jobs—health ping, stack backfill, LLM product extraction—with Postgres-backed retries. Most ingest still runs through APScheduler locks.

Q: How does multi-worker deployment work if needed?

A: Run multiple uvicorn replicas with BRIEFR_SCHEDULER_ENABLED=0 on API-only nodes and exactly one scheduler owner. Set BRIEFR_RATE_LIMIT_STORE=db so auth, refresh, and IOC limits are shared. APScheduler must not run on every replica or jobs would duplicate.

Q: What is the wallboard and how does it differ from the analyst UI?

A: Wallboard v2 is a kiosk-oriented, mono-styled tile grid for SOC displays. It authenticates via X-BRIEFR-Wallboard-Token header (or admin-configured token), not the analyst session cookie. Top-risk tiles rank by Operational Priority then Threat Score.

Architecture tradeoffs

Q: Why is BRIEFR a monolith rather than microservices?

A: A single deployable unit matches the solo-operator and small-team audience: one Postgres, one uvicorn process, one scheduler owner. Cross-cutting concerns—auth, rate limits, metering, and job locks—stay coherent without distributed tracing overhead. Scale-out is optional via API-only workers plus a shared rate-limit store.

Q: Why does BRIEFR run a single uvicorn worker by design?

A: Default rate-limit token buckets are in-process. Multiple workers would split buckets unless BRIEFR_RATE_LIMIT_STORE=db persists them in sync_state. The documented production pattern is one API worker plus one scheduler owner, not an arbitrary worker fleet.

Q: What is the DetailDrawer and why is it central?

A: The DetailDrawer is the CVE deep-dive overlay: Overview (OP/Threat/Env), Intel, Detect, Related, and more. A drawer bundle endpoint assembles sub-resources in parallel, each on its own DB connection, so asyncpg concurrency stays safe while the UI renders quickly.
