Security & trust boundaries

Sessions, JWT refresh, rate limits, secrets, and fail-closed production posture.

What it does

Q: What network egress assumptions should operators know?

A: The app initiates outbound HTTPS to NVD, threat feeds, and optional IOC/LLM APIs. Inbound is typically nginx → uvicorn on localhost. No inbound agent protocol—it's a pull-based intel dashboard, not an EDR.

Q: What is the trust model for correlation and scoring output?

A: Scores are computed server-side from auditable inputs (KEV, CVSS, EPSS, stack terms). Correlation lanes expose explainable factors—not opaque ML black boxes for OP/Threat. ML augments optional detection context and embeddings retrieval, not the primary risk band.

Integration

Q: How are webhook destinations secured?

A: Admin CRUD for webhook destinations stores configs masked on GET. Delivery dedupe is per destination. Test webhooks work even on disabled destinations for validation. Delivery log errors are masked on read.

Failure modes & edge cases

Q: What CORS and origin controls exist?

A: ALLOWED_ORIGINS binds at middleware startup; changing it requires restart (honest apply_strategy: restart in config schema). Self-hosted deployments typically front nginx on one origin; dev uses Vite proxy to /api.

Security

Q: What are BRIEFR's two independent auth layers?

A: Optional edge auth: Cloudflare Tunnel + Zero Trust email OTP protects the public hostname—outside FastAPI. Application auth: username/password with server-side sessions (briefr_at cookie), JWT access tokens, and refresh rotation. Operators can use either or both; they do not replace each other.

Q: How does session authentication work?

A: First-run /api/auth/setup creates the admin user. Login issues a short-lived access token and refresh token stored in HttpOnly cookies. Analyst /api/* routes require a valid session via middleware; admin routes additionally require the admin role with live is_active revalidation.

Q: Explain JWT + refresh token flow.

A: Access tokens authorize API calls; refresh tokens rotate on POST /api/auth/refresh. Concurrent 401s dedupe through a shared in-flight refreshAccessToken() in api.js so one refresh does not stampede and revoke all sessions. Password change revokes every active session immediately.

Q: What happened to the legacy admin API key?

A: Sprint A0 removed BRIEFR_ADMIN_API_KEY because it failed open when unset. Admin operations now require a logged-in user with the admin role. Production fails closed without JWT_SECRET—no silent dev auto-generation in production posture.

Q: How are rate limits implemented?

A: Token-bucket limiters guard auth, refresh, IOC lookup, and admin endpoints. Enable with RATE_LIMIT_ENABLED=1 in production. Buckets default in-memory; BRIEFR_RATE_LIMIT_STORE=db persists them in sync_state for multi-worker deployments.

Q: What SSRF protections exist?

A: Outbound fetches block CGNAT range 100.64.0.0/10 and other unsafe targets. Refresh endpoints reject sessions past expires_at. LLM summary routes require authenticated sessions—no anonymous PDF summarization that could proxy arbitrary URLs.

Q: How are secrets handled at rest?

A: Secret-typed admin config keys encrypt in app_settings when BRIEFR_SETTINGS_KEY is set (ADR-006). Without it, secrets stay in process env or .env only. Structured logging redacts *_KEY, *_TOKEN, *_SECRET, and *_PASSWORD in extra fields—never log raw secrets in message strings.

Q: What is the wallboard trust boundary?

A: Wallboard uses a dedicated header token, not the analyst session. Query-string ?token= was removed (Sprint A7). Optional WALLBOARD_TOKEN in admin config can gate kiosk mode. Tokenless wallboard in production triggers posture warnings.

Q: How does BRIEFR fail closed in production?

A: Startup logs warnings for unsafe flags: rate limits off, insecure cookies, tokenless wallboard when BRIEFR_ENV=production. The Security admin panel mirrors the same checks. Missing JWT_SECRET blocks production boot rather than generating an ephemeral secret.

Q: What audit trail exists for operator actions?

A: audit_log records admin mutations with redacted targets via redact.py. DB explorer browse events log without row bodies. Webhook and config changes are traceable. Retention cleanup ages audit rows on a conservative 365-day window.

Q: How is role revalidation enforced?

A: JWT role claims are not trusted blindly—handlers re-check users.is_active and role on sensitive routes (#392). Deactivated users lose access immediately even if an old access token has not expired.

Q: What protects the admin DB explorer?

A: Allowlisted tables only—deny by default. Sensitive tables (users, sessions, webhook_destinations) return 404. cves requires a cve_id filter. Rate limit 30/min; browse is audited without returning full row payloads in logs.

Q: How does LLM outbound data minimization work?

A: ai/llm_payload.py skips provider HTTP when messages or source text are empty—no quota burn on blanks. Prompt text is not stored in ai_operations; only redacted metadata and token counts. Admin can view captured payloads for failed ops when recorded.

Q: How are refresh-token reuse attacks handled?

A: Refresh rotation with reuse detection can revoke all sessions if the same refresh token is presented twice. Frontend dedupes concurrent refresh calls to avoid accidental self-revocation under parallel 401 retries.

Q: How would you harden a fresh BRIEFR install?

A: Set JWT_SECRET, enable RATE_LIMIT_ENABLED=1, use AUTH_COOKIE_SECURE=1 behind TLS, configure BRIEFR_SETTINGS_KEY for DB-stored secrets, rotate wallboard token, and optionally add Cloudflare Zero Trust at the edge.
