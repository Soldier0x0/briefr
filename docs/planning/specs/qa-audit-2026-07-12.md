# QA Audit — 2026-07-12 (functionality, UI/UX, operations)

**Status:** Observation only — **no code changes in this document.** Every finding
below was reproduced live against a running dev instance (backend + frontend,
seeded SQLite dev DB, 15 CVEs) and cross-checked against source. Where a finding
overlaps an already-tracked item, it's cross-referenced rather than duplicated.

**Method note:** the Browser preview's screenshot capture failed repeatedly in this

## 1. Functionality / reliability findings

### F1 (P0-adjacent) — DetailDrawer DETECT tab: 30-second blocking call, then a user-visible false timeout

**Reproduced:** opening the DETECT tab on a CVE, `GET /api/cves/{cve_id}/detection`
took **30,357 ms** to respond (backend log, `briefr.access`). The frontend's own
request timeout fired before that, so the user sees *"Could not load detection
content. Request timed out — the server may be overloaded. Try again in a
moment."* even though the backend was still working and eventually returned `200`.

**Root cause:** [`backend/routers/cves.py:1537`](../../../backend/routers/cves.py)
(`GET /api/cves/{cve_id}/detection`) calls out to GitHub Search
([`backend/detection/rule_sources.py:44`](../../../backend/detection/rule_sources.py),
15 s timeout) synchronously, in the request path, on every first (uncached) view of
a CVE's DETECT tab. In this dev environment `GITHUB_TOKEN` is unset, so the call
runs unauthenticated, is slow, and the backend log shows it ultimately failing with
`401`: `GitHub Search failed (query='CVE-2026-99999+repo:SigmaHQ/sigma'): 401`.
**One external source's slowness/failure blocks the entire endpoint response** —
Sigma/Elastic rules, generated templates, and SIEM queries all wait behind the
GitHub call even though none of them depend on it.

**Why this matters beyond the dev environment:** any operator who hasn't configured
`GITHUB_TOKEN` (optional per the docstring, but the *unauthenticated* path is
exactly what's slow) hits this on **every CVE's first DETECT view** — not a rare
edge case. It also risks tripping GitHub's unauthenticated rate limit (10
req/min) under normal analyst use, at which point every subsequent DETECT open
gets the slow-then-fail path.

**Proposed fix (not implemented here):** run the GitHub Search call with
`asyncio.gather` alongside the other rule sources instead of sequentially, so a
slow/failing GitHub call no longer gates the rest of the response; and/or shorten
its own timeout and treat a `401`/network failure as an immediate skip (already
partially done — the `except` at line 72 logs and continues) rather than only
after the full 15 s elapses. Separately, verify the frontend's fetch timeout for
this endpoint is at least as long as the backend's worst-case latency, or (better)
make the frontend timeout match the *shortest* source's guaranteed latency once
sources run in parallel.

**Proposed BACKLOG entry:** **QA-F1**.

## 2. UI/UX findings

### U1 — DetailDrawer header: hard-clipped, not wrapped, at mobile widths

**Reproduced:** at 375px viewport (iPhone-class width), `.drawer-header`'s content
— CVE ID, severity badge, Unpin/Start investigation/Review indicators/REPORT
buttons, close button — measured **569px of content in a 376px-wide container**
(193px overflow), with `overflow: hidden` on the containing `.drawer-panel`
([`DetailDrawer.css`](../../../frontend/src/components/DetailDrawer.css)). The
excess is **clipped, not scrollable or wrapped** — some of that row is simply
invisible at this width.

**Root cause:** `.drawer-header` ([`DetailDrawer.css`](../../../frontend/src/components/DetailDrawer.css))
is `display: flex` with no `flex-wrap` and no dedicated `@media` rule collapsing
its action-button row at narrow widths. The drawer *does* have a `max-width: 1023px`
breakpoint that turns it into a bottom sheet (§ "Responsive drawer" rules), but
nothing inside that breakpoint (or the deeper 900px/560px ones, which only target
the OTX group list) addresses the header's own button row.

**This is very likely what "text overflowing" and "too crowded" both point at** in
the drawer — same root cause, one missing responsive rule.

**Proposed fix (not implemented here):** wrap the header actions onto a second row
at narrow widths (`flex-wrap: wrap` plus a max-width breakpoint), or move
Start investigation / Review indicators / REPORT into an overflow menu on mobile,
keeping only Pin and Close always visible — consistent with how `.header-right`
already handles overflow via `.header-overflow-wrap` (see U3 below for a sibling
case of the same pattern done correctly elsewhere).

**Proposed BACKLOG entry:** **QA-U1**, folds into the existing UX-C1/UX-C2 button
work (same file, same "interactive control consistency" spirit) rather than
opening unrelated new scope.

### U2 — DetailDrawer: BRIEFR's signature accent color is real but thin, not felt as a signature

**Reproduced (with a documented false-start — see §4 for the corrected method):**
`var(--accent)` (`#c8b88a`, the warm gold token distinct from `--red`) genuinely
renders in the drawer — confirmed on the Pin/Unpin active state, the active tab's
underline, and the summary blockquote's left border. But across a full Overview-tab
scan (88 descendant elements), only **3 distinct elements** carry it; on the
sparse-data Intel tab (55 elements) it's the same handful of chrome elements, not
content. Everything else in the drawer is `--text`/`--text2`/`--text3` gray or
`--red`/`--border` — which is *correct* per PRODUCT.md (red reserved for
destructive/severity, density over decoration), but the net effect is that accent
shows up only in 2–3 small chrome touches per tab, easy to miss, which matches
the "lost" description even though it isn't technically absent.

**Assessment:** this is a **design-weight** finding, not a functional bug — the
color is applied correctly everywhere it's coded to appear; the code just doesn't
currently give the accent a strong-enough anchor point to read as a "signature."
No fix is prescribed here (a design decision, not an RCA-derivable one) — flagged
for a design pass, e.g. one deliberate accent anchor per tab (a section label, an
icon, a border) rather than spreading 2–3 touches across the whole panel.

**Proposed BACKLOG entry:** **QA-U2** (design review, not a coded "fix").

### U3 — Global header: 29px real horizontal overflow at ~375px viewport widths

**Reproduced:** at 376px, `.header-inner`'s `scrollWidth` (405px) exceeds its
`clientWidth` (376px) by 29px, confirmed via `scrollWidth`/`clientWidth`
(`.header-nav` correctly verified `display:none` at this width — not the cause).
`.header-right` itself fits its own children cleanly (256px content in a 256px
box) — the overflow is in the combined `.header-left` (logo, ~110px) +
`.header-right` (~256px) not leaving room for `.header-inner`'s own padding/gap at
this specific width. Smaller and more marginal than U1 — likely only visible on
narrower real devices (iPhone SE-class, 375px) rather than the common 390–430px
range.

**Proposed fix (not implemented here):** audit `.header-inner`'s padding + gap
budget against `.header-left` + `.header-right`'s combined minimum width at
exactly 375–390px; likely a small `clamp()` or padding reduction at a new
sub-640px breakpoint tier.

**Proposed BACKLOG entry:** **QA-U3**, low severity — bundle with U1 (same
responsive-pass PR) rather than shipping alone.

## 4. Investigation-tooling false positives (recorded so a future pass doesn't re-walk them)

1. **"Brief page renders fully stacked above Feed"** — the accessibility-tree
   reader (`read_page`) walks the raw DOM regardless of the HTML `hidden`
   attribute, so a kept-mounted-but-hidden tab (`App.jsx` line 866,
   `hidden={activeTab !== 'brief'}`, a legitimate keep-mounted-for-fast-switching
   pattern) appeared to be full-height stacked content. Verified via
   `getBoundingClientRect()` + `getComputedStyle()` that the hidden tab
   contributes 0 real layout height. **Not a bug** — a tool-reading artifact.
2. **"Accent color entirely absent from the drawer"** — first pass queried the
   wrong DOM subtree (`document.querySelector('.drawer-panel, aside')` can match
   an unrelated `aside`) and checked a non-existent CSS property name
   (`borderColorTop`), producing a false zero. Corrected in U2 above.
