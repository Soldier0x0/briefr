Preface

How BRIEFR is built, and why — the long version

This is not a quick reference. It's written to be read start to finish, the way you'd work through a textbook chapter by chapter: a concept, then real code, then the reasoning behind it, then questions to check you actually absorbed it — not just recognized it.

How to study this, not just read it

BRIEFR's own internal docs/LEARNING_PATH.md has the right method, and this book follows it at full depth across the whole codebase instead of four modules: you don't learn a system by reading about it, you learn it by tracing it and re-explaining it in your own words.

  1. Read one chapter fully — the concept, the code, the reasoning.
  2. Open the real file in the repo and find the exact function discussed. Read it in context, not just the excerpt here.
  3. Close the chapter and explain it out loud, unaided, as if to an interviewer who will ask a follow-up.
  4. Answer every self-check question at the end without looking back. If you can't, that's the signal to re-read — not a failure, that's what the question is for.
  5. Move on only when you could defend a design decision, not just describe it.
  6. Prefer the multi-file book at docs/study-guide/ for reading (responsive TOC drawer, faster page loads). Edit this monolith, then run python scripts/build_study_guide_book.py to regenerate.

Part 0 covers concepts you'll need before anything else makes sense — read it first even if some of it is familiar, because a few terms (watermark, hub suppression, operational priority) are BRIEFR-specific and get redefined here. Before that, the System Design page gives you the whole shape of the system in four pictures — worth a first look now, and worth returning to after every Part as a reality check.

Part 0 · Mechanics

The engineering patterns you'll see everywhere

Fourteen recurring ideas. None are BRIEFR inventions — they're standard patterns — but you'll meet every one of them again by name in the chapters ahead, so it's worth having a crisp definition of each before that happens.

A word on why this book leads with mechanics rather than jumping straight to main.py: almost every "why did they build it this way" answer in the chapters ahead turns out to be one of these fourteen patterns applied to a specific problem. Once you recognize the pattern, the specific application stops looking arbitrary.

Client–server & REST

The browser (client) never touches the database directly. It sends HTTP requests to the FastAPI backend (server), which is the only thing with database credentials. "REST" here just means: resources are nouns in the URL (/api/cves/{id}), and the HTTP verb (GET/POST/DELETE) says what you're doing to that noun.

Why it matters here: every security boundary in BRIEFR sits at this line. The frontend enforces nothing — it just doesn't render buttons a user can't use. Real authorization always happens in dependencies.py, server-side.

Session cookie vs. JWT

A session cookie is an opaque ID; the server looks it up in a table to find out who you are. A JWT (JSON Web Token) is self-describing — it carries the claims (user_id, role) inside itself, cryptographically signed, so the server can verify it without a database lookup.

Why it matters here: BRIEFR uses both, deliberately, for different halves of the same login: a short-lived JWT access token for speed, and an opaque, database-backed refresh token for revocability. Chapter 11 is entirely about why one alone wasn't enough.

Password hashing (bcrypt)

You never store a password — you store bcrypt(password, salt), a one-way function. bcrypt is deliberately slow (tunable via a "rounds" cost factor) so that even if the hash table leaks, brute-forcing it is expensive per guess.

Why it matters here: BRIEFR uses bcrypt directly rather than a wrapper library — see Chapter 11 for exactly why, and for the "dummy hash" trick that closes a timing side-channel.

Connection pooling

Opening a new database connection is expensive (TCP handshake, auth, session setup). A pool keeps a set of connections open and hands them out to requests as needed, instead of opening/closing one per request.

Why it matters here: Postgres uses a real pool (asyncpg) that can be exhausted under load, raising a specific PoolExhaustedError. SQLite, BRIEFR's dev/test fallback, has no pool at all — a fact with real consequences, in Chapter 9.

Token bucket rate limiting

Imagine a bucket that refills with tokens at a fixed rate and holds a maximum capacity. Every request costs one token; no tokens, no request (or it waits/gets rejected). This smooths bursts while still allowing occasional spikes, unlike a rigid "N requests per fixed minute" counter.

Why it matters here: BRIEFR runs token buckets in both directions — throttling inbound clients (Chapter 12) and pacing its own outbound calls to NVD/GitHub/OTX so it never gets banned (Chapter 16).

Circuit breaker

Borrowed from electrical engineering: after too many consecutive failures calling a dependency, "open the circuit" — stop even trying, fail fast, for a cooldown window. This protects both your own system (no thread pool exhaustion waiting on a dead dependency) and the dependency (no hammering a service that's already down).

Why it matters here: every external feed (NVD, OTX, GitHub, KEV) goes through a shared circuit breaker in resilient_client.py — Chapter 16 walks through the actual state machine.

SSRF (Server-Side Request Forgery)

An attack where a server is tricked into making an HTTP request on the attacker's behalf — often to internal-only services (metadata endpoints, internal admin panels) the attacker couldn't reach directly. Classic vector: any feature where the server fetches a URL supplied by a user.

Why it matters here: operator-supplied webhook destination URLs are exactly this shape of risk. Chapter 27 covers BRIEFR's mitigation (resolve → validate → pin) in full, with the real code.

Idempotency & watermarks

An operation is idempotent if doing it twice has the same effect as doing it once — critical for anything that might crash mid-run and get retried. A "watermark" is a saved checkpoint (a timestamp, an ID, a commit SHA) marking how far a sync has progressed, so a resumed run starts from there rather than from the beginning — or worse, from nowhere.

Why it matters here: this is the single most repeated idea in the ingest layer (Chapter 14) — every feed answers "what's my watermark, and what happens if I crash right after reading it but before saving it?" differently, and those differences are revealing.

Async/await & the event loop

Python's async def functions don't run in parallel threads — they cooperatively yield control at each await point, letting one thread juggle thousands of in-flight I/O operations (HTTP calls, DB queries) without blocking. It's concurrency, not parallelism.

Why it matters here: nearly every backend function in this book is async def. It's also why a single asyncpg connection can't run two queries "at once" even from concurrent-looking code — a real bug class referenced in Chapter 21.

ORM vs. raw SQL

An ORM (SQLAlchemy, Django's ORM) maps database rows to objects and can generate SQL for you, abstracting the dialect differences between databases. Raw SQL means you write the query text yourself.

Why it matters here: BRIEFR deliberately has no ORM. Every query is hand-written SQL, in two dialect-specific versions where needed (Chapter 9) — a real cost (more code, more discipline) paid for query-level control and zero abstraction-leak surprises.

CVSS — Common Vulnerability Scoring System

A 0–10 severity score computed from a vulnerability's technical characteristics (attack vector, complexity, privileges required, impact). It answers "how bad is this if exploited" — it says nothing about whether anyone is actually exploiting it, or whether it affects you.

Why it matters here: CVSS is one of six inputs to BRIEFR's Risk Score, weighted at only 0.10 — deliberately low, because it's the least differentiating signal (Chapter 18 explains why).

EPSS — Exploit Prediction Scoring System

A FIRST.org model producing a 0–1 probability that a given CVE will be exploited in the wild in the next 30 days, based on observed scanning/exploitation telemetry across the internet. Unlike CVSS, it's a live, moving prediction, not a static technical rating.

Why it matters here: EPSS is weighted 0.15 in the Risk Score, and its day-over-day delta (not just its level) independently feeds the Momentum component and the morning brief's "EPSS movers" section.

KEV — Known Exploited Vulnerabilities (CISA)

CISA's curated catalog of CVEs confirmed to have been actively exploited in real attacks — not predicted, confirmed. US federal agencies are required to patch KEV entries by a published due date.

Why it matters here: KEV membership is weighted 0.25 in the Risk Score (second only to asset relevance) and independently floors the newer Threat Score at 80 regardless of anything else — Chapter 18 explains why a confirmed-exploited CVE is treated almost as a special case rather than just another weighted input.

CPE — Common Platform Enumeration

A structured naming scheme for software/hardware (cpe:2.3:a:vendor:product:version:...) that NVD attaches to CVEs to say precisely which versions are affected — the machine-readable version of "affects Apache 2.4.0 through 2.4.53".

Why it matters here: matching your declared asset stack against CPE version ranges is the mechanical core of the 0.35-weighted asset component — Chapter 19 is the whole story of how that matching actually works, including what happens when a CVE has no CPE data at all.

MITRE ATT&CK

A knowledge base of adversary tactics and techniques observed in real intrusions, organized into a matrix (Initial Access, Execution, Persistence, ...) with each technique given an ID like T1190 (Exploit Public-Facing Application).

Why it matters here: ATT&CK technique IDs are the routing key for BRIEFR's detection-engineering templates (Chapter 21) and its threat-scenario narratives (Chapter 23) — a CVE maps to a technique, and the technique maps to everything downstream.

Sigma rules

A vendor-neutral, YAML-based format for writing detection logic once and translating it into any SIEM's native query language (Splunk SPL, Elastic KQL, Microsoft Sentinel KQL, and others) via a converter.

Why it matters here: BRIEFR both fetches community Sigma rules and generates its own from templates (Chapter 21), then translates them into concrete SIEM queries for whichever platform an analyst actually runs.

Where each primer idea shows up later

Use this as a map, not a second textbook: circuit breaker → Chapter 16 (resilient_client.py); watermark/idempotency → Chapter 14 (feeds); JWT+refresh → Chapter 11 (auth); token bucket → Chapters 12 and 16; SSRF → Chapter 27 (webhooks); CVSS/EPSS/KEV/CPE → Chapter 18–19 (scoring/matching); ATT&CK/Sigma → Chapter 21 (detection); connection pooling / no-ORM → Chapter 9 (data layer).

Part 0B · System architecture

The shape of the whole system, before the parts

Three chapters answering the questions a "how is this actually put together" review always asks first: is it a monolith or microservices, and why; what hardware footprint the design choices actually target; and — the one that ties every later chapter together — what talks to what, and just as importantly, what was deliberately kept from talking to what.

Part 0B · Chapter A1

Monolith by design — and why not microservices

One process, one database, one deploy artifact. The absence of microservices here isn't a gap to fill later — it's a fit to the actual problem.

ROADMAP.mddeploy/briefr-backend.service

What "microservices" would even mean here

A microservices architecture splits a system into independently deployable services, each usually owning its own database, talking to each other over the network (HTTP or a message queue), so that different teams can develop, deploy, and scale each piece separately. BRIEFR is the opposite of that on every axis: one FastAPI process (main.py) serves every route, one Postgres (or SQLite) database holds every table, one systemd unit (deploy/briefr-backend.service) is the entire deployable artifact, and the scheduler that runs feeds, scoring, and correlation lives inside that same process, not as a separate worker service. Even Procrastinate (Chapter 17) — which sounds like it might be a separate job-queue service — is a library running an in-process worker inside the same Python process, coordinating purely through shared Postgres tables, not through a network call to some other running service.

Why a monolith fits this specific problem, not just "monoliths are simpler in general"

The generic case for microservices is real but conditional: it pays off when different parts of a system need independent scaling (one component gets 100x the traffic of another), independent deployment cadence (different teams shipping on different schedules without blocking each other), or genuine fault isolation (one component crashing shouldn't take down an unrelated one). None of those conditions hold for BRIEFR as it's actually used. It's explicitly a single-operator tool today (ROADMAP.md's non-goals table states plainly: "Multi-tenant SaaS in V1.x" is out of scope, with schema seams left for a possible future, not built now) — there's no independent traffic pattern to scale one piece against another, because there's fundamentally one analyst's browser making requests. There's no multi-team deploy-cadence problem to solve, because one person (or a small team) maintains the whole thing. And fault isolation between, say, the correlation engine and the CVE list view is achieved more simply — and more cheaply — by the request-path discipline you've now seen enforced everywhere in this book (heavy work happens in the scheduler, never blocking a request) than by splitting them into separate network-connected services.

What microservices would have actually cost here is concrete, not abstract: every cross-component call that's currently a Python function call within one process would become a network request, needing its own error handling, retries, timeouts, and versioning story — exactly the kind of complexity Chapter 16's circuit breakers and Chapter 15's locking already have to solve for BRIEFR's genuinely external dependencies (NVD, OTX, GitHub). Multiplying that same complexity across internal components that don't need it would be pure overhead, paid for a scaling and fault-isolation benefit the system doesn't currently need.

The one thing that looks like a second service — and how it's actually kept separate correctly

ROADMAP.md's non-goals table names the one place BRIEFR's own team considered something closer to a real second service: an optional telemetry/log-analytics sidecar referred to internally as "Jupiter" (built on ClickStack), explicitly kept optional and outside core — the table states the core app is deliberately not becoming "log firehose ingestion" and that this capability, if wanted, is "an optional Jupiter sidecar," not a rebuild of the core system's architecture. The same table rules out forking or rebuilding a tool like Kibana/HyperDX for that purpose ("use stock ClickStack for telemetry UI if needed") — the instinct to reach for off-the-shelf infrastructure rather than building and maintaining a bespoke second service is the same monolith-favoring instinct applied one level up: even the one legitimate case for "another service" gets handled by adopting an existing tool as an optional add-on, not by growing BRIEFR's own architecture into a distributed system.

Also explicitly ruled out, and worth knowing precisely why: ROADMAP.md's non-goals also name "commercial SIEM replacement" and "generic LLM chat SOC" — both real products other tools already build well. BRIEFR positions itself narrowly as an intel, detection-content, and investigation pane, not a log-ingestion platform or a chatbot wrapper — a scope decision that, not coincidentally, is also what keeps the monolith viable: a SIEM's log-firehose ingestion volume is exactly the kind of workload that would eventually force a distributed architecture, and BRIEFR has deliberately scoped that requirement out rather than build toward it.

Part 0B · Chapter A2

The resource-consciousness thread — designed for modest hardware

A recurring, mostly-unstated design bias runs through nearly every chapter in this book: keep the footprint small enough to run comfortably on a low-end VPS. This chapter names it explicitly and is honest about where it isn't yet backed by a documented number.

ml/embeddings.pyrate_limit.pydocs/audit/PHASE_06_performance.md

Naming the thread — a design bias visible only once you look across chapters

No single file in this codebase says "keep memory under X gigabytes." But look back across the chapters you've already read and a consistent pattern emerges, choice after choice, each one individually justified on its own terms and collectively adding up to a system that stays lightweight: CPU-only ONNX embeddings (Chapter 24 — BAAI/bge-small-en-v1.5 via fastembed, no GPU, no PyTorch runtime) instead of a larger transformer model that would need meaningfully more RAM and ideally a GPU to run at reasonable speed. A single uvicorn worker (Chapter 12's rate-limiting chapter noted this explicitly — --workers 1) instead of a multi-process pool that would multiply baseline memory by however many workers ran. In-memory rate-limit buckets, the outbound API queue, and the read cache (Chapters 12, 16, and the API surface chapters) instead of standing up a separate Redis instance purely to hold small, ephemeral counters. SQLite as the zero-config default (Chapter 9) rather than requiring Postgres even for a first-time evaluator just trying the tool out. Free and cheap-tier hosted LLM APIs (Chapter 24) rather than self-hosting an open-weight LLM locally, which would require the single largest chunk of RAM and compute of anything in this list by a wide margin. Client-side PDF generation (Chapter 5) instead of a headless-Chromium rendering process living inside the backend. Lazy-loaded, code-split chart and export libraries on the frontend (also Chapter 5) instead of one enormous eagerly-loaded bundle.

None of these were framed, in the code or docs, as "we did this to hit a RAM budget" — each has its own local justification (privacy, cost, simplicity, avoiding a new dependency). But taken together, they describe a system whose default configuration is comfortable running on genuinely modest hardware: a small VPS with a couple of CPU cores and a few gigabytes of RAM, not a dedicated machine with a GPU and dozens of gigabytes free.

The honest gap: this isn't a documented, benchmarked number yet

It would overstate the case to claim BRIEFR has an official "runs in 2GB RAM on 2 cores" specification — it doesn't, and it's worth being precise about that rather than inventing a certainty the project itself doesn't claim. The project's own performance audit (docs/audit/PHASE_06_performance.md) says so directly, listing it as an open gap in its own words: "what's missing is guidance/limits: recommended CPU/RAM/disk envelopes." The same audit's overall score of 7/10 for performance readiness reflects real, specific findings worth knowing precisely rather than a vague "needs work": the Postgres connection pool defaults to a minimum size of 1 and maximum of 10 (modest, and consistent with a small-footprint target, but also a real concurrency ceiling nobody has load-tested against); the CVE feed defaults to OFFSET-based pagination rather than the more scalable keyset pagination that already exists but is opt-in; recharts is imported statically in chart wrappers with no bundle-size budget enforced in vite.config.js; and roughly twenty places in the db/ layer run an await execute/fetch call inside a loop, a pattern worth watching for N+1-style query cost as data volume grows. None of these are urgent given today's usage pattern (a single operator's browser), and the audit says as much — but they are the concrete reasons "how much hardware does BRIEFR actually need" doesn't yet have a number attached to it, only a design direction.

What the design direction is consistent with, stated as a target rather than a guarantee

Given the choices actually made — a single worker process, CPU-only small-model inference, in-memory ephemeral state instead of a separate cache service, and a SQLite path that needs no database server at all for evaluation — the natural, honest way to state the target is: this architecture is built to be comfortable on a small VPS in the low single-digit gigabytes of RAM and one or two CPU cores, for a single operator's traffic pattern — not "requires 16GB and a GPU," and not "certified to run in 512MB" either. If you're sizing a box to run this yourself, a couple of cores and 2–4GB of RAM is the range every individual choice in this system points toward, even though — per the paragraph above — nobody has yet run the load test that would turn that direction into a documented, verified number. Chapter titled "Roadmap, reversals & open gaps" later in this book lists exactly this as an open item: publishing a real recommended CPU/RAM/disk envelope, backed by measurement rather than inference from design choices.

Part 0B · Chapter A3

How the pieces connect — and why some deliberately don't

The single most useful mental model for holding this entire codebase in your head at once: the database is the message bus, and most "why isn't X wired to Y" questions have a real, considered answer.

The one connectivity fact that explains most of the others: the database is the message bus

Read across every chapter so far and one structural fact keeps recurring in different clothes: the scheduler (feeds, scoring, correlation, detection-context sync, embeddings backfill) and the request path (routers) essentially never call each other's functions directly. They communicate almost entirely by writing to, and reading from, the same Postgres/SQLite tables. A scheduled job computes a correlation snapshot and writes it to a table; a router reads that table. A scheduled job upserts a CVE's EPSS score; a router reads it. This is, functionally, the same pattern a message queue or event bus gives you in a distributed system — a durable, asynchronous handoff point between producer and consumer — except BRIEFR gets it for free from the database it already needs for everything else, with no extra infrastructure. Once you see this pattern, most of the "why does A never call B directly" questions in this codebase have the same one-line answer: because A writes to a table, and B reads that table, on its own schedule.

It's worth asking the alternative directly, since "just use Postgres" can look like an oversight rather than a decision: why not a real message broker — Redis Streams, RabbitMQ, Kafka — sitting between the scheduler and the API the way a textbook distributed system would? A broker earns its cost when you need at-least-once delivery semantics across process boundaries, consumer groups scaling independently of producers, or replay from an arbitrary offset — none of which apply here, because there is exactly one producer process and one consumer process, and they're the same process (Chapter A1). Adding a broker would mean a new piece of infrastructure to deploy, monitor, and keep running on every self-hosted box, purely to re-implement a durable handoff Postgres already gives BRIEFR as a side effect of tables it needs anyway. The one thing a real broker buys that a table doesn't — a push notification the instant new data lands, instead of a poll or a fixed schedule — isn't needed either: nothing in BRIEFR promises sub-second freshness, every feed already runs on its own interval, and the API's own reads are already cheap indexed lookups regardless of exactly when the row was written. This is the same "adopt a dependency only when the simpler tool genuinely can't do the job" instinct behind the monolith decision in Chapter A1, applied one layer down.

A map of what's actually connected to what

Connected, one-way, through the database: feeds → the cves/kev/epss_history tables → scoring reads them on request; correlation's nightly job → per-CVE snapshot tables → routers/cves/intel.py's correlation endpoint reads them; the embeddings backfill job → stored vectors → semantic search reads them (Chapter 24's "must use stored vectors only" rule is this exact pattern, stated as an explicit constraint rather than left implicit); webhook-alert trigger functions (Chapter 27) are called only from scheduler jobs, never from a router, and dispatch outward to Discord/Telegram/generic HTTPS — a one-way fan-out, nothing calls back in.

Connected, directly, as ordinary function calls within one request: a CVE detail request calls into scoring, matching, and template-sentence generation synchronously, because those are cheap, deterministic, in-process computations appropriate for the request path (Chapter 18's whole "explainable formula, not a request-path bottleneck" design is precisely what makes this direct call safe, where a slow correlation join was not — Chapter 20's ADR-004 incident is the cautionary tale for what happens when something that should be an async, database-mediated handoff gets called synchronously instead).

Deliberately not connected, and each for a stated reason: correlation and detection engineering (Chapters 20–21) never call each other — correlation only ever hands scoring a boolean escalation flag, and detection never queries correlation state at all, because the two answer genuinely independent questions (is this CVE part of a real campaign, versus what would a detection rule for it look like) that don't need each other's internals to function correctly. The security_architecture/ module (Chapter 26) deliberately does not implement its own matching or scoring logic, reusing existing functions instead — a connectivity choice as much as a code-reuse one, since a hand-rolled second implementation would be a second thing that could silently drift from the first. Generated Sigma/SIEM rules (Chapter 21) are never automatically deployed into a live SIEM — the pipeline stops at "here's a rule for a human to review and paste in," a deliberate air gap between "BRIEFR generated this" and "this is now running in production detection," because unreviewed generated content becoming live detection logic without a human in the loop is a risk nobody chose to accept. The wallboard (Chapter 30) runs its own separate cookie-session scheme rather than reusing the main JWT auth system, and the scoped search-token bearer credential (Chapter 11) is deliberately walled off from the admin permission system entirely — two different flavors of the same instinct: a narrower credential for a narrower job, not wired into the broader system.

The browser never talks to the outside world directly — everything is proxied

One connectivity boundary is easy to take for granted precisely because it's so consistently enforced: the React frontend never calls NVD, OTX, GitHub, or any LLM provider directly from the browser. Every external call is proxied through the FastAPI backend, which is the only thing that ever holds an API key for any of those services. This isn't a performance optimization — it's a security boundary stated in different terms than Chapter 11's authentication chapter, but built on the same underlying principle: a credential should live in exactly as many places as it needs to, and the browser, being fully visible to whoever is sitting at it, is never one of those places for a third-party API key.

Why AI is used sparingly — the case against a bigger role, stated once

Every chapter so far has made one small, local "why not more ML/LLM here" argument on its own turf. This chapter pulls all of them into a single line of reasoning, because the pattern across them is the actual answer, not any one instance of it.

scoring/risk.pyai/llm_router.pyml/embeddings.pyROADMAP.md

The question worth asking directly: this is 2026, AI is everywhere — why isn't BRIEFR built around it?

It's a fair challenge, and worth answering directly rather than deflecting to "we use some AI." BRIEFR could plausibly have been built as an LLM-first product: a chat interface over your CVE data, an agent that decides what's a priority, a model that learns your organization's risk tolerance from feedback. None of that is what got built. Instead, across every chapter in this book, AI shows up in exactly two narrow, well-fenced roles — CPU-only local embeddings for semantic similarity (Chapter 24), and hosted-LLM calls for three specific, optional enrichment tasks (Chapter 24B) — and everywhere else, a deterministic formula, a fixed lookup table, or plain code does the job instead. That's not an oversight or a resource constraint alone; it's a position, and it's visible in four separate, independently-justified decisions that happen to all point the same direction.

Four decisions, one pattern: explainability beats raw predictive power for this problem

Risk Score is a fixed weighted formula, not a learned model (Chapter 18). A gradient-boosted tree trained on historical exploitation data could plausibly out-predict the six-component formula BRIEFR actually ships. It wasn't built, because a security analyst asking "why is this CVE ranked above that one" needs an answer that is the computation, not an approximation of it produced by a separate explainability layer bolted onto a black box afterward. A fixed formula is also perfectly reproducible — the same CVE and asset profile score identically today and a year from now, which matters when an analyst asks why a score changed and the honest answer needs to be a specific component delta, never "the model's weights drifted during retraining."

Detection rules are generated by an LLM but never auto-deployed (Chapter 21, Chapter A3). An LLM extracts detection-rule artifacts from CVE text — genuinely useful, genuinely "AI" in the loose sense — but the pipeline stops at "here's a rule for a human to review," on purpose. Generated content becoming live detection logic in a real SIEM without a human reading it first is exactly the kind of unreviewed-automation risk this project has chosen not to accept, regardless of how good the model producing it is.

Semantic search stays hybrid, never vectors-alone (Chapter 24). Embeddings are excellent at "this text means something similar" and comparatively weak at exact-token matching — a CVE ID, a specific version string, an error code pasted in verbatim. Rather than trust the model to cover that gap, BRIEFR blends vector similarity with ordinary keyword search deliberately, so the two techniques cover each other's blind spots instead of asking one imperfect technique to do a job it's structurally bad at.

Every LLM feature has a deterministic fallback, without exception (Chapter 24). BRIEFR must fully function for an operator who configures zero LLM API keys — a real, supported deployment mode, not an edge case — because every LLM-touched feature is additive polish layered on a core product whose correctness never depends on it. That's the constraint that keeps the previous three decisions honest: nothing in the product is allowed to become load-bearing on a model's output, so nothing has the incentive to reach for one just because it's available.

"Generic LLM chat SOC" is a named non-goal, not an oversight

ROADMAP.md states this as a standing decision with a reason on record, not a gap waiting to be filled: a chat-style SOC assistant is "considered a commodity" — plenty of other tools already build a general-purpose LLM chat layer over security data, and building another one wouldn't be BRIEFR's contribution. The project's actual bet is the opposite of "put a model in front of everything": pick the handful of places where a model's output is genuinely additive (summarizing, extracting structure from messy free text) and everywhere else, do the more boring thing that can be pinned down, tested, and explained exactly. That's a scope decision as much as a technical one, and it's the same instinct — see Chapter A1's non-goals table — that also keeps BRIEFR a monolith rather than a distributed system: narrow the problem on purpose, rather than reaching for the most powerful available tool by default.

What would have to change before AI's role grew

None of this is a permanent ceiling — it's a statement about where the tradeoff currently lands, and it's worth being precise about what would actually move it. A learned risk-scoring model would become worth the explainability cost only once there's enough of BRIEFR's own labeled outcome data (which CVEs an operator actually acted on, and which they correctly ignored) to meaningfully outperform the fixed formula rather than just approximate it — data this project doesn't yet have because it's a young, single-operator-oriented tool, not a mature platform with years of feedback loops. Auto-deploying generated detection rules would need a much higher, independently-verified confidence bar than any current model realistically clears, plus a real rollback story if a bad rule shipped automatically. And a genuine chat interface would need to solve, honestly, the same problem every LLM-chat security product has to solve — hallucination on security-consequential answers — before it could be trusted anywhere near "should I act on this," which is precisely the question BRIEFR's fixed, auditable scoring answers today without that risk.

Why Business Source License 1.1 — and the AGPL decision it reversed

The license changed twice before the public flip: proprietary → AGPL-3.0-or-later → BSL-1.1. This chapter explains the current model and is honest about the reversal, since a study guide that hides its own subject's history isn't trustworthy.

LICENSEdocs/planning/STRATEGY.md

What's actually on record — including the reversal

docs/planning/STRATEGY.md §6 records two decisions in sequence, both dated: "Decided 2026-07-10 (Track F2): AGPL-3.0-or-later," then "Superseded 2026-07-19 (Track F2-R)" in favor of the Business Source License 1.1 (BSL). Both were made before the public repository flip, which matters for exactly one reason: no external party had received code under the AGPL grant yet, so reversing it carried none of the legacy-grant complications that revoking a license already held by outside forks would create. The current, governing license is BSL-1.1 — LICENSE, CONTRIBUTING.md, and every active source file's SPDX header (SPDX-License-Identifier: BUSL-1.1) all agree on this.

What BSL-1.1 actually does — a paywall with a built-in expiry, not permanent copyleft

BSL is a different shape of license than either AGPL or a permissive license, and it's worth being precise about the difference rather than treating "source-available" as a synonym for "open source." BRIEFR's specific terms (set in the LICENSE file's "Additional Use Grant"): anyone may read, copy, modify, and self-host the code free of charge for personal, non-commercial purposes — but use by or on behalf of a for-profit organization ("Commercial Use") requires a one-time, lifetime commercial license purchased from the Licensor. That is the paywall AGPL does not have — AGPL would let a business self-host and even modify BRIEFR commercially for free, as long as they shared modifications back over the network; BSL asks that same business to pay once, with no such carve-out. The second defining feature is the "Change Date": four years after each version's publication, that version automatically converts to the Apache License 2.0 — fully permissive, no restrictions at all. So BSL isn't a permanent restriction; it's a time-boxed head start, letting the Licensor capture commercial-use revenue on recent versions while guaranteeing that revenue window eventually closes and the code becomes as open as it gets.

This is the same license family HashiCorp used for Terraform/Vault and IBM continues to use for Terraform since its BSL-authoring MariaDB origin — a well-understood, if debated, pattern for source-available commercial software that wants public code review and free non-commercial self-hosting without giving competitors a free ride to build a paid hosted clone.

What this costs, honestly — and why AGPL was considered first

The tradeoff is real. Some organizations and distros flatly exclude BSL-licensed dependencies from "open source" bundles (it isn't OSI-approved), which AGPL — however restrictive — clears. AGPL's specific worry (a hosted competitor built on BRIEFR's own code, contributing nothing back) is answered differently by each license: AGPL answers it by forcing that competitor to publish their modifications; BSL answers it by making that competitor pay for the right to run it commercially at all, a blunter but more directly monetizable mechanism. The Track F2 → F2-R sequence in this project's own history is itself worth understanding as a real example of a team trying the reciprocal-sharing answer first, and switching to the direct-payment answer once — reflected in STRATEGY.md's "Adoption engineering" pillar — commercial-license revenue became the more important goal than guaranteed source-sharing by commercial forks.

The concept: why "just React" is itself a decision

Modern frontend work almost always starts by picking a meta-framework — Next.js, Remix, SvelteKit — because most apps need at least one of: fast first paint for anonymous visitors, SEO-indexable pages, or server-rendered HTML for slow connections. Choosing "none of that, just a client-rendered SPA" is a real architectural decision, not a default, and it only makes sense when none of those three needs apply.

Why this was the right call for BRIEFR specifically

There are no anonymous visitors to give a fast first paint to, and nothing here needs to rank in search results — the two biggest reasons to reach for SSR simply don't apply. What's left is the ordinary case for a plain SPA: request the login page once, authenticate, then everything after that is API calls returning JSON that React renders. Given that, the decision collapses to "which frontend library," and React won by ecosystem gravity rather than a formal bake-off: Radix UI (the accessibility primitives ADR-003 mandates) ships first-class React bindings, react-router-dom, TanStack Table, Recharts, and cmdk all assume React as the default target, and the maintainer's own familiarity mattered too, since this is a self-hosted, largely solo-maintained project.

React 19 specifically, rather than pinning to 18, was chosen because Radix's primitives already certify React 19 compatibility, and the codebase carries no legacy class-component or old-Context-API code that a major-version bump would break. There's no exotic 19-only feature BRIEFR leans on (no Server Components, no use() hook doing anything load-bearing) — it's simply the current stable release of the library already chosen for other reasons, taken at face value.

What you gain, and what you knowingly give up

Gained: the largest available ecosystem overlap with Radix's exact primitive set; a hooks-based mental model that fits cleanly with the Context-based state approach in Chapter 4; automatic batching and improved Suspense semantics from React 19 itself; and the simplest possible deployment story — a static JS bundle served by any web server, with zero server-side runtime coupling to the FastAPI backend beyond the /api proxy.

Given up, knowingly: true first paint is slower than a framework that can stream server-rendered HTML — irrelevant here because every real user is authenticated before they see meaningful content anyway. React's re-render model also needs some memoization discipline in data-dense views (the CVE list, the correlation graph); this is mitigated rather than solved, by leaning on TanStack Table's headless, virtualization-friendly model (Chapter 3) instead of hand-rolling table performance.

A misconception worth heading off: "React 19 was chosen for its new compiler / Server Components" would be the wrong story to tell in an interview — BRIEFR uses neither. The version bump tracked ecosystem compatibility (Radix), not a feature BRIEFR actively exploits.

ADR-003 — semantic tokens and Radix, explicitly not Tailwind

The UI's actual design system: how it's built, the audit that forced it into existence, and why the obvious modern default (Tailwind + shadcn) was rejected.

The concept: design tokens

A design token is a named variable for a design decision — a color, a spacing value, a motion duration — referenced by name (--severity-critical) rather than by raw value (#c0392b) everywhere it's used. The payoff is that changing the definition in one place changes it everywhere, and more importantly, the name carries meaning a raw hex code can't: --severity-critical tells you what the color is for, so a reviewer can catch "you used the danger color for a neutral link" at a glance instead of having to remember what #c0392b means.

Why this exists: the audit that forced it

ADR-003 wasn't written speculatively — it documents the fallout of a real 2026-07-14 UX review of the running product, which found the UI "capable and deep but inconsistent and, in places, amateur/broken." The specific findings are worth reading in full because each one maps directly to a root cause in the "decision" section that follows: raw browser-default checkboxes and selects (the most visible "homemade" signal to a user); "selected/active" state rendered four different ways across the app (green feed chips, red preference radios, a red/orange nav tab, a faint sidebar highlight); the color red doing double duty for both "danger" and "just a neutral link," which is actively confusing in a security tool where red should mean something; sub-AA text contrast; bespoke, non-portaled tooltips that overflowed their containers; and one entire section of the app that had shipped essentially unstyled.

The report's own diagnosis is the important part: every one of those symptoms traced back to the same root cause — un-named, duplicated color decisions made ad hoc, component by component, with no shared vocabulary to catch the drift. That diagnosis is what justifies a token system as the fix, rather than a series of one-off patches: patching the four different "selected" colors individually would leave the mechanism that produced four different colors untouched, and a fifth would appear in the next feature.

How the fix is actually built

Two separate decisions do the work. First, CSS custom properties as the mechanism — not a CSS-in-JS library, not a utility framework — chosen because it's already the project's existing idiom (App.css already had an ad-hoc token block before this ADR formalized it), it needs zero new runtime dependency, and it supports live theme-switching (dark/light mode, the tool-wide motion toggle) purely by swapping which values a variable resolves to, with no JavaScript re-render required. Second, Radix UI primitives as the behavior layer — unstyled, accessible building blocks (Checkbox, Select, Dialog, Tabs, Tooltip, DropdownMenu, Popover) that supply focus management, keyboard navigation, and correct ARIA semantics "for free," styled entirely through BRIEFR's own tokens. This is precisely aimed at the audit's findings: Radix's Checkbox replaces the raw browser-default checkbox; its Tooltip is portaled (rendered outside the normal DOM flow, escaping overflow clipping) which fixes the tooltip-overflow bug; its focus-visible handling fixes the weak focus rings.

The system is organized as a three-layer hierarchy — Primitives (one Radix component per interaction pattern, styled) → Composites (things built from primitives, like a filter bar) → Features (whole page sections) — with an explicit rule against duplicate, bespoke implementations of the same pattern. Migration itself is staged and reversible: legacy raw token names (--red, --bg2) are kept as aliases pointing at the new semantic tokens during the transition, so nothing visibly breaks while components are migrated one at a time, each in its own component-scoped PR with a visual-regression check.

The alternatives, and why each was rejected

ADR-003 records three alternatives it seriously weighed, and the rejection reasoning is more instructive than the decision itself:

Full shadcn/ui + Tailwind — the modern default choice for exactly this situation, and probably the fastest path to a polished result. Rejected specifically because BRIEFR is a plain-CSS codebase today, and adopting Tailwind is a large, disruptive migration of a shared surface (every single component's className would change) for a project whose maintainer had already explicitly declined Tailwind. Note the reasoning isn't "Tailwind is bad" — it's "the migration cost and an explicit maintainer preference outweigh the velocity gain here."

A styled component kit (MUI, Chakra, Mantine) — these ship both behavior and a visual language. Adopting one would have fixed the accessibility gaps quickly, but fighting the kit's own opinionated look to preserve BRIEFR's dark-terminal identity was judged not worth the cost — you'd spend as much effort un-styling MUI as you'd spend styling Radix from scratch, without the same end-state control.

Hand-build every primitive, no dependency at all — zero new dependencies, maximum control, but it means re-implementing focus traps, portaling, and ARIA compliance from scratch, which is precisely the category of bug the original audit found the team getting wrong. Rejected as high accessibility risk for a self-inflicted reason (avoiding one dependency).

Shared UI primitives

components/ui/ is the shared Radix-backed primitive layer (Dialog/AlertDialog, Select, Checkbox, Switch, Tabs, Tooltip, DataGrid, DateTimePicker, EmptyState/ErrorState/Skeleton, Toast, …) styled with BRIEFR tokens. Feature code should compose these rather than inventing one-off controls — that is how ADR-003 stays enforceable across analyst and admin.

The concept: server state vs. client state

A useful split when reasoning about any app's state: server state is data that lives in a database and is just being displayed — a list of CVEs, a risk score, a correlation graph. It's fetched per-view, and the source of truth is always the server, never the browser tab. Client state is state that only exists because the user is interacting with this particular browser session right now — who's logged in, what am I currently investigating, what's my declared asset stack. Global state-management libraries like Redux earn their complexity when an app has a lot of the second kind, shared across many distant parts of the component tree. When most of an app's state is actually the first kind, a heavyweight global store mostly ends up managing cache invalidation for data the backend already owns — solving a problem that server-state libraries (or, as here, plain re-fetching) already solve more directly.

Why three Contexts turned out to be enough

Looking at what's actually global here: AuthProvider holds who's logged in and their session status; AssetProfileProvider holds the analyst's declared software stack — the input that feeds the 0.35-weighted asset-match component of every risk score (Chapter 18); InvestigationContext holds in-progress investigation/drawer state. That's the entire inventory of state that's genuinely needed in more than one distant part of the tree at once. Everything else — a CVE list, a detail drawer's contents, a correlation cluster — is fetched fresh by the component that needs it and doesn't need to be "global" in any sense. Three Contexts covering three genuinely global concerns is proportionate to that shape; reaching for Redux here would be solving for a scale of cross-cutting client state the app doesn't actually have.

Fonts, exports, and testing — the smaller decisions that round out the stack

Three unrelated-looking choices that share one thread: keep the runtime footprint and the operational dependencies as small as the SPA architecture already implies.

@fontsource/*jspdfhtml2canvaswrite-excel-fileplaywright

Self-hosted fonts, not a Google Fonts <link>

DM Sans (body/UI), DM Serif Display (headings), and IBM Plex Mono (labels, data, monospace contexts) are bundled as @fontsource npm packages and imported directly in main.jsx, rather than the far more common approach of a <link> tag pointing at fonts.googleapis.com. The code comment in main.jsx states the reasoning directly: "no runtime requests to Google (privacy posture, offline capability, no FOUT on cold loads)." Unpacking each part — privacy posture: a self-hosted security tool shouldn't leak "someone opened this page" to a third party as a side effect of rendering text. Offline capability: BRIEFR is designed to be runnable in air-gapped or restricted-network environments, where a hard dependency on reaching Google's CDN for the app to render its own fonts correctly would be a real operational failure. No FOUT (flash of unstyled text): fonts ship in the same bundle as everything else, so there's no network round-trip during which the browser shows a fallback font and then swaps it.

Client-side PDF generation, not a server-rendered report

PDF reports are built entirely in the browser: html2canvas renders a DOM node to a canvas bitmap, and jspdf assembles those bitmaps into a PDF file, all without a network round trip to the backend for rendering. The alternative most backend-heavy systems reach for is a server-side headless-browser rendering service (a Chromium instance the backend drives to print a PDF) — deliberately avoided here. The tradeoff is explicit: client-side rendering costs some CPU on the user's machine and produces a screenshot-quality PDF rather than a true vector-layout one (expect subtly soft edges and awkward page breaks in a very long report, since html2canvas is literally rastering pixels, not laying out text). What it buys in return is architecturally significant: zero backend rendering infrastructure, zero headless-Chromium dependency to keep patched and running in the FastAPI process, and reports generate instantly without ever touching the request path's heavy-work constraint (danger zone 6, mentioned throughout this book) — because generating a PDF isn't "work the backend does" at all.

56 unit test files run through Node's own built-in node:test module rather than Jest or Vitest — for what are mostly pure-function unit tests (scoring math, formatting helpers, validators), a full test framework's mocking/snapshot machinery isn't needed, and skipping it is one less dependency to version and configure. App bootstrap and dependency injection

What actually happens between "run uvicorn" and "the API is answering requests" — and why the shutdown path is engineered as carefully as the startup path.

main.pydependencies.py

The concept: application lifespan

FastAPI's lifespan is an async context manager wrapped around the entire life of the process: code before the yield runs once at startup, code after it runs once at shutdown, and everything in between is "the app is up." It exists because a web app almost always needs to acquire some resources once (a database pool, a background scheduler) rather than per-request, and release them cleanly when the process stops — not leak a half-open connection pool or leave a scheduled job mid-write when the process is killed.

async def lifespan(app: FastAPI):
    backend = "postgresql" if is_postgres() else "sqlite"
    logger.info("main.py lifespan: starting backend (%s)", backend)

    if settings.briefr_require_postgres and not is_postgres():
        raise RuntimeError(
            "BRIEFR_REQUIRE_POSTGRES=1 but DATABASE_URL is not set to a postgresql:// DSN. "
            "Migrate via Admin -> Database, apply DATABASE_URL, and restart."
        )

    if not is_postgres():
        recovery = ensure_db_or_restore()   # SQLite-only: auto-heal a corrupt file
        if recovery.get("status") == "restored":
            logger.warning("Recovered corrupt database from backup: %s", recovery.get("archive"))
    else:
        await run_postgres_migrations()   # Postgres-only: Alembic upgrade to head

    await init_pool()
    await init_db()
    # ...operator settings bootstrap, scheduler start, Procrastinate worker start...

main.py, the opening of lifespan() — abridged, real control flow

Why startup is sequenced exactly this way

Read the sequence as a dependency chain, not an arbitrary list. The Postgres-required check comes first because everything after it assumes the database posture is what the operator intended — failing loudly here rather than limping along on an accidental SQLite fallback in what was meant to be a production deploy. The SQLite corruption check and the Postgres migration step are mutually exclusive branches of the same idea: before anything reads or writes real data, make sure the schema on disk is the schema the code expects — for SQLite that means verifying the file isn't corrupt (and restoring from backup automatically if it is), for Postgres it means running any pending Alembic migrations to bring the schema to head (Chapter 10). Only after that is the connection pool opened, and init_pool() deliberately runs before init_db()'s idempotent DDL fixups need it. Get this order wrong — say, open the pool before migrations run — and you risk pooled connections racing a schema change mid-flight, exactly the failure mode run_postgres_migrations()'s placement in this function is designed to avoid.

Why route registration order is frozen

A detail easy to dismiss as bureaucratic until you understand FastAPI's route matching: it tries routes in the order they were registered and uses the first one whose path pattern matches. A literal path like /api/cves/export and a parameterized sibling like /api/cves/{cve_id} can both match a request for /api/cves/export — whichever was registered first wins. If a future change reordered router registration in main.py, /api/cves/export could silently start being swallowed by the {cve_id} handler, treating "export" as if it were a CVE ID, with no error, just wrong behavior. tests/test_router_split.py exists specifically to catch this class of regression by snapshot-testing the exact OpenAPI route list — a test that looks pedantic is actually guarding a genuinely sharp edge in how FastAPI resolves overlapping routes.

Why shutdown avoids os._exit(0)

dependencies.py's trigger_graceful_restart() (used by the admin UI's "restart" button) sends a signal that lets uvicorn's normal shutdown sequence run to completion, rather than calling os._exit(0) to terminate immediately. The reason is direct: an immediate exit skips the code after the yield in lifespan() — connection pool close, scheduler stop, in-flight background task drain (Chapter 15's task_registry.py) — none of which would run. A restart that skips cleanup isn't just untidy; it can leave a half-written scheduler job or an unflushed metrics counter, silently corrupting state that a clean restart is supposed to avoid.

The dependency-injection layer: require_user and require_admin

FastAPI's dependency injection lets a route declare "I need an authenticated user" as a function parameter, and the framework runs that function before the route handler, short-circuiting with an error response if it raises. dependencies.py is where BRIEFR's two most important dependencies live: require_user (any authenticated session) and require_admin (session and the admin role). The detail worth sitting with is that require_admin re-reads the user's role from the users table on every single call, rather than trusting the role claim already sitting inside the JWT the user presented. That's an extra database read on every admin-gated request — a real, measurable cost, paid deliberately. The payoff: if an admin gets demoted mid-session, the very next admin-gated request they make is rejected, without waiting for their 15-minute access token to expire on its own. This is a live illustration of a security tradeoff you'll see reasoned about explicitly in Chapter 11 too — trusting a signed token's claims is fast but stale; re-checking the database is slower but current, and BRIEFR chooses "current" specifically for the one role check where staleness is a real risk (a demoted or offboarded admin retaining elevated access for up to 15 minutes).

Security callout: CSP (Content-Security-Policy) headers, added by a dedicated middleware, are reasonably strict — default-src 'self', no unsafe-inline scripts. docs_url/redoc_url/openapi_url (FastAPI's auto-generated interactive API docs) are disabled entirely in production, which removes a free endpoint-enumeration tool from an unauthenticated attacker's toolkit.

Configuration and encrypted settings

Three files, three different jobs: what the process reads at boot, what an operator can change without redeploying, and how the sensitive half of that gets protected at rest.

config_schema.pysettings.pysettings_crypto.pyoperator_settings.pyADR-006

Two different kinds of configuration

It's worth separating two things that look similar but aren't: process configuration — read once from environment variables or a .env file at process start, and requiring a restart to change (settings.py's pydantic Settings singleton: database URL, JWT secret, core rate-limit rates) — versus operator configuration — writable live through the Admin UI without a restart, persisted to the database, described by an ~80-field registry (config_schema.py's CONFIG_SCHEMA) that specifies each field's type, bounds, help text, and whether changing it needs a restart to take effect.

Why config_schema.py exists as a single registry

Its own docstring states plainly what it replaces: three separately-maintained lists that used to live directly in routers/admin.py — WRITABLE_CONFIG_KEYS, INTEGER_KEYS, RESTART_REQUIRED_KEYS. Maintaining the same information as three parallel lists is a classic source of drift: add a new writable key and forget to also add it to RESTART_REQUIRED_KEYS, and an operator changes a setting that silently doesn't take effect until a restart they were never told to do. Collapsing three lists into one schema (one entry per key, describing everything about it at once) makes that class of bug structurally impossible rather than merely less likely — there's no second list to forget to update, because there is no second list.

Environment-variable precedence, and why it's load-bearing

BRIEFR resolves a config value through three layers, in a fixed order: process environment (whatever the OS/container actually set before Python started) wins over the database (app_settings table, written by Admin UI saves) wins over the .env file. This ordering is not incidental — it's what makes container deployments predictable: an operator can set DATABASE_URL as a real environment variable in their deployment manifest and know with certainty that no Admin UI click can ever override it, because real host environment always wins. settings.py implements this precedence with a small but important piece of ordering: it snapshots which keys already exist in the process environment before calling load_dotenv(), specifically so that loading .env can't accidentally overwrite a real environment variable that happened to also appear in the file.

Encrypted secrets at rest (ADR-006)

Before ADR-006, an operator-saved secret — an API token, a webhook URL with an embedded credential — sat in the app_settings table as plain text. Anyone with read access to the database (a backup file, a restored snapshot, a compromised replica) could read every configured secret directly. The fix is Fernet symmetric encryption (AES-128 in CBC mode with an HMAC for integrity) applied specifically to fields whose schema entry declares type: "secret", keyed by an optional BRIEFR_SETTINGS_KEY environment variable, SHA-256-derived into a Fernet key.

The rollout design is worth studying as a model for how to ship a breaking-adjacent security improvement without actually breaking anything: it is entirely additive. An install that never sets BRIEFR_SETTINGS_KEY keeps working exactly as before — with no key configured, secrets simply aren't persisted to the database at all (they still work via .env/process env, just never touch the DB). Once a key is configured, new saves are encrypted and stored as enc:v1:<fernet-token>; a decrypt_secret() call on an old plaintext row (no enc:v1: prefix) passes it through unchanged rather than erroring, so legacy rows keep working until the next time an operator re-saves that setting through the Admin UI, at which point it gets encrypted going forward. No forced migration, no downtime, no "upgrade and your secrets stop working" moment.

Security callout — a real gap worth knowing: settings_crypto._fernet() returns None silently when no key is configured, rather than raising. Every caller must explicitly check for that None and decide what to do — a caller that forgets the check risks silently storing a secret in plaintext instead of failing loudly. If you're auditing this code, the call sites in operator_settings.py are exactly where to verify that check actually exists everywhere it needs to.

Fails closed, on purpose, in production only: if BRIEFR_ENV=production and JWT_SECRET is unset, settings.py raises RuntimeError immediately — the process refuses to start rather than silently generating a throwaway secret that would invalidate every session on the next restart. In dev/test, by contrast, an unset secret is auto-generated with secrets.token_hex(32) and persisted back into .env so it survives restarts during local development. Same missing value, deliberately different behavior depending on environment.

Operator settings in the database

operator_settings.py is the writable admin-config path that persists keys to app_settings so values survive a .env refresh on deploy. Precedence remains process env → DB → .env. Secret-typed keys encrypt at rest when BRIEFR_SETTINGS_KEY is set (ADR-006); without it, secrets stay env-only and are not written to the DB. Admin Save still mirrors to .env for compatibility.

The database.py compatibility shim

The shortest chapter in this book, and a useful lesson in why "just delete the old file" is sometimes the wrong instinct during a refactor.

database.py

At 57 lines, database.py contains almost no logic of its own. It defines one meaningful thing — DB_PATH, the on-disk location of the SQLite dev/test database — and then star-imports and re-exports everything from the real, current data-access modules under backend/db/, plus a handful of underscore-prefixed "private" names that external callers happen to import directly and that a plain import * would otherwise silently drop.

The backstory: the original, monolithic database.py was split apart into the current backend/db/ package during an earlier refactor phase, with every function moved verbatim into its new module. That refactor left 35-plus existing call sites across the codebase still doing from database import upsert_cves (or similar) — pointing at a module that, after the split, no longer contained that function directly. Rather than hand-editing every one of those 35+ import statements across the codebase in the same PR as a structural refactor (real risk of introducing an unrelated bug in an unrelated file, for no functional gain), the team left this shim in place: database.py still exists, still answers to every old import, and simply forwards to the real implementation now living elsewhere.

The one genuinely subtle detail: DB_PATH deliberately stays a literal attribute directly on this module, rather than being re-exported from db/config.py like everything else here. The reason lives in db/connection.py, which does a lazy import database followed by database.DB_PATH specifically so that a test's monkeypatch.setattr("database.DB_PATH", ...) takes effect. monkeypatch.setattr works by reaching into a named module object and replacing an attribute on it directly — that only functions correctly if DB_PATH genuinely lives on the database module, not if it's merely re-exported through an import chain from somewhere else. Move it, and every test that overrides the database path for isolation would silently start monkeypatching a name nobody actually reads from anymore.

Why no ORM, revisited concretely

Part 0 introduced the ORM-vs-raw-SQL tradeoff in the abstract; here's what "no ORM" actually looks like in a real query module. db/app_settings.py defines its queries as paired string constants, one per database dialect, sitting side by side:

_SELECT_VALUE_SQLITE = "SELECT value FROM app_settings WHERE key = ?"
_SELECT_VALUE_PG     = "SELECT value FROM app_settings WHERE key = $1"

_UPSERT_SQLITE = """
INSERT INTO app_settings (key, value, updated_at)
VALUES (?, ?, ?)
ON CONFLICT(key) DO UPDATE SET
    value = excluded.value, ..."""

_UPSERT_PG = """
INSERT INTO app_settings (key, value, updated_at)
VALUES ($1, $2, $3)
ON CONFLICT(key) DO UPDATE SET
    value = excluded.value, ..."""

db/app_settings.py — the exact _SQLITE / _PG pairing CLAUDE.md's danger zone describes

Notice the two dialects aren't subtly different for no reason: SQLite uses positional ? placeholders, Postgres uses numbered $1/$2 placeholders — a real driver-level difference neither aiosqlite nor asyncpg will paper over for you. Every query module in db/ follows this same shape: write the SQLite version, write the Postgres version, and a small dispatch function (_is_postgres_connection(db)) picks the right one at call time. There is no automatic translation between them for new code — this is the exact meaning of the project's own rule that a new query has to be written twice, deliberately, by a human who understands both dialects' behavior for that specific query.

What pg_adapt.py actually is (and, importantly, isn't)

It would be easy to assume pg_adapt.py is a general SQLite-to-Postgres translation layer that saves you from writing dialect-specific SQL — that assumption would be wrong, and CLAUDE.md is explicit about it: db/dialect.py, an earlier general-purpose translator, was deleted entirely in a refactor referred to internally as "Post-B" (2026-07). Checking the current repository confirms that file no longer exists. What remains, pg_adapt.py, is scoped much more narrowly: it's internal machinery inside PostgresConnection that exists only to translate legacy SQLite-flavored SQL still being emitted by code outside the db/ package — older router and auth-layer queries written with SQLite idioms (? placeholders, datetime('now')) before the Postgres-native convention was established. Its regex-based _postgres_translate_sql() rewrites those specific patterns (datetime()/date()/julianday() calls, INSERT OR REPLACE/INSERT OR IGNORE into ON CONFLICT equivalents, placeholder renumbering) at the connection boundary, as a compatibility bridge for legacy call sites — not as a general-purpose feature new code is meant to rely on. Writing a brand-new query and hoping pg_adapt.py will make your SQLite SQL "just work" on Postgres is precisely the mistake this file's own docstring warns against.

The connection abstraction: one protocol, two real implementations

db/types.py defines a shared DbConnection protocol — an interface both backends implement identically from the caller's point of view, so query-module code doesn't need an if is_postgres() branch scattered through every function; the branch happens once, inside get_connection(). SqliteConnection wraps aiosqlite, opened in WAL (write-ahead logging) mode with a 30-second busy timeout and foreign keys enforced — WAL mode specifically because it lets readers and a single writer proceed concurrently rather than SQLite's default fully-serialized locking, which matters for a dev/test environment where the scheduler and an interactive request might touch the database at nearly the same moment. PostgresConnection wraps a pooled asyncpg connection, opening a transaction lazily on the first execute() call and leaving commit/rollback entirely to the caller — the connection layer doesn't guess when a logical unit of work ends, the code using it says so explicitly.

Connection pooling, made concrete

Part 0 defined a connection pool abstractly; here's the concrete shape. init_pool() opens a process-global asyncpg pool sized between 1 and settings.database_pool_size connections. get_connection() acquires one from the pool with a timeout — if every pooled connection is already checked out and the timeout expires, it raises a specific PoolExhaustedError, which main.py's exception handler turns into an HTTP 503 (Service Unavailable) rather than a generic crash. This is a meaningfully better failure mode than either silently queuing forever (a request that never returns) or a raw unhandled exception (a 500 with no useful signal) — the client gets a clear, actionable "the server is overloaded, retry" response instead of either extreme. SQLite, by contrast, has no pool at all: each call opens a fresh aiosqlite connection, which is fine for the low-concurrency dev/test use case it's meant for, but is a real, deliberate limitation you should be able to name if asked "does SQLite scale here" — it doesn't, and it isn't meant to.

Why the schema itself is still one database, not split (ADR-001)

ADR-001 documents a genuine tension in BRIEFR's roadmap: the project has an open-core plan to publish a monthly public CVE/correlation snapshot, but a raw pg_dump of the live production database today would leak operator data alongside it — user accounts, session tokens, IOC watchlist entries, webhook destination URLs. The obvious-looking fix is a physical schema split (an intel schema containing only exportable data, an app schema containing everything operator-specific) so a dump of one schema is safe by construction. ADR-001 explicitly considers and defers that split — it would double the migration and test surface immediately, in exchange for a benefit (safe automated exports) the project doesn't need yet, since the public snapshot feature hasn't shipped. Instead, the boundary between "safe to export" and "not safe to export" is enforced today by an allowlist export script (scripts/export_intel_snapshot.py) that only touches tables it's been told are safe, with the physical split explicitly left as a decision to revisit in a later ADR once the open-core feature actually ships. This is worth noticing as a pattern in its own right: sometimes the architecturally "correct" fix is deliberately deferred because the feature that would justify its cost doesn't exist yet, and a narrower, additive mitigation covers the present risk well enough.

Error normalization across two very different drivers

SQLite and Postgres drivers raise entirely different exception hierarchies for the same logical failure (a locked database, a constraint violation). db/errors.py catches both sqlite3.* and asyncpg.* exceptions at the connection boundary and re-raises them as BRIEFR's own dialect-neutral types — DatabaseError, DatabaseLockedError — so that code outside the db/ package (routers, business logic) can catch one exception type regardless of which database is actually running underneath. This is the payoff of the whole dual-backend design done right: the abstraction boundary is drawn at exactly the right place — dialect differences are absorbed inside db/, and everything outside it can pretend there's only one database.

The trap this whole architecture exists to prevent, stated plainly: the default test suite runs against SQLite. A query can pass every test in that suite and still break in production, because SQLite silently tolerates things Postgres rejects outright (type coercion is far looser; CAST(x AS REAL) on a non-numeric string is forgiving in SQLite and an error in Postgres — you'll meet this exact example again in Chapter 22's morning-brief chapter). Any change to the data layer needs to be run against both backends before you can trust it — the project's own tooling for that is a disposable Postgres container on port 5433, specifically to avoid colliding with a developer's own local Postgres on 5432.

Alembic migrations — forward-only, Postgres-only

Why the two backends have entirely different migration stories, and why that asymmetry is intentional rather than an oversight.

alembic/env.pyalembic/versions/*.py — 33 files

Alembic is a schema-migration tool: each change to the database schema is captured as a small, ordered Python file with an upgrade() function (apply the change) and a downgrade() function (undo it), chained together by a revision/down_revision pair so the tool always knows the exact linear order migrations must apply in. BRIEFR has 33 of these, from 001_initial_schema.py through 033_search_api_tokens.py, and they run automatically — not just from a developer's terminal, but from db/init.py's run_postgres_migrations(), called during every single backend startup against a live Postgres DATABASE_URL (Chapter 6). A quick optimization keeps this from being wasteful: before running anything, Alembic compares the database's current alembic_version marker against the migration scripts' head revision, and skips the upgrade step entirely if they already match — so a normal restart with no pending migrations does one cheap comparison, not 33 no-op replays.

Here's the asymmetry that matters: SQLite never touches Alembic at all. The zero-config dev/test database gets its schema from a completely separate mechanism — a large inline executescript() block in db/init.py's init_db(), plus a long, hand-maintained list of best-effort ALTER TABLE statements wrapped in try/except, replayed in full on every process start. This is why CLAUDE.md's danger-zone warning about migrations matters so much in practice: the SQLite schema and the Postgres schema are not derived from one shared source of truth — they are two independently hand-maintained descriptions of "what the schema should look like," kept in sync by developer discipline, not by tooling. A developer who adds a Postgres migration and forgets the equivalent SQLite DDL change (or vice versa) creates a real, silent divergence between what the test suite validates and what production actually runs on.

Why forward-only, and why it's not just a style preference

"Never edit an applied migration, always add a new one" sounds like a stylistic convention until you trace through what editing one would actually do. Alembic's alembic_version table doesn't store a hash or diff of the schema — it stores the ID of the last migration that was run. If migration 017 has already been applied in production and you go back and edit its upgrade() function, production's schema doesn't change (that code already ran, once, in the past) but the script directory now describes a different history than what actually happened. The next deploy sees "I'm already past revision 017" and does nothing — silently leaving your edited change entirely unapplied in production, with no error, because from Alembic's point of view there's nothing new to do. The only correct way to change something migration 017 already did is a brand-new migration 034 that alters it further — history is append-only, exactly like a git log you're not allowed to rebase once it's pushed.

Authentication — sessions, tokens, and passwords

The full login system, replacing a legacy shared admin-key header — and the reasoning behind every one of its individually small, deliberate security choices.

auth/tokens.pyauth/passwords.pyauth/repo.pyauth/usernames.pyauth_middleware.py

Two tokens, not one, and why that split exists

BRIEFR issues two different credentials at login, each optimized for a different property. A short-lived access token — a JWT, self-contained and stateless, checked by decoding and verifying its signature, no database lookup required — is fast to verify on every request but, once issued, cannot be individually revoked before it naturally expires. An opaque refresh token — a random string with no embedded meaning — is checked against a database table (sessions) on use, which makes it slower to verify but fully revocable at any moment, since revocation just means deleting or marking that one database row. The two are complementary precisely because they trade the same property in opposite directions: the access token optimizes for speed at the cost of instant revocability; the refresh token optimizes for revocability at the cost of a database round-trip. Using one alone would force a single tradeoff onto the entire system; using both lets each request pick the cheaper one (the access token) for routine reads, while keeping a slower-but-revocable mechanism (the refresh token) in reserve for the moment revocation actually matters — a stolen session, an offboarded user, a suspicious login.

auth/tokens.py, in full for the relevant functions — notice the refresh token is never stored raw, only its SHA-256 hash

That last function is a small but important detail: the raw refresh token is handed to the browser once, at login, and never persisted anywhere on the server — only hash_refresh_token()'s output goes into the sessions table. If the database ever leaked (a backup file exposed, a read replica compromised), an attacker with the hash table alone cannot reconstruct the original tokens and therefore cannot replay anyone's session — the same principle as never storing a plaintext password, applied to a session credential instead.

Password hashing, and the timing-attack detail most implementations miss

BRIEFR hashes passwords with bcrypt directly, at 12 rounds — a deliberate choice over passlib, a popular wrapper library, because the code's own comment notes passlib is unmaintained and has broken compatibility with bcrypt versions 4.1 and above. Depending on an unmaintained abstraction layer over a well-maintained primitive is a real risk in security-sensitive code; calling bcrypt directly removes that dependency entirely.

DUMMY_HASH = bcrypt.hashpw(secrets.token_bytes(32), bcrypt.gensalt(rounds=12)).decode("utf-8")

def hash_password(plain: str) -> str:
    return bcrypt.hashpw(plain.encode("utf-8"), bcrypt.gensalt(rounds=12)).decode("utf-8")

def verify_password(plain: str, hashed: str) -> bool:
    try:
        return bcrypt.checkpw(plain.encode("utf-8"), hashed.encode("utf-8"))
    except ValueError:
        return False

auth/passwords.py, in full — DUMMY_HASH is generated once at import time, from random bytes

The subtle piece worth studying is DUMMY_HASH. Without it, a naive login handler might do "look up the username; if not found, return an error immediately; if found, call verify_password." That branch has a measurable timing difference — a nonexistent username returns fast (no bcrypt call at all), while an existing username with a wrong password returns slower (a full, deliberately-slow bcrypt comparison runs). An attacker who can measure response times precisely enough can use that difference alone to enumerate which usernames exist in the system, without ever guessing a single correct password. DUMMY_HASH closes this: when a username lookup fails, the login handler still runs verify_password(plain, DUMMY_HASH) against this fixed, meaningless hash, so a nonexistent username costs the same bcrypt-comparison time as a wrong password on a real one. The two cases become indistinguishable by timing alone.

Session rotation and reuse detection

When a refresh token is used, auth/repo.py's rotate_session doesn't simply issue a new one and move on — it explicitly revokes the old session row rather than deleting it outright. That distinction matters: because the hash of the old, now-revoked token is still sitting in the table (marked revoked, not gone), a second attempted use of that same old token — which shouldn't happen in normal operation, since a legitimate client only uses a refresh token once before getting a new one — is detectable as reuse rather than silently accepted or silently rejected with no signal. In the concrete attack scenario this defends against: an attacker steals a refresh token and uses it once to mint their own session. When the legitimate user's client later tries to use that same (now-already-rotated) token, the system can recognize "this exact token was already rotated once" and treat it as a signal that the token was compromised, rather than as an ordinary, unremarkable refresh.

Username validation as a security control, not just data hygiene

auth/usernames.py lowercases and validates usernames against a strict pattern — 3 to 32 characters, alphanumeric plus underscore/hyphen, must start and end with an alphanumeric character. The code's own comment frames this as reducing "homograph confusion" — the risk that two visually similar usernames (using look-alike Unicode characters, or subtly different capitalization) could be mistaken for each other in an audit log or a security review, which matters in exactly the way it wouldn't for a consumer app: a security operator scanning an audit trail for a specific account needs to trust that what they're reading is what's actually there.

The scoped bearer-token path — a second, narrower credential

Separate from the interactive-session cookie flow entirely, auth_middleware.py recognizes a second kind of credential: an Authorization: Bearer briefr_search_... token, intended for machine or service access rather than a human browser session. This token is deliberately more restricted than a full login session in two ways at once — it's checked against a small, explicit allowlist of read-only paths (semantic search, CVE detail/related/drawer GET requests only — enforced by a path regex, not by role) rather than the general permission system, and it has its own separate rate-limit bucket. The design principle here is the security concept of least privilege applied to machine credentials specifically: a service that only needs to query search results gets a credential that can only query search results, rather than reusing the same broad session mechanism a human analyst uses.

The one honest tradeoff to be able to name in an interview: access tokens are stateless JWTs, which means an individual access token cannot be revoked before its 15-minute expiry, even if the corresponding session is revoked — only the refresh token is revocable via the sessions table. After a suspected token leak, an operator who revokes the session has still left up to 15 minutes of residual access on any already-issued access token. This is a deliberate, documented tradeoff (short TTL bounds the exposure window tightly), not an oversight — but it's exactly the kind of detail worth being able to state precisely rather than hand-wave past.

Rate limiting — inbound, and the residual risk that's accepted rather than solved

Token buckets protecting BRIEFR from abuse, with a client-identification scheme more careful than it might first appear.

rate_limit.pyrate_limit_store.py

Chapter 16 covers the outbound half of rate limiting — pacing BRIEFR's own calls to NVD, GitHub, and OTX. This chapter covers the inbound half: protecting BRIEFR's own endpoints (login, IOC lookup, refresh, admin routes, the wallboard) from being hammered by a single client, using the token-bucket algorithm introduced in Part 0.

Why buckets are process-local, and the constraint that makes that safe

The buckets live entirely in the process's own memory — not a shared cache, not a database table, by default. A code comment states directly why that's safe here rather than a latent bug: the deployment runs uvicorn with --workers 1, meaning there is exactly one process handling requests, so "the rate limit" and "this process's in-memory bucket" are the same thing. The comment goes further and flags the exact way this assumption could later break silently: if a future change added more uvicorn workers for throughput, each worker would get its own independent copy of every bucket, and the effective rate limit would be multiplied by the worker count without any code change actually intending that — five workers would mean a "10 requests per minute" limit becomes 50 per minute in practice, invisibly. rate_limit_store.py is the prepared escape hatch for exactly that future: setting BRIEFR_RATE_LIMIT_STORE=db moves bucket state into the sync_state table (SQLite or Postgres, whichever is active), shared across however many workers or replicas are running — off by default specifically to keep the zero-config dev/test path as simple as possible.

def client_key(request: Request) -> str:
    peer = request.client.host if request.client else ""
    if peer not in _TRUSTED_PROXY_PEERS:
        # Direct connection (LAN dev, or someone bypassing nginx): the
        # socket address is the only trustworthy identity — forwarded
        # headers here would be attacker-controlled bucket keys.
        return peer or "unknown"

    # Set by the Cloudflare edge and overwritten there, so it cannot be
    # forged by clients coming through the tunnel.
    cf_ip = request.headers.get("cf-connecting-ip", "").strip()
    if cf_ip:
        return cf_ip

    # nginx appends $remote_addr as the rightmost X-Forwarded-For hop; the
    # rightmost non-loopback hop is therefore proxy-attested, while the
    # leftmost hops are whatever the client sent.
    forwarded = request.headers.get("x-forwarded-for", "")
    hops = [hop.strip() for hop in forwarded.split(",") if hop.strip()]
    for hop in reversed(hops):
        if hop not in _TRUSTED_PROXY_PEERS:
            return hop

rate_limit.py's client_key(), real code — the exact trust boundary is worth reading twice

Why forwarded headers are only trusted conditionally

X-Forwarded-For and similar headers exist so a reverse proxy can tell the backend "the real client IP was X, even though I'm the one actually connecting to you" — necessary because otherwise every request would appear to come from the proxy's own address. The catch is that these are just ordinary HTTP headers, and any client can set them to anything at all when talking directly to the backend. client_key()'s logic resolves this correctly: it only trusts forwarded headers at all when the direct socket peer — the actual TCP connection, which can't be spoofed the way a header can — is a known, trusted reverse proxy (Cloudflare's edge or the local nginx). A request arriving directly, bypassing the trusted proxy entirely, gets keyed by its raw socket address only, exactly because trusting a header from an untrusted direct connection would let an attacker mint an unlimited number of fresh rate-limit buckets simply by sending a different fake X-Forwarded-For value on every request — defeating the entire point of rate limiting.

The code comment is honest about a residual gap rather than pretending the mitigation is complete: a host on the same local network as the proxy, connecting to nginx directly rather than through Cloudflare, could still present a forged header that nginx would then legitimately append to. This is accepted explicitly for BRIEFR's current private-beta threat model — a security decision made visible in a comment rather than silently absorbed as an unstated assumption.

Why login is rate-limited by username, not IP

Every other bucket in this file is keyed by client IP, but login_username_bucket is keyed by the submitted username instead. This targets a specific attack pattern IP-based limiting can't catch: credential stuffing, where an attacker tries the same stolen username against many different passwords, spread across a large pool of source IPs (a botnet, a residential proxy service) specifically to stay under any single IP's rate limit. Keying by username instead catches this directly — no matter how many different IPs an attacker rotates through, they're all hammering the same account, and that account's bucket empties regardless of which address each attempt came from.

Logging and redaction — two systems, and one real gap between them

Structured JSON logs, an admin log viewer, and a documented boundary on what redaction actually covers — worth understanding precisely, not just trusting.

structured_logging.pyredact.py

It's easy to assume a codebase has "one logging system with redaction built in," but BRIEFR actually has two separate mechanisms solving two different problems, and conflating them is the most common way to misjudge how well-protected a given piece of data actually is.

structured_logging.py: the logging pipeline itself

Every log line becomes one JSON object emitted to stderr — deliberately structured rather than free-text, so log aggregation tools (or a human grepping the output) can filter by field rather than parsing prose. A contextvar-based mechanism propagates a request_id/job_id/run_id through the whole call chain of a single request or job, so every log line produced while handling one request can be correlated back to it — genuinely useful when a request touches five subsystems and something in the middle fails. A fixed-size, in-process ring buffer holds the last 500 log entries specifically to back the Admin UI's live log viewer, without needing a separate log-shipping pipeline for that feature.

def _should_redact_field(key: str) -> bool:
    key_upper = key.upper()
    return key_upper in _REDACT_EXACT or any(
        key_upper.endswith(suffix) for suffix in _REDACT_SUFFIXES
    )

structured_logging.py — this function only ever sees the keys of extra={...} kwargs, never a log message string

The gap, stated exactly, not hand-waved

CLAUDE.md states this directly, and reading the actual function confirms it precisely: _should_redact_field() only ever inspects the keys of whatever dictionary is passed as extra={...} to a logging call, masking the value when the key's name ends in _KEY, _TOKEN, _SECRET, or _PASSWORD (or matches a short exact-match list). It never touches the log message string itself — the human-readable text passed as the first argument to logger.info(...). This is a real, deliberate design boundary, not an accidental gap someone forgot to close: logger.info(f"NVD sync failed with key {api_key}") interpolates the secret directly into the message text and sails straight past redaction untouched, while logger.info("NVD sync failed", extra={"api_key": api_key}) passes the exact same information through the one code path that actually gets checked. The entire safety of this system rests on every call site in the codebase following that convention correctly — there's no code-level enforcement stopping a developer from writing the first version.

redact.py: a completely different surface

Where structured_logging.py is about what gets written to log output, redact.py is about what gets returned from the Admin config API and stored in the audit log — a different data path serving a different purpose (an operator viewing their own saved config; an auditor reviewing what changed and when).

def mask_secret_value(value: str) -> str:
    text = (value or "").strip()
    if not text:
        return "not configured"
    if len(text) <= 8:
        return "***"
    return f"{text[:4]}…{text[-4:]}"

redact.py — shows first/last 4 characters of a longer secret, enough for an operator to recognize which key is configured without exposing it

Beyond this exact-field masking, redact.py also runs a heuristic — _looks_like_secret_value — over config values that don't already have a schema-declared type: "secret", matching known API-key prefix formats (gsk_ for Groq, sk- and sk-or-v1- for OpenAI-family and OpenRouter keys, vulncheck_, and similar) or simply flagging any long, token-shaped string with no spaces or slashes. This is a genuinely best-effort net, not a guarantee: it will miss a short secret, an unrecognized provider's key format, or a secret embedded mid-sentence inside a longer free-text value — say, a webhook delivery error message that happens to quote back an API key as part of the upstream error text. A separate, deliberately coarser function, mask_webhook_delivery_error, exists specifically for that surface: it redacts any full URL and any string containing the words "token," "password," or "secret" (case-insensitive), or anything longer than 80 characters — trading precision for a wider net on a surface where the shape of what needs hiding is less predictable.

The practical rule that falls out of both systems together: if you're extending BRIEFR and handling anything sensitive, secrets belong in extra= keyword arguments when logging (never interpolated into the message string), and in schema-typed "secret" config fields when they flow through the Admin config surface (never as free text a heuristic has to guess about). Feed sources — 29 files, four distinct shapes of the same problem

Every feed answers the same question — "how do I sync only what changed" — differently, and the differences tell you something real about each upstream's own design.

feeds/*.pyfeeds/nvd.pyfeeds/kev.pyfeeds/epss.pyfeeds/cvelistv5.py

The feeds/ directory has four rough tiers: primary CVE sources (NVD, CISA KEV, FIRST EPSS, cvelistV5, vulnrichment, and cpe_catalog.py — NVD's full CPE 2.3 dictionary, checkpointed across runs since the corpus is large and never touched on the request path), exploit/PoC availability trackers (ExploitDB, Metasploit modules, Nuclei templates, PoC-GitHub), threat-intel mirrors (AlienVault OTX, ThreatFox, OSV, VulnCheck's own KEV mirror), and context feeds (MITRE ATT&CK, ATLAS, news/case studies). Rather than walk all 29 files, this chapter goes deep on four that each teach a genuinely different lesson about watermark design — the pattern from Part 0 that recurs, differently shaped, in every single one of them.

NVD — pagination and hard rate limits force the shape

NVD's REST API paginates at 2000 results per page and enforces a strict rate limit — 5 requests per 30 seconds without an API key, 50 with one — that a naive client would blow through in seconds on any non-trivial sync. fetch_nvd_cve_updates(watermark) branches on whether a watermark already exists: with one, it queries lastModStartDate/lastModEndDate starting from the watermark minus a 15-minute overlap window (clamped to a 120-day maximum span NVD's API itself enforces); with none — a fresh install's first-ever sync — it instead bootstraps from a pubStartDate window covering the last 14 days, since there's no watermark yet to resume from. Every page fetch passes through the shared outbound queue (Chapter 16) before the actual HTTP call, and a 429 response inside the page-fetch loop retries indefinitely rather than raising — consistent with the project's stated principle that ingestion never drops a request just because a rate limit was hit.

The 15-minute overlap on every resumed sync is a small, deliberate over-fetch: it guarantees that a CVE modified in the last few seconds before the previous sync's cutoff timestamp — which might not have been fully committed to NVD's own backend at the exact moment it was queried — gets picked up again rather than silently missed by a hair. The cost is trivial (re-fetching and re-upserting a handful of already-known CVEs, which the idempotent upsert in Chapter 9's data layer makes a safe no-op); the benefit is closing a subtle race condition at the boundary of "what does 'modified since X' even mean when X is a moving target."

KEV — no watermark at all, and why that's correct here

CISA's KEV catalog is a small, static JSON file with no delta or "since" API of any kind — you get the whole current catalog or nothing. Given that, feeds/kev.py makes the only reasonable choice: it re-fetches and re-applies the entire catalog on every scheduled run, with no watermark concept whatsoever. Idempotency here doesn't come from a watermark at all — it comes entirely from the upsert being keyed by CVE ID downstream, so re-applying an unchanged catalog entry is simply a no-op write. The one defensive check worth noting: if CISA's endpoint ever returned a malformed or genuinely empty response, blindly applying it would look like "every KEV flag in the database should be cleared" — catastrophically wrong. A guard (FeedFetchError("KEV catalog parsed empty")) raises instead of silently applying an empty catalog, protecting against exactly that failure mode.

EPSS — a bulk file beats one API call per CVE

FIRST.org's EPSS scores update daily for the entire CVE corpus — hundreds of thousands of rows. Calling their per-CVE API once for every CVE BRIEFR tracks would be enormously wasteful; instead, feeds/epss.py prefers downloading the daily bulk CSV (gzip-compressed, published once a day) and filtering it in memory to just the CVE IDs BRIEFR actually needs, falling back to the batched per-CVE API (100 CVEs per request) only for whatever the bulk file doesn't cover — typically CVEs published so recently they postdate the last daily snapshot. A neat optimization on top of the bulk-download path: file_identity.py computes and stores a SHA-256 hash of yesterday's downloaded file; if today's download hashes identically (meaning FIRST.org hasn't actually re-published new data since the last check, which does happen), the entire decompress-and-parse cycle is skipped outright rather than redundantly reprocessing byte-identical data.

cvelistV5 — a git SHA as a watermark, and why that's the cleverest one

MITRE's cvelistV5 GitHub repository often has a CVE's initial JSON record hours before NVD has gotten around to analyzing and publishing it — genuinely earlier signal, worth syncing on its own timeline. The watermark design here is the most interesting of the four: instead of a timestamp, BRIEFR stores the repository's git commit SHA it last synced up to, and uses GitHub's compare API (/compare/{base_sha}...{head_sha}) to ask, in one cheap call, exactly which files changed between that SHA and the current HEAD.

async def fetch_cvelistv5_delta(watermark_sha: str | None) -> tuple[...]:

        return [], [], watermark_sha, False   # transient failure — don't advance

    if watermark_sha and watermark_sha == head_sha:
        return [], [], head_sha, True       # nothing changed — a real, successful no-op

    base_sha = watermark_sha or await _fetch_bootstrap_base_sha(branch, ...)

feeds/cvelistv5.py, abridged — the fourth return value, watermark_advanced, is the whole idempotency story

Why a git SHA instead of a timestamp: GitHub's compare API is exact — it returns precisely the files that changed between two commits, with no ambiguity about time zones, clock skew between BRIEFR's server and GitHub's, or what "modified since X" means when X is a wall-clock time. A SHA-based watermark is also immune to a subtle class of bug that plagues timestamp watermarks: if BRIEFR's own clock drifts even slightly, a timestamp watermark could silently skip or re-fetch records; a git SHA has no such ambiguity, because "has this exact commit already been synced" is a yes/no question with no room for interpretation.

The function's explicit watermark_advanced: bool return value is the idempotency guarantee made visible in the type signature itself, not left implicit. The caller is only allowed to persist a new watermark SHA when this flag is true — meaning the fetch genuinely completed successfully, even if that success was "nothing changed." If the fetch fails partway through (a network error, a GitHub outage), the function returns False, and the caller must leave the old watermark exactly where it was. A crash or failure here doesn't corrupt anything — it just means the next scheduled run naturally re-attempts the exact same range of history, because nothing was ever marked as done.

A known, accepted gap: the compare API's changed-file list is capped at roughly 300 entries by GitHub itself. If more than 300 files changed since the last sync (a large batch update upstream, or BRIEFR having been offline a long time), the sync logs a truncation warning and processes what it received — some changes could be silently missed until a subsequent run's compare call happens to catch them. This is a real, acknowledged limitation, not a closed loop, and worth being able to name precisely rather than assuming the sync is always complete.

The outbound queue and circuit breakers — never dropping a request on purpose

One shared choke point every feed passes through before it ever touches the network, built around a single stated principle: wait, don't fail.

Every outbound call any feed module makes — to NVD, GitHub, OTX, CISA, FIRST.org, any of it — is routed through resilient_client.py's resilient_get/resilient_request, never a raw httpx call made directly by a feed module. This centralization is what makes it possible to reason about outbound reliability in one place instead of 29 separate, inconsistent implementations.

CIRCUIT_FAILURE_THRESHOLD = 3
CIRCUIT_COOLDOWN_SECONDS = 60.0

def _record_failure(source: str, error: str, *, cooldown_seconds=None) -> None:
    state = _state(source)
    state["consecutive_failures"] += 1
    if state["consecutive_failures"] >= CIRCUIT_FAILURE_THRESHOLD:
        cooldown = cooldown_seconds if cooldown_seconds is not None else CIRCUIT_COOLDOWN_SECONDS
        state["circuit_open_until"] = time.time() + cooldown

def is_circuit_open(source: str) -> bool:
    open_until = _circuit_open_until(source)
    return bool(open_until and time.time() < open_until)

resilient_client.py, real code — three consecutive failures, sixty seconds of silence, then one more try

The circuit-breaker state machine, made concrete

Part 0 described a circuit breaker in the abstract; here it is exactly. Each source (NVD, OTX, GitHub, and so on) has its own independent health state: a count of consecutive failures, and a timestamp marking when the circuit reopens. After 3 consecutive failures, the circuit "opens" for 60 seconds — during that window, is_circuit_open() returns true immediately and calls to that source fail fast without even attempting the network request, protecting BRIEFR from wasting time and connections hammering a service that's already down. A single success resets the failure count to zero and clears the open-until timestamp entirely — the breaker doesn't require a gradual healing period, one clean response is enough to trust the source again. This asymmetry (three strikes to open, one success to close) is a deliberate choice: opening the circuit is a costly false-negative to get wrong too eagerly (you'd stop legitimate traffic to a source that was only briefly slow), so it requires a real pattern of failure; closing it back up is cheap to get wrong (worst case, one more failed request before it reopens), so a single success is enough evidence.

Never dropping a request, and what that actually costs

The module's own design principle, stated directly: a 429 (rate limited) response should make the caller wait and retry, not fail the entire sync outright. This is why NVD's page-fetching loop (Chapter 14) retries on 429 indefinitely rather than raising after some fixed number of attempts — a design that trades "the sync might take noticeably longer than expected on a bad day" for "the sync never simply gives up partway through and leaves data half-updated." api_queue.py implements the pacing half of this: a registry tracking, per source, how many requests are currently in flight and when the next one is allowed to start, so a caller doesn't just retry blindly but genuinely waits until pacing constraints are satisfied — visible live in the admin UI as requests move through queued → waiting → active states, rather than being an invisible internal detail.

source_rate_limits.py adds one more layer of care: several distinct BRIEFR feeds — PoC-GitHub, cvelistV5, Metasploit-module sync — all ultimately hit GitHub's API under the hood, and GitHub's rate limit is per account, not per feed. If each feed paced itself independently, thinking it alone was respecting GitHub's limit, the three of them running concurrently would collectively blow straight through it. resolve_pacing_key aliases all three onto one shared pacing bucket keyed simply as github, so the constraint that actually exists (one shared quota) is modeled as one shared bucket, not three independent ones that happen to sum past the real limit.

A specific, non-obvious detail: GitHub's rate-limit headers (x-ratelimit-remaining, x-ratelimit-reset) work differently from the generic Retry-After header most APIs use. Retry-After is a relative delay ("wait 30 seconds"); GitHub's x-ratelimit-reset is an absolute Unix epoch timestamp marking when its rolling window resets. BRIEFR's pause-duration calculation branches on which kind of header a given source actually sends — computing reset_at - time.time() for GitHub specifically, rather than naively parsing it as if it were a relative delay, which would produce a wildly wrong (usually enormous) wait time.

Queue operations and metering

api_queue_operations.py and api_metering.py sit beside the in-memory api_queue.py pacing layer: operations helpers for queue introspection/control paths, and metering for usage accounting — neither replaces the token-bucket / circuit-breaker story in this chapter; they extend the operational surface around it.

Why a fixed formula, and why fixed doesn't mean simplistic

Each component contributes a 0–1 sub-score, gets multiplied by its weight, and the six weighted contributions sum to a final 0–100 Risk Score. What makes this more than a toy weighted average is that every component ships a human-readable sentence explaining exactly why it scored what it did — component_sentences renders something like "Asset match: confirmed exposure on your declared nginx stack" alongside the raw number. This isn't a cosmetic nicety; it's a hard product requirement that traces directly to a broader design principle stated in this project's own UI rules: every status word, pill, or score needs a discoverable explanation. A learned model (a gradient-boosted tree, a neural net trained on historical exploitation data) could plausibly outperform a fixed formula on raw predictive accuracy, but it can't give that same per-component, audit-ready "here's exactly why" explanation without a whole separate layer of explainability tooling bolted on afterward — and even then, that tooling approximates the model's reasoning rather than stating it exactly. A fixed formula's explanation is its computation; there's no approximation gap between what happened and what gets shown.

There's a second, quieter benefit: a fixed formula is trivially reproducible and regression-testable. Feed the same CVE and the same asset profile into calculate_risk_score twice, in two different environments, a year apart, and you get the exact same number — useful for an intelligence product where an analyst might reasonably ask "why did this score change between yesterday and today," and the honest answer needs to be a specific, traceable component delta, not "the model's internal weights shifted slightly during retraining."

Why KEV is weighted so heavily, and why CVSS is weighted so little

It's worth sitting with the relative weights rather than skimming past them. KEV membership — confirmed, real-world exploitation, per Part 0's definition — is weighted 0.25, the second-highest of all six components, just behind asset relevance itself. CVSS, by contrast, gets only 0.10, the lowest tier alongside the exploit-availability component. This ordering encodes a real judgment about signal quality: CVSS describes how bad a vulnerability could be under a worst-case exploitation scenario, but says nothing about whether anyone is actually doing that in practice — and in practice, most CVEs with a high CVSS score are never exploited at all, making CVSS a weak discriminator between "should this be your top priority today" and "should this be priority #400." KEV, meanwhile, is about as strong a signal as exists in this domain: CISA doesn't add a CVE to that catalog speculatively, only after confirming real-world exploitation. Weighting confirmed reality nearly three times higher than theoretical worst-case severity is the formula's single clearest statement of what it actually believes matters.

The newer split system — Threat Score, Environment tier, Operational Priority (ADR-002)

A real flaw emerges once you actually use the blended Risk Score in practice: if an analyst hasn't loaded an asset profile yet — or a CVE genuinely doesn't match anything in their stack — the 0.35-weighted asset component contributes close to zero, which drags the entire blended score down. A CVE that's critically dangerous in the abstract but irrelevant to this specific environment ends up looking indistinguishable from a CVE that's just not very dangerous at all — both show up as "low score," for two completely different reasons an analyst has no way to tell apart from the number alone. ADR-002's fix is to stop blending those two questions into one number and answer them separately instead.

A Threat Score renormalizes the five non-asset weights (dividing by 0.65, since removing the 0.35 asset weight means the rest no longer sum to 1.0) into a purely asset-independent "how dangerous is this, full stop" score — and applies a hard floor: any CVE on the KEV list scores at least 80 on this scale, regardless of what the additive formula alone would produce, because confirmed real-world exploitation is treated as decisive rather than merely a strong input among several. Separately, an Environment Relevance tier — a category, not a number, one of CONFIRMED / LIKELY / POSSIBLE / WEAK / UNKNOWN / NO_MATCH — captures how strongly this CVE matches the declared stack, and is deliberately never blended back into the Threat Score. Finally, an Operational Priority band (P1 through P4) is derived from a fixed lookup table crossing the two:

PRIORITY_TABLE = {

scoring/priority.py, the actual lookup table — read it as a decision matrix, not a formula

Notice what this table actually encodes, row by row: a CRITICAL-threat CVE with UNKNOWN environment relevance (a stack that hasn't been fully profiled yet) still lands at P1 — the system deliberately errs toward over-alerting rather than under-alerting when it genuinely doesn't know whether something applies to you, rather than silently defaulting an unknown match to "safe to ignore." Compare that to a LOW-threat CVE with NO_MATCH environment relevance, which lands at P4 regardless — a case where both dimensions agree there's nothing here worth an analyst's attention. One further mechanism sits on top of the table: corr_escalation, an optional flag that can bump a P2 or P3 band up by exactly one level (never P1, never a two-level jump) when Chapter 20's correlation engine independently finds strong evidence of an active, real-world campaign involving this CVE — a second, independent signal allowed to override the base table by a bounded, single step, not overwrite it outright.

Asset and CPE matching — the mechanical layer under the 0.35 weight

Deterministic version arithmetic where the data is structured, careful fuzzy fallback where it isn't.

matching/cpe.pyscoring/asset_match.py

Every risk score's heaviest-weighted component depends on answering one deceptively simple question: does this CVE actually affect something the analyst runs? NVD attaches structured CPE version ranges to most CVEs — machine-readable statements like "affects Apache HTTP Server 2.4.0 through 2.4.53 inclusive" — but an analyst's own declared asset stack is free text they typed themselves ("nginx", "Apache 2.4", "our web servers"), and reconciling exact structured data against messy human-entered text is the entire problem this module solves.

The design deliberately keeps two concerns separate rather than reaching for one fuzzy-matching library to handle everything at once: exact version arithmetic (does 2.4.51, say, actually fall within a range with an inclusive start and exclusive end?) is handled by version_in_range(), implementing NVD's four boundary fields (version_start_including, version_start_excluding, version_end_including, version_end_excluding) as straightforward inclusive/exclusive comparisons — with a small but necessary wrinkle: version strings like "1.2.10" need to sort after "1.2.9," not before it alphabetically, so comparison logic treats digit-only segments numerically rather than as plain string comparison. Separately, fuzzy product-name matching handles the messy human-text side, via normalized substring and token-containment checks. Keeping these two concerns apart, in plain auditable Python rather than a general fuzzy-matching library, is a deliberate choice consistent with the whole scoring stack's "explainable over powerful" posture (Chapter 18) — you can point at exactly which comparison produced which result, for any CVE, at any time.

resolve_asset_component() — the actual bridge into the Risk Score — tries the structured CPE match first, and only falls back to a nine-tier fuzzy graduation (exact CPE match, then CPE product match without version, then plain product-name match, then vendor-only match, then OS match, then AI-system match, then a description-mention match, descending in confidence) when the structured match returns exactly zero — meaning no CPE data matched at all, not merely a weak match. That distinction matters: a genuine structured "product matches, but no version specified" result already carries real signal (worth 55 out of 100 in the scoring scale), and letting a weaker fuzzy text match override that legitimate partial structured signal would actually throw away good information rather than supplement missing information — the fallback exists specifically for the case where structured data is entirely absent, not for the case where it's merely imperfect.

The correlation engine — a five-phase build, and why it had to move off the request path

Twenty-one files, three overlapping version-numbering schemes, one real production incident that reshaped the whole thing, and a scoring synthesis layer bolted on after the fact. This is the deepest chapter in the book — it earns it.

correlation/*.py — 21 filesADR-004

What "correlation" actually means here — and what it deliberately isn't

Worth being precise about scope before anything else, because the name is genuinely ambiguous across the codebase: this engine is primarily about CVE-to-CVE linkage — connecting different CVEs that share threat-intelligence evidence, chiefly OTX (AlienVault Open Threat Exchange) "pulses" and the indicators of compromise attached to them. It secondarily covers CVE-to-actor/sector attribution (via MITRE ATT&CK technique overlap and OTX's own adversary tagging) and CVE-to-vendor volume anomalies (a sudden spike in CVEs from one vendor). It is explicitly not CVE-to-detection matching (Chapter 21 owns that) and not CVE-to-asset matching (Chapter 19 owns that).

Reading the file docstrings: three numbering schemes, one evolving system

Almost every file in this package carries an inline "Phase N" or "CORR-PR-N" label in its docstring, and taken at face value they look inconsistent — priority.py calls itself "Correlation v3," while config.py still hardcodes CAMPAIGN_ALGORITHM_VERSION = "2.0.0-phase2" even though campaigns.py's actual behavior (pulse-family deduplication, a later addition tagged CORR-PR-9) is well past what "Phase 2" meant in the original plan. The accurate story, reconstructed from a now-superseded planning document (docs/archive/superseded/CORRELATION_V2_PLAN.md) plus every file's own docstring: a phased plan (Phases 1 through 5) was written and largely built section-by-section — the plan's own quality-control subsections (§24.1 through §24.13) map almost one-to-one onto individual files here — and then, after the plan was formally superseded by a newer spec document, more was built on top without renumbering: a priority-scoring synthesis layer (informally "v3"), and later still, ADR-004's precompute architecture. Don't read the phase labels as a strict changelog — read them as archaeological layers, each still live in production, none of them replaced by the next.

Phase 1 — Foundation: normalize, suppress hubs, dedupe pulses into campaigns

ioc_normalize.py is the entry gate every raw OTX indicator passes through before it's usable for correlation at all: it defangs indicators (OTX data arrives as hxxps://, 1[.]2[.]3[.]4-style defanged text, which this module un-defangs via four regex replacements), collapses type-name drift (IPV4/IPV6→IP, HOSTNAME→DOMAIN, MD5/SHA1/SHA256→HASH), and — worth calling out as a deliberate, documented scope decision — flags a small hardcoded set of 16 well-known public DNS resolvers (Google's 8.8.8.8, Cloudflare's 1.1.1.1, Quad9, OpenDNS, and their IPv6 equivalents) as always-noise. The code comment explains why the list stops there rather than growing into a full CDN/cloud-IP denylist: maintaining a comprehensive "which IPs are too generic to mean anything" feed was judged not worth the ongoing maintenance burden, when the general popularity-based degree penalty (below) already catches broader noise structurally instead of by name.

hub_suppress.py is the direct, named fix for the incident this chapter's ADR-004 section covers below: is_hub_cve() flags any CVE whose IOC pulse-count exceeds CORRELATION_HUB_CVE_PULSE_CAP (default 50), and filter_campaign_members() applies an asymmetric rule worth understanding precisely — if the CVE being queried is itself a hub, only its direct co-members survive (heavily capped); if it's not a hub, any peer that is one gets dropped from the expansion entirely. This asymmetry is what stops a single Log4Shell-scale CVE from gluing hundreds of otherwise-unrelated CVEs into one giant, meaningless "campaign" via shared low-value infrastructure. A separate function, apply_member_cap(), enforces a hard membership ceiling (default 25) by sorting CVE IDs and keeping the first N — deterministic across rebuilds, not weighted, so the same query always returns the same members.

pulse_families.py (tagged CORR-PR-9, a later addition) solves a real duplication problem: different analysts submit near-duplicate OTX pulses describing the same real-world campaign, under different names, with mostly-but-not-fully overlapping IOC sets. Two merge rules, implemented via classic union-find (disjoint-set with path compression): pulses merge if they share an identical CVE member set and identical normalized name, or if they clear a Jaccard similarity of at least 0.7 on their non-hub IOC sets (each side needing at least 3 IOCs before the comparison is considered meaningful — comparing two pulses that each have one IOC in common would be statistical noise, not a real similarity signal). Family IDs and campaign IDs are both derived deterministically as sha256(oldest_pulse_id)[:12], anchored to the family's oldest member — so IDs stay stable across nightly rebuilds even as a family's membership grows over time. A bridging function, legacy_campaign_id_for_pulse(), preserves the pre-dedup per-pulse ID scheme purely so that analyst suppressions recorded before this migration still resolve correctly afterward.

campaigns.py is both the nightly builder and the read path — its behavior has grown well past its own "Phase 1" docstring label. build_campaigns_from_pulses() calls rebuild_pulse_families first, then builds exactly one campaign per family (not per pulse), skips families under 2 members, computes lifecycle via the function covered below, and — notably — soft-retracts (rather than deletes) campaigns whose family vanished since the last run, preserving suppression history rather than silently losing it. The read path, get_campaigns_for_cve(), does something worth pausing on: it expands a campaign's membership with CVEs that share strong IOCs (hash/domain) with the anchor CVE even if they were never co-tagged in the same OTX pulse — a deliberate choice so that strong shared evidence isn't artificially siloed into the weaker "infrastructure" bucket (below) purely because of where OTX happened to draw pulse boundaries.

Phase 2 — Evidence: shared infrastructure, confidence, freshness decay, and honest copy

ioc_graph.py is, concretely, the file behind the ADR-004 incident below — its _shared_ioc_rows() function is the exact self-join (otx_pulse_iocs against itself, joined through otx_cve_pulses) that produced the O(n²) blowup on hub IOCs. find_shared_infrastructure_v2() is the orchestrator: batches enrichment confirmations and ThreatFox corroboration checks (rather than one query per IOC), computes per-edge confidence, aggregates multiple edges per peer CVE into one confidence tier, and sorts results by confidence first and IOC-type strength second (hash > domain > url > ip) — explicitly so a strong peer is never truncated out of the result limit in favor of one that merely sorted earlier alphabetically.

confidence.py holds the per-edge scoring rules, and it's worth being precise about the exact order of operations, because the order is itself a design decision: start from a base score by IOC type (hash=high, domain/url=medium, IP=low, with IP additionally forced to low if it's a noise address per ioc_normalize.is_noise_ip); apply confirmation adjustments from cached third-party enrichment (GreyNoise "malicious" bumps confidence up, GreyNoise "benign" pulls it down, MalwareBazaar/URLhaus hits bump it up); apply the degree penalty last

freshness.py is the exact formula this book quoted earlier, and it's worth re-reading now with the full picture: base score by type (hash 0.9, domain 0.6, url 0.65, IP 0.3) × a logarithmic degree penalty (flat below a pulse-count of 3, smoothly decaying above it — a softer, graduated sibling to hub_suppress.py's hard 50-pulse cliff) × an exponential freshness decay keyed to a per-type half-life (IP 30 days, URL 60, domain 120, hash 365 — reflecting that a file hash discovered a year ago is exactly as malicious today, while an IP from a year ago has very likely changed hands) × a corroboration factor rewarding independent confirmation with diminishing returns. One detail worth knowing: when neither an observed_at nor ingested_at timestamp is available at all, the function explicitly skips decay entirely (factor forced to 1.0, flagged freshness_fallback: true) rather than penalizing an indicator just because its age happens to be unrecorded.

confirm.py enforces a hard architectural rule worth stating plainly: it reads already-cached third-party enrichment (GreyNoise/MalwareBazaar/URLhaus, via the same ioc_cache table Chapter 23's IOC lookup writes to) and never makes a new HTTP call at correlation read-time — corroboration is only ever based on data some other subsystem already fetched for its own purposes. copy.py is small (three functions) but carries a real security property: every OTX-derived free-text string (pulse names, adversary names) that reaches an analyst's screen passes through sanitize_pulse_text() first, which HTML-escapes and truncates it — because OTX pulse names are community-submitted, user-generated text, and rendering them unsanitized would be a stored-XSS vector into BRIEFR's own UI.

attribution.py handles the alias-aware conflict check already covered in this book's earlier pass, precisely: build_alias_families() indexes every alias in MITRE's mitre_groups.aliases field so that "APT28" and "Fancy Bear" resolve to the same family, and attribution_conflict() returns true — a conflict — only when there's no evidence of agreement between an OTX-attributed adversary and a MITRE-technique-matched actor, rather than requiring positive proof of disagreement.

The analyst feedback loop: two genuinely different kinds of human input

It's worth distinguishing two mechanisms that sound similar but record different things. suppressions.py is dismissal — an analyst saying "hide this specific finding," scoped to a campaign, a CVE pair, a pulse, or an infrastructure link. Its most intricate piece, resolve_suppressed_campaign_ids(), exists because of a real migration wrinkle: suppressions were recorded against per-pulse campaign IDs before pulse_families.py's dedup shipped, so this function expands an old suppressed ID into whichever new, family-anchored campaign ID it now belongs to — an old dismissal keeps working correctly even after the underlying campaigns got merged. feedback.py is a separate, later addition (CORR-PR-12) recording a genuinely different judgment: confirm, reject, or resolve_conflict — not "hide this," but "this correlation is/isn't actually correct," which feeds directly into the confirmation-rate and rejection-rate metrics covered below.

threatfox_corroboration.py is the mechanism behind "independent corroboration" mentioned above: it cross-references an OTX-sourced IOC against BRIEFR's separately-ingested ThreatFox mirror table (Chapter 14), and a match there — a second, independent intelligence source agreeing — feeds directly into freshness.py's corroboration factor.

lifecycle.py computes a campaign's stage — emerging (≤7 days), active (≤14), declining (≤30), stale (>365 days with no KEV/PoC boosters) — strictly from the most recent true observation timestamp of any member (a pulse link date, an IOC's own observed_at), never from when BRIEFR itself happened to ingest that data (tagged CORR-PR-7, explicitly to prevent a genuinely stale campaign from appearing "emerging" just because BRIEFR synced it late).

The previously-undiscovered mechanism: local.py — correlation signal that needs no OTX key at all

This is the file this book's earlier gap-audit specifically flagged as unresearched, and it turns out to bundle two small, unrelated responsibilities under one "Phase 3" label. First, stack-matching: a Python-side re-check of whether a CVE mentions any of the operator's declared stack terms, deliberately mirroring (rather than re-querying) the SQL-based stack-match clause used elsewhere, to avoid a second database round trip on data already in hand. Second, and more consequentially, KEV/exploit "boosters": given a campaign's member CVE list, this function checks which members are independently KEV-listed or have public exploits — local database facts requiring no OTX API key whatsoever. This is the concrete mechanism behind BRIEFR's "degraded mode" promise: even with no OTX key configured at all, KEV/PoC/stack signal still flows into campaign scoring, because it never depended on OTX data in the first place. One nuance worth getting right: a booster is explicitly documented as a priority signal, not a confidence signal — a KEV-listed peer doesn't make the underlying correlation more trustworthy, it makes it more urgent to act on — which is precisely why boosters feed into priority.py's scoring (below) rather than confidence.py's.

Phase 4–5 — What analysts and operators actually see

clusters.py is the single function backing GET /api/correlation/clusters — the "Campaigns" list view. It filters to non-retracted, non-stale (unless explicitly requested), 2-or-more-member campaigns, cross-references the watchlist table to compute how many members are pinned, and sorts by a deliberate priority order: stack-relevance first, then watchlisted-member count, then total size, then lifecycle stage (emerging sorts before stale), then label alphabetically as a final tiebreak — a direct implementation of "show the analyst's own stack and pins first," not a generic popularity sort.

status.py backs the admin diagnostics view: last-run timestamps, campaign counts by lifecycle stage, CVE and OTX coverage percentages, suppression counts, and the latest metrics snapshot (below) — plus a static feature-flag manifest advertising which correlation capabilities are actually live, so the frontend/operator can introspect the deployed feature set directly.

metrics.py (CORR-PR-13) is the nightly self-monitoring snapshot this book referenced earlier, now precisely: over a rolling 30-day window it computes confirmation_rate and rejection_rate from the feedback table, a weak_edge_ratio (the fraction of all stored IOCs that are the weakest tier, IP-type), an orphan_cve_ratio (CVEs with OTX pulses but no campaign membership at all — a coverage gap, not a quality one), a campaign_survival_rate (today's active-campaign count over yesterday's — a churn signal), and a median_evidence_age_days. This is what turns correlation quality from an assumed property into a trackable, dated number.

The v3 addition: priority.py — one ranked number from four independent signals

This module is a later, un-phase-labeled addition sitting on top of everything above — its own docstring calls it "Correlation v3" and explicitly says it "mirrors scoring/risk.py's additive-capped-contribution model" (Chapter 18), applying the same explainable-and-bounded design instinct to a structurally different problem: converting four independent signal arrays (campaign, infrastructure, actor, temporal) into one 0–100 number an analyst can triage from directly, instead of scanning four separate lists.

Each of the four contributions is computed independently, then only positive ones are kept, sorted descending, summed, and capped at 100. The campaign contribution takes the highest-confidence campaign's confidence fraction, adds a flat +0.15 bonus if that campaign carries a KEV or exploit booster from local.py (explicitly documented as urgency, not certainty — the reason CORR-PR-4 moved this bonus out of confidence.py and into this file specifically, to keep the two concepts from bleeding into each other), caps the combined fraction at 1.0, and multiplies by 40. The infrastructure contribution adds a shared-IOC-count bonus (capped at +0.2) before multiplying by 25. The actor contribution adds a flat +0.3 if the matched actor's known sector overlaps the CVE's inferred sector, before multiplying by 20. The temporal contribution is simply min(1.0, anomaly_score / 5.0) × 15. Every component also carries a human sentence, so the final triage number is never presented without its own explanation — the same explainability requirement you've now seen enforced in the Risk Score, the Environment tier, and here, for a fourth time.

ADR-004 — the production incident, now traceable to an exact function

This is worth reading as a case study in how a real performance failure reshapes an architecture, because the numbers are concrete and the root cause is now traceable to a specific function rather than a vague "the correlation query." At production scale, ioc_graph.py's _shared_ioc_rows() self-joined a 132,802-row IOC table against a 49,209-row CVE-pulse table, and a small number of hub IOCs caused the join's result set to explode combinatorially — the textbook O(n²) fan-out problem. The measured result: GET /correlation took roughly 61 seconds, past the 60-second database timeout BRIEFR itself enforces. Worse, the Operational Priority endpoint (Chapter 18) called the exact same correlation-escalation check internally, silently inheriting the identical cost — an entire UI element simply never rendered, with no obvious error pointing back to correlation as the cause.

This directly violates the project's heavy-work-never-on-the-request-path rule. ADR-004's fix, gated behind CORRELATION_PRECOMPUTE_ENABLED (default off): a nightly job precomputes and stores a correlation snapshot per CVE, so the request path becomes a cheap indexed read. The same underlying compute function, _compute_correlation_for_cve() in engine.py, is reused for both the nightly precompute pass and the live on-demand fallback — meaning the system fails open to the old, slower-but-correct behavior rather than erroring outright whenever precompute is disabled or a snapshot doesn't exist yet.

engine.py — the orchestrator tying every phase together

This is the largest file in the package and the only one routers import directly. Beyond hosting _compute_correlation_for_cve and its cached public wrapper get_correlation_for_cve (6-hour cache, ADR-004 precompute-or-fallback logic, and a degraded-stub response on any exception rather than a propagated error), engine.py also implements the two correlation signals that don't live in their own files: actor/sector correlation (MITRE technique overlap, filtered to at least 25% technique overlap with the candidate group, plus a weaker OTX free-text adversary-field signal layered on top) and temporal volume anomaly detection (flagging a vendor whose this-week CVE count is at least 3× its 90-day rolling average — gated through local.py's stack-match check so an anomaly in a vendor nobody runs is suppressed as noise rather than surfaced).

The nightly orchestration, run_nightly_correlation(), runs in a fixed order worth knowing because each step depends on the one before it: rebuild the IOC-degree table first (so this run's confidence scoring uses fresh popularity counts) → temporal anomaly detection → prune campaign members whose CVE no longer exists (data hygiene against NVD retractions) → actor/sector correlation for recently-active CVEs → rebuild campaigns from pulses (which internally rebuilds pulse families first) → snapshot the quality metrics → optionally, if precompute is enabled, recompute and store a snapshot for up to 500 CVEs per run, committing after each individual row so a mid-batch crash only loses the one in-flight row, never the whole batch. Every stage wraps its own try/except with a Postgres-specific rollback helper, because Postgres — unlike SQLite — aborts an entire transaction after any single failed statement, so one failed metrics computation must not be allowed to poison the campaign-rebuild work that already succeeded in the same run.

Detection engineering — a generator, deliberately not a live detector

Why the rule-generation path is explicitly "no LLM," and where an LLM is allowed to help instead.

Given a CVE (and optionally an ATT&CK technique or CWE it maps to), this subsystem assembles a "detection pack" — community Sigma and Elastic rules fetched live from GitHub, BRIEFR's own template-generated Sigma rules, ready-to-paste SIEM queries in four dialects (Elastic KQL, Splunk SPL, Microsoft Sentinel KQL, IBM QRadar AQL), and YARA rules built from file hashes OTX has observed in the wild. It's worth being precise about what this is not: nothing here executes against live logs or fires an alert. It generates and aggregates starter content for an analyst to adapt — a detection-engineering accelerator, not a detection engine in the SIEM sense.

Why the generation path is explicitly, deliberately "no LLM"

Community rule coverage (SigmaHQ's public repository, Elastic's detection rules) is genuinely patchy — most CVEs, especially recent or less prominent ones, simply have no published community rule yet, and waiting for one is not a real fallback plan. The obvious modern instinct is to have an LLM generate a plausible-looking rule on demand. detection/composer.py's own docstring rejects that instinct explicitly: the template-based generation path is deterministic, keyed by ATT&CK technique ID or CWE, precisely because a generated detection rule needs to be reproducible (the same input always produces the same rule, so two analysts comparing notes are looking at the same thing) and honestly labeled — every generated rule ships with status: experimental and an explicit briefr_confidence tier (HIGH/MEDIUM/LOW), rather than an LLM's confident-sounding prose that might describe detection logic which doesn't actually work as written, with no easy way for an analyst to tell the difference between "this was carefully derived" and "this sounds plausible."

LLM involvement isn't absent from the system entirely — it's deliberately isolated to a narrower, separate, scheduler-only step: extracting structured hints (HTTP paths, parameters, keywords) from CVE and exploit-writeup text, which then enriches the deterministic templates rather than replacing them. The distinction matters: an LLM is trusted to notice "this exploit writeup mentions the path /api/upload" (a narrow, checkable extraction task) but never trusted to invent the actual detection logic (the Sigma rule's condition block) from scratch.

Routing a CVE to a detection class, and a documented concurrency bug fix

class_router.py is the single resolution path everything else depends on: an ATT&CK technique prefix (T1190 maps to a web_exploit class) or a normalized CWE (CWE-89, SQL injection, maps to sqli) resolves to one stable "detection class" slug, which every downstream template set — Sigma generation, SIEM query generation, class-level fallback queries — keys off consistently. One implementation detail is worth knowing because it's a real, previously-shipped bug fix rather than a stylistic choice: community-rule fetching from GitHub (Sigma rules, Elastic rules) runs strictly sequentially, not in parallel via asyncio.gather as you might otherwise expect for two independent network calls. A code comment explains why directly — both lookup functions share a single asyncpg connection, and Postgres does not permit two concurrent queries on the same connection at once. Running them concurrently previously caused a documented 15-to-30-second hang (two queries silently contending for the same connection, each waiting on the other), fixed simply by making the two calls sequential instead. It's a small, concrete lesson in something Part 0 flagged in the abstract: async/await gives you concurrency, not automatic safety, and a shared resource (here, one database connection) can still serialize supposedly-parallel code in a way that produces exactly the kind of hang you'd assume async was supposed to prevent.

Injecting extracted artifacts without corrupting the rule

When the LLM-extracted keywords/paths from artifact extraction get merged into a generated Sigma rule, the merge only happens for rules whose condition is the flat keywords type — a simple "does the log line contain any of these strings" match. A different Sigma rule shape — say, a Windows process-tree selection/filter rule with structured field matching — has an entirely different schema, and blindly injecting extracted keyword strings into that structure would silently produce a malformed or logically wrong rule rather than a working one. The safety check here is narrow and specific on purpose: enrichment only applies where the target shape is simple enough to guarantee it can't corrupt the underlying detection logic.

The DetectionContext family — one cache entity, three independent writers

Four files share the word "context" in their name and are easy to assume are redundant — they aren't. context.py is purely the data model and cache accessor: it defines the DetectionContext envelope shape (CWE IDs, product, detection class, an artifacts list, plus provenance fields recording which model/provider populated it), and builds a bare version of it from nothing but static CVE metadata — no network call, no LLM. The other three files are independent jobs that populate the artifacts field of that same cached envelope, each with a different trigger and a different method:

context_sync.py is the cheap, broad backfill job (disabled by default): it finds every CVE that has no context row at all yet and writes a bare, empty-artifacts envelope for it, prioritizing KEV/PoC/recency — its entire job is making sure every CVE has something to read, never adding real artifacts itself. context_nuclei_sync.py is a deterministic enrichment job (on by default), triggered specifically for CVEs just touched by the exploit-sync job (Chapter 14): it parses actual Nuclei template YAML (via nuclei_parser.py, no LLM at all) to extract real HTTP paths, parameters, and keywords, and merges new artifacts onto whatever already exists, capped at 8, deduping by content. context_llm_sync.py is the LLM-based sibling (disabled by default, needs an explicit flag and a configured provider): it targets CVEs with a public exploit that haven't had an LLM extraction attempt recently, runs inside the per-job provider-skip session from Chapter 24 (so one empty response from a provider doesn't waste the rest of a batch retrying it), and — worth flagging as a real, load-bearing difference from the Nuclei job — overwrites the artifacts field outright rather than merging. If both jobs eventually touch the same CVE, whichever ran more recently wins completely on the artifacts field, not just contributes to it.

Both enrichment jobs converge on the same validation gate in artifact_extract.py: paths capped at 200 characters (max 5), params/keywords capped at 80 characters (max 10 each), HTTP method restricted to a real-verb whitelist, and an artifact that's entirely empty across all three fields is discarded outright rather than stored as a hollow shell. This shared gate is what lets a caller reading a DetectionContext never need to know or care whether Nuclei parsing or an LLM populated it — both paths are guaranteed to produce the same validated shape.

The fallback tier below ATT&CK techniques: class_queries.py

When a CVE maps to no ATT&CK technique at all, class_queries.py is the next tier down — ten vulnerability classes (path traversal, command injection, SQL injection, XSS, deserialization, code injection, unsafe upload, SSRF, XXE, auth bypass, memory corruption, default credentials), each with all four platform queries pre-built from one of three shared "query pack" templates (URI-based, path-based, body-based hunting terms) or, for the classes that don't reduce neatly to "look for these terms in a field" (unsafe upload needs a method-and-extension combination; memory corruption and default credentials are event-code or account-name based), fully bespoke queries instead.

Per-platform SIEM query generation — four genuinely different query languages, concretely

siem_queries.py is the ATT&CK-technique tier proper, covering 11 real techniques plus a generic default, and it's worth seeing the actual syntax differences rather than taking "four dialects" as an abstract claim. For the same underlying detection intent (T1190, exploiting a public-facing application), Elastic KQL reads as field:value pairs — http.response.status_code:(400 or 403 or 500 or 503) and http.request.body.bytes > 500. Splunk SPL is space-separated implicit-AND search terms piped into aggregation stages — the same rule ends with | stats count by {{SRC_IP}}, {{URI}}, status | sort - count, using a pipe-stage syntax none of the other three platforms have. Microsoft Sentinel is Kusto — it starts from a bare table name and chains | where/| project stages, calling functions like ipv4_is_private() that don't exist in the other dialects. IBM QRadar AQL reads like SQL — SELECT ... FROM events WHERE ... LAST 24 HOURS, with QRadar's own time-window clause built into the query text itself rather than left to the platform's UI. Every generated query also ships a field-name legend, because a placeholder like {{SRC_IP}} maps to a different real column depending on which specific log source an analyst has actually configured (Splunk's {{URI}}, for instance, might really be uri_path, cs_uri_stem, or url depending on the sourcetype) — the generated query is a strong starting point, not a guaranteed drop-in.

Finding rules that already exist, before generating new ones

rule_sources.py is the community-rule discovery layer this chapter's class-router section already referenced for its documented concurrency fix — worth adding one more real detail: unauthenticated GitHub code search is capped at 10 requests per minute, and the module's own comment records that this limit caused a genuine 15-to-30-second hang on a CVE's very first Detect-tab view, initially misdiagnosed as a frontend bug before the root cause (an unconfigured GITHUB_TOKEN still attempting a rate-limited search) was found. The fix mirrors a pattern you've seen elsewhere for GreyNoise and OTX: if no GitHub token is configured at all, skip the search call entirely rather than let it queue. SigmaHQ is searched by CVE ID first, falling back to ATT&CK technique IDs only if that yields nothing; Elastic's rule repository, by contrast, is searched by technique ID only, since Elastic's own rules are organized around techniques rather than indexed by CVE.

YARA rules from OTX-observed hashes, concretely

yara_generator.py validates every candidate string against a strict format check (exactly MD5, SHA1, or SHA256 length and hex-character shape — nothing else is accepted as a "hash") and, critically, maps each hash length to the matching YARA builtin function — a 32-character hash gets hash.md5(0, filesize) == "...", a 64-character hash gets hash.sha256(...) — rather than assuming every hash is SHA-256. Every generated rule's metadata block is explicit about its own provenance: author = "BRIEFR (generated from OTX)" and confidence = "experimental", so a rule built this way is never mistaken for one an analyst hand-verified.

A specific implementation detail here doubles as a genuinely useful, general lesson about the dual-SQLite/Postgres architecture from Chapter 9: EPSS delta ranking (finding the CVEs whose score moved the most) is computed in Python after fetching raw change-history rows, rather than with a SQL ORDER BY on a cast numeric value — because SQLite's CAST(x AS REAL) is forgiving of non-numeric text (silently produces 0 rather than erroring), while Postgres's equivalent cast raises an error outright on a genuinely non-numeric string. A query that works fine against the SQLite test suite can fail outright in Postgres production for this exact reason — precisely the trap Chapter 9 warned you to test both ways, made concrete in a real, specific piece of code rather than left abstract.

The brief computes its own _priority_score heuristic rather than reusing Chapter 18's Operational Priority system — and this is a deliberate choice, not a missed refactoring opportunity. A KEV deadline due soon starts at 100 points plus an urgency bonus that scales with how few days remain; a brand-new KEV entry starts at 90; an EPSS mover starts at 70 plus a bonus scaled to the size of its score jump; a stack match starts at 60, boosted further if it's also KEV-listed or has a rising EPSS trend. The reason a P1–P4 band alone wouldn't serve this purpose: the brief needs to interleave five genuinely different kinds of reason into one ordered list, and a coarse four-bucket priority band can't distinguish "a KEV deadline in 2 days" from "a KEV deadline in 13 days" the way a continuous urgency-scaled score naturally can — the brief's job is fine-grained ranking within a single list, which is a different problem from Chapter 18's job of assigning a stable, explainable priority tier to one CVE in isolation.

ML and LLM enrichment — three genuinely different categories, and zero Anthropic dependency

Local embeddings, hosted-API LLM calls, and plain deterministic enrichment are three separate things that get talked about as if they were one — this chapter draws the actual lines, verified directly against the code.

ml/embeddings.pyml/product_extraction.pyai/llm_router.pyenrichment/*.py

Three categories, not one blurry "AI" bucket

It's worth being disciplined about vocabulary here, because "AI" gets used loosely to mean at least three structurally different things in this codebase. True local machine learning: CPU-only sentence embeddings, computed by a small ONNX model (BAAI/bge-small-en-v1.5, via the fastembed library) running entirely on BRIEFR's own hardware, no network call involved — used to power "related CVEs" and semantic search via cosine similarity between vectors. This is env-gated off by default, and computed only during scheduled backfill jobs; the request path only ever reads vectors that were already computed and stored, with an explicit code comment stating "Related CVEs must not call this — they use stored vectors only," closing off any temptation to compute an embedding live on a request. LLM-assisted enrichment: a genuine network call to a hosted large-language-model API — extracting a structured {vendor, product, version_range} triple from free-text CVE descriptions when NVD hasn't yet analyzed a freshly-published CVE, extracting detection-rule artifacts (Chapter 21), and generating on-demand PDF executive summaries. All three are scheduler-side or explicitly on-demand, gated off by default, and every single one has a deterministic template fallback available. Plain deterministic enrichment, no ML or LLM involved at all: regex-derived MITRE technique tags and proof-of-concept flags pulled from NVD's own reference-link tags, DNS hostname format validation, and third-party IOC reputation lookups (VirusTotal, AbuseIPDB, GreyNoise) — these are just structured API calls or pattern matching, and calling them "AI" would be a real category error worth correcting if you hear it described that way.

The provider chain — verified: no Anthropic client exists anywhere in this stack

A direct search across ai/, ml/, and enrichment/ confirms there is no Anthropic or Claude API client anywhere in this codebase. ai/llm_router.py instead implements a fixed-order failover chain across free and cheap-tier providers — Groq, then Cerebras, then OpenRouter, then Gemini as the last resort — explicitly "not round-robin": one attempt per provider per call, in that exact priority order, falling through to the next only on failure or an empty response. The reasoning, visible in the code's own comments (a display-order comment states plainly that admin UI ordering matches failover priority, "Gemini is last resort"), is straightforward cost engineering: keeping a self-hosted tool's operating cost near zero by leaning on free and cheap-tier LLM providers rather than paying premium-tier API prices for enrichment tasks that are genuinely optional polish, never load-bearing functionality.

Why every LLM feature has a deterministic fallback, without exception

This is the detail that ties the whole chapter together: BRIEFR must fully function for an operator who configures zero LLM API keys at all — a real, expected, and fully-supported deployment mode, not an edge case. A single gate function, any_llm_provider_configured(), controls whether LLM-dependent features attempt to run at all; when it's false, PDF executive summaries fall back to a template-based _template_executive_summary instead of an LLM-generated one, product extraction and detection-artifact extraction simply don't run (CPE data and deterministic Nuclei-YAML parsing still populate the same underlying fields through non-LLM paths), and semantic search degrades to keyword-only matching, reporting that fact honestly in its response metadata rather than silently pretending to be semantic. Every one of these enrichments is additive polish layered on top of a fully-functional core product — never something the core product's correctness depends on.

The actual algorithm underneath "semantic search" — cosine similarity, made concrete

It's worth de-mystifying exactly what "embeddings" computes, since the term gets used as if it were magic. An embedding model turns a piece of text into a fixed-length list of numbers — a vector — positioned in a high-dimensional space such that texts with similar meaning end up as nearby vectors, even if they share few or no exact words in common. "Semantic search" then reduces to a genuinely simple piece of arithmetic: compute the embedding vector for a search query, compute (or, in BRIEFR's case, already have stored) the embedding vector for every candidate CVE description, and rank candidates by cosine similarity — the cosine of the angle between two vectors, which is 1 when they point in exactly the same direction (maximally similar in meaning) and 0 when they're orthogonal (unrelated). There's no learning or inference happening at search time at all — the model already did the hard work once, ahead of time, when it produced the stored vectors; a live search is pure vector arithmetic, which is exactly why it's cheap enough to run on the request path when a live LLM call would not be.

At real scale, comparing a query vector against every single stored vector one by one (a brute-force linear scan) becomes too slow to do on every request once the CVE corpus is large. This is what pgvector's ANN (Approximate Nearest Neighbor) index solves — a data structure that finds vectors very close to the true nearest matches, in a fraction of the time a brute-force scan would take, trading a small, usually irrelevant amount of ranking precision for a large, very relevant speed gain. BRIEFR's hybrid search then blends this vector-similarity ranking with ordinary keyword search rather than relying on vectors alone — deliberately, because embeddings are excellent at "this text means something similar" and comparatively weak at exact-token matching (a CVE ID, a specific product version string, an exact error code an analyst pastes in verbatim) — the two techniques cover each other's blind spots.

Why BAAI/bge-small-en-v1.5 specifically — and why not a bigger, "better" model

Embedding models span an enormous size range — from tens of millions of parameters up to models comparable in size to a full LLM. BRIEFR's choice sits deliberately at the small end for reasons that connect directly to Chapter 25's resource-consciousness thread: bge-small-en-v1.5 is a compact model (roughly on the order of tens of millions of parameters, not billions) specifically chosen so it runs acceptably fast on ordinary CPU hardware via ONNX through fastembed — no GPU, no PyTorch runtime dependency, no meaningful extra RAM budget beyond loading one small model file. A larger, more capable embedding model would very likely produce marginally better semantic rankings, but at a real cost this project has explicitly declined to pay: slower CPU inference (mattering directly for how long a bulk backfill job takes, since Chapter 24 established this only ever runs in the scheduler, never on the request path), a meaningfully larger memory footprint just to hold the model in memory, and — for anyone considering a hosted embedding API instead of a local model — a recurring per-call cost and a dependency on sending CVE and asset-stack text to a third party, which cuts directly against BRIEFR's self-hosted, privacy-conscious posture (the same instinct behind self-hosting fonts in Chapter 5, stated again at the ML layer). A small, local, CPU-only model is the one choice that satisfies "works fully offline," "costs nothing per query," and "keeps analyst data on the box" simultaneously — three properties a larger or hosted model would each individually break.

The real restrictions this choice imposes — worth naming precisely, not glossing over

A small local model is not a free lunch, and the honest restrictions are worth stating explicitly rather than only praising the upside. Fixed dimensionality: every vector this model produces has the same fixed length, set once by the model architecture — switching to a different embedding model later isn't a drop-in config change, because old and new vectors would live in incompatible spaces, meaning a model change requires re-embedding the entire historical corpus from scratch, not a quiet migration. English-biased: the model name says it plainly (-en-) — this is trained predominantly on English text, so semantic quality for non-English CVE descriptions or analyst queries would be meaningfully weaker, a real limitation for any future internationalization of the product. No fine-tuning on BRIEFR's own domain data: the model is used exactly as published, off the shelf, with no additional training on CVE-specific or security-specific text — it brings general-purpose semantic understanding, not a specialized notion of, say, which CVEs security professionals consider "similar" in a way a general text model wouldn't naturally capture. CPU-bound throughput: embedding a large historical backlog of CVEs is measurably slower on CPU than it would be on a GPU, which is precisely why the backfill is scheduler-only, resumable, and explicitly never something the request path can trigger inline — a direct, load-bearing consequence of the CPU-only choice, not an unrelated design decision.

Inside the LLM failover chain — pacing, quota, audit trail, and the one request-path exception

Eleven more files behind llm_router.py's four-provider chain: how BRIEFR keeps every free-tier provider from ever seeing more traffic than it publishes, and how every attempt gets a permanent, queryable record.

Proactive pacing vs. reactive quota tracking — two different mechanisms, easy to conflate

Worth separating two things that sound like the same job. llm_pacing.py is proactive: before ever making a call, it computes the minimum safe interval between requests to a given provider from that provider's published RPM (requests/minute) and TPM (tokens/minute) limits, takes whichever bound is more restrictive, and applies a safety-margin "headroom" percentage on top (85% by default — treating a stated 30-RPM plan as if it were really 25.5 RPM, so normal jitter and estimation error can't accidentally exceed the real limit). quota.py is reactive: it's a plain in-process dictionary that simply records whatever rate-limit headers a provider actually sends back after a real call (remaining requests, remaining tokens, reset timestamps), purely as an observability cache for the admin UI — it computes nothing and enforces nothing itself, it's just a cache of ground truth the provider handed BRIEFR after the fact.

The real, published free-tier numbers behind the pacing math are worth knowing because they explain the failover order: Groq's own limits (30 RPM / 8,000 TPM, held in groq_config.py) are the most generous, which is why it's tried first; Cerebras's free-trial limits (5 RPM / 30,000 TPM) are the tightest of the four on requests-per-minute, explaining why it sits mid-chain rather than first despite otherwise being a fast, capable provider; OpenRouter's free tier (20 RPM / 40,000 TPM) sits third with the only 1-second pacing floor of the four (the others default to 0.5s); Gemini Flash-Lite's free tier (15 RPM / 250,000 TPM) is deliberately last — not because its limits are worst, but per the code's own ordering comment, because it's explicitly reserved as the last resort. Each provider's quota-warning threshold is a flat, hardcoded "5 requests remaining" trigger for the admin UI's low-quota banner — not configurable, a deliberately simple tripwire rather than a tunable alert system.

Two small guard files sit in front of every one of these calls. llm_payload.py checks that a prompt actually has substantive content before any HTTP work happens at all — an empty or near-empty message never leaves the process, closing off the cheapest possible way to waste a scarce free-tier quota. llm_session.py scopes a per-batch-job memory of which providers have already returned an empty (not erroring, just content-less) response during the current job, so a Groq that goes quietly unresponsive partway through a 50-CVE batch doesn't get retried on every remaining CVE in that same run — it's skipped locally for the rest of the job while still counting toward the shared circuit breaker globally. The actual wire-format clients are split in two: openai_chat.py is the one shared client for the three providers (Groq, Cerebras, OpenRouter) that all speak the OpenAI-compatible chat-completions format, while gemini_client.py exists separately because Google's generateContent API has a genuinely different request shape (a contents/parts structure and a top-level systemInstruction, rather than a flat messages array) and its own header-based auth convention rather than a bearer token. groq_config.py holds shared Groq URL/model defaults (GROQ_MODEL / GROQ_MODEL_SUMMARY) and groq_limits() for pacing. operations_admin.py is the read-only payload builder for the admin "AI Operations" page — assembling per-provider health, quota, and configuration state into the JSON the frontend renders, with no database queries of its own beyond what's handed to it already aggregated. Package entry ai/__init__.py re-exports only the on-demand summary helpers from ai/summary.py (generate_executive_summary, generate_investigation_summary) — LLM router internals are imported by path, not via this package facade.

One source of truth for which model runs which task, in what order

model_catalog.py is the single place that answers "which provider, which model, in what order, for this specific task" — its own docstring calls it the system's SSOT. There are exactly three LLM-backed tasks in the whole system (product extraction, PDF summaries, detection-context extraction), and the file's insertion order for provider env-var keys is the documented failover order the admin UI displays. One task-specific branch point is worth knowing: PDF summaries use a larger Groq model (120b parameters) as their first hop, while the other two tasks use a smaller one (20b) — a summary is generated rarely, on explicit user request, so the extra cost/latency of a bigger model is worth paying; product and detection extraction run in scheduler batches across potentially hundreds of CVEs, where a smaller, faster model matters more. A small operational scar is preserved directly in a code comment: OpenRouter's free Gemini Flash-Lite model ID was removed from OpenRouter's own catalog at one point, forcing a fallback default model swap — evidence that even a carefully engineered free-tier stack is still exposed to upstream catalog churn outside BRIEFR's control.

Every LLM attempt gets a permanent audit row — success, failure, or empty alike

operations_recorder.py writes one row to the ai_operations table for every completion attempt, not just successes — including a classified error reason (empty, circuit_open, timeout, auth, rate_limit, model_not_found, or unknown, derived by pattern-matching the raw exception text) and, critically, fallback_from_provider/fallback_from_model fields — so a single logical operation that failed over from Groq to Cerebras to Gemini before finally succeeding leaves a reconstructable trail of the entire chain it walked, not just the final outcome. This recorder deliberately swallows its own exceptions (wrapped in a bare try/except with a warning log) — a design point worth connecting back to Chapter 16's outbound-metering discipline: the audit trail must never be capable of breaking the actual LLM call it's recording.

The one LLM call that does run on the request path — and why it's allowed to

The underlying data is a structured YAML corpus split cleanly into two categories with very different trust levels: generated facts (components, the API inventory, scheduler job list, database table list, BRIEFR's own detected tech-stack terms — all regenerated automatically by scripts/generate_security_corpus.py directly from the codebase) and curated judgment (trust boundaries, security controls, abuse-case scenarios, documented security decisions, known risks, and their review history — each curated record requires an explicit review_date and supporting evidence, not just an assertion).

The design principle stated directly in the module's own code is the single most important thing to understand about it: "no new matching/scoring code." Every view in this feature deliberately reuses logic that already exists and already ships in the real product — the stack-match clause from routers/cves/list.py, the coverage-map builder from routers/forge.py, the threat-scenario generator from Chapter 23 — rather than computing its own independent version of anything. This is a genuinely clever piece of engineering discipline: it guarantees, by construction, that the security-architecture view can never silently drift out of sync with what the product actually does, because it has no separate code path capable of drifting in the first place. A less careful implementation might reimplement "does this CVE match our stack" a second time for this feature specifically — and the two implementations could quietly diverge the moment one of them gets updated and the other doesn't.

A staleness mechanism keeps the curated half honest over time: any curated record whose review_date is more than 90 days old renders as explicitly STALE in the UI and is excluded from the feature's aggregate ratio calculations (like "percentage of controls actively verified"). Without this, a security review written once could sit unchanged for years, silently presenting a snapshot of a system that has since changed underneath it as if it were still current — the 90-day cutoff forces the curated content to be periodically re-attested or visibly marked as no longer trustworthy, rather than aging silently into a false sense of assurance.

Worth heading off directly: this is not the tool being paranoid about its own supply chain, and it's not a marketing feature dressed up as security theater. What "drift detection" precisely means, verified against the code

"Drift detection" is a claim easy to leave vague, so it's worth being exact about what corpus_drift.py actually compares. It imports the generator script (scripts/generate_security_corpus.py) directly, runs it into a fresh temporary directory, and does a parsed-value equality comparison — not a byte-for-byte text diff — between each committed generated YAML file and its freshly-regenerated counterpart. Why this specific feature needed real SSRF hardening

Recall Part 0's definition of SSRF: a server tricked into making a request on the attacker's behalf, often reaching internal-only services the attacker couldn't otherwise touch directly. Webhook destination URLs are exactly this shape of risk in BRIEFR, because they're operator- or user-supplied input that the server then dutifully fetches — a malicious or compromised operator account (or a webhook URL copied from an untrusted source) could point a "destination" at an internal-only admin panel, a cloud metadata endpoint, or any other service the server can reach but an external attacker normally couldn't.

webhooks/ssrf.py — the blocklist covers RFC1918 private space, loopback, link-local, CGNAT, and IPv6 equivalents

The real request flow, worth tracing exactly because the details are what make this mitigation actually correct rather than superficially plausible: safe_webhook_request() first parses the destination URL and resolves its hostname via DNS, then runs every resolved IP through validate_resolved_ips(), rejecting any address that falls in the blocked-networks list above before a single byte is sent anywhere. Only then does it connect — critically, to the pinned, already-validated IP address literal, not to the hostname again. This detail is the one most naive SSRF mitigations get wrong: if you validate the hostname's DNS resolution once and then reconnect using the hostname a second time, an attacker who controls the DNS record (or exploits a very tight timing window between validation and connection) can have it resolve to a safe address for your check and a dangerous internal address for the actual connection — a class of bug called DNS rebinding. Connecting to the exact IP you already validated, rather than re-resolving the hostname, closes that gap by construction.

That creates a second problem the code has to solve immediately: if you connect to a bare IP address literal, standard TLS certificate validation checks the certificate against that IP — which fails for essentially every real-world webhook destination, since Discord, Slack, and similar services sit behind CDNs whose certificates are issued for the hostname, not for whichever of their many backend IPs happens to answer a given connection. The code's own comment explains the fix precisely: it sets sni_hostname to the original hostname, so the TLS handshake presents and validates against the correct hostname via SNI (Server Name Indication) while the actual TCP connection still goes to the pre-validated, pinned IP — getting both properties at once, correct certificate validation and SSRF safety, that would otherwise seem to be in tension. The same code carves out two narrow, correct exceptions: it skips setting SNI when the destination URL is itself a bare IP literal (RFC 6066 forbids IP literals in SNI, and there's no hostname to validate against in that case anyway), and it IDNA/punycode-encodes non-ASCII hostnames before use, because Python's ssl module raises a UnicodeEncodeError during the handshake otherwise.

One more layer, easy to overlook: sanitize_outbound_headers() strips a hardcoded list of BRIEFR-internal authentication and API-key headers before any outbound webhook request is sent — Authorization, the internal admin-key header, and every configured third-party API key header. This closes a completely different risk than SSRF itself: even a validated, safe destination shouldn't ever receive BRIEFR's own internal credentials as a side effect of some header being carried along accidentally from an internal context.

A naming correction worth making explicitly: it would be reasonable to assume webhooks/sender.py holds the low-level HTTP transport logic this chapter just walked through — it doesn't. Read directly, it's a thin, six-name facade re-exporting dispatch_event/send_alert/send_test_message from engine.py and two small "is this destination configured" convenience checks. The actual SSRF-hardened transport lives entirely in engine.py and ssrf.py — sender.py exists purely to give other modules a small, stable import surface without needing to reach into engine.py directly.

Both backends produce tar bundles with optional X25519 encryption — and the encryption key is required, by an explicit enforced check, to live outside the backup directory itself, for a reason that should be obvious once stated: an encrypted backup whose decryption key sits right next to it in the same backup archive or directory provides no real protection at all if that directory is ever copied, leaked, or compromised as a whole.

Migration (migration/sqlite_to_postgres.py) is a completely separate concept from Alembic, despite touching some of the same territory — Alembic (Chapter 10) only ever handles schema DDL, forward-only, automatically, on every startup. This module is a one-shot, admin-triggered data copy: an operator moving from the zero-config SQLite dev setup to a real Postgres production deployment runs this once, and it first runs alembic upgrade head against the new Postgres target to get the schema right, then copies actual rows table by table in dependency order (respecting foreign-key relationships so a child row is never inserted before its parent exists), persisting progress into sync_state so that a crash mid-migration is correctly reported to the operator as "interrupted, needs attention" rather than silently appearing to have succeeded, or worse, silently appearing as if it simply hadn't started.

Diagnostics (support_pack.py) assembles a single redacted JSON bundle — health status, database integrity, feed health, correlation status, production-posture warnings, and recent log entries — for an operator to hand to someone helping them debug an issue, explicitly redacting database connection URLs and never including secrets of any kind, consistent with Chapter 13's redaction discipline. Monitoring (api_key_health.py) actively pings every external API key BRIEFR has configured (NVD, Groq, Gemini, GitHub, OTX, GreyNoise, AbuseIPDB, and others) with a cheap, low-cost probe request, persists the result, and emits an operator notification (Chapter 28) the moment one goes unhealthy — with a genuinely thoughtful dedup detail: it normalizes digit runs inside error messages before comparing them for deduplication purposes, so an error message whose only difference from the last one is an embedded timestamp or a changing port number doesn't defeat deduplication and spam the operator with what looks like a new, distinct failure every single time it's checked.

Wallboard (wallboard/service.py, session.py) is a read-only kiosk-mode dashboard — the kind of thing you'd put on a wall-mounted monitor in a SOC — cached for roughly 45 seconds since kiosk displays typically poll every 60 to 120 seconds and don't need fresher data than that. It runs its own entirely separate signed httpOnly cookie session scheme rather than reusing the main JWT auth system from Chapter 11, specifically so the raw, shareable WALLBOARD_TOKEN secret is never actually stored client-side in any form a browser could expose — a deliberate isolation between "credential a human logs in with" and "credential a kiosk display authenticates with," even though both ultimately grant read access to similar data.

The rest of the backup toolchain, and two smaller ops files

backup/postgres_util.py holds every Postgres-specific helper manager.py calls into rather than implementing directly: locating the real pg_dump/pg_restore binaries (checking both the system PATH and Debian's versioned /usr/lib/postgresql/N/bin/ path), running them as subprocesses with --no-owner --no-acl (so a restore doesn't fight over Postgres role ownership on a different box), tolerating pg_restore's exit code 1 as "warnings only" rather than a hard failure, verifying a dump file's integrity by checking its magic-byte header before trusting it, and redacting the connection URL's embedded credentials before it's ever written to a log line. backup/__main__.py is the CLI surface an operator actually runs by hand or from a cron job (python -m backup run|list|restore|verify|ensure|keygen) — pure argument dispatch onto the functions above and in manager.py, each subcommand returning a shell-appropriate exit code so it composes correctly in scripts.

monitoring/notifications.py is the aggregation layer sitting one level above the API-key health checker: it merges recent audit-log rows, job-error entries, and unhealthy-key alerts into a single, time-ordered operator notification feed — reusing Chapter 13's audit-log redaction rather than re-implementing it. metrics/request_counter.py is genuinely trivial, confirmed directly rather than assumed: a thread-locked integer counter with an atomic read-and-reset, existing purely to answer "how many requests came in since the last resource sample" for the resource-monitoring collector this chapter's Chapter 31 companion covers.

read_cache.py is the short-TTL in-process cache used by hot read paths (including health-style endpoints) so polling UIs do not stampede the database. storage_metrics.py and resource_collector.py feed Admin Storage / Resources charts — table sizes, host disk, CPU/memory trends — without standing up Prometheus.

task_registry.py exists because of a genuinely subtle Python detail worth knowing in its own right: asyncio's event loop only holds a weak reference to a task you spawn with asyncio.create_task() and don't otherwise keep a reference to — meaning Python's garbage collector is technically free to collect that task object (silently cancelling it mid-execution) the moment nothing else refers to it, even while it's still actively running. A fire-and-forget background operation (an ingest sync, a snapshot build) spawned this way could simply vanish partway through, with no exception, no log message, nothing — a bug class documented internally as REST-002/REST-012. task_registry.py's fix is to hold a strong reference to every such spawned task in a registry the module itself owns, specifically so shutdown can wait (with a bounded timeout, not indefinitely) for in-flight tasks to finish cleanly, instead of either killing them mid-write or leaving them to be silently garbage-collected at an unpredictable moment.

Finally, tracking.py is worth a one-line correction to a natural first assumption: despite the generic name, this is external API quota tracking — daily, weekly, monthly, and hourly usage counters per external service (NVD, VirusTotal, AbuseIPDB, GreyNoise, OTX, and the LLM providers from Chapter 24) — not user analytics or telemetry of any kind. Its has_quota() check gates outbound calls before they're made, letting BRIEFR proactively avoid exceeding a provider's quota rather than discovering the violation only after a request fails.

The last five files: metering's two halves, queue-status labeling, the read cache, and resource sampling

Top-level api_metering.py and db/api_metering.py (Chapter 9) share a name but split a single job in two: the top-level file is the write-path hook, called from resilient_client.py after literally every outbound HTTP attempt anywhere in the system, pulling actor/job/request context from contextvars and handing off to the db/ module's actual SQL — wrapped in a bare try/except specifically so a metering failure can never take down the outbound call it's trying to measure. api_queue_operations.py is not a queue implementation at all — it's pure labeling and redaction for the API-queue status UI Chapter 16 describes: it translates internal operation keys into analyst-facing strings ("Fetching vulnerability intelligence" rather than cve_lookup), and sanitizes any context ID before it's ever displayed — a CVE ID or IP address passes through cleanly, but a webhook URL gets its path tail stripped so a Discord/Slack webhook secret embedded in a URL never surfaces in the admin UI.

read_cache.py is exactly as small as it sounds, confirmed directly: an in-process dictionary plus a monotonic clock, a 45-second default TTL, no Redis, no persistence — this is the literal mechanism behind /api/health's caching from Chapter 25. resource_collector.py is the scheduler-side sampler feeding the admin Resources dashboard (Chapter 30's resource_metrics.py table): it walks BRIEFR's own process tree (and Postgres's, when applicable) via psutil, computes CPU percentage from raw time deltas rather than trusting a blocking library call, and pulls the request count from metrics/request_counter.py on every sample specifically so the counter can be reset immediately after each reading. storage_metrics.py is the complementary table-level view: per-table disk usage (a genuinely different query per backend — Postgres's own size functions vs. SQLite's dbstat virtual table) and a rough daily-growth estimate derived from comparing successive backup archive sizes over time, honestly reporting "insufficient history" rather than guessing when fewer than two backups exist to compare.

The systemd unit — hardening flags that are each a real decision

Reading deploy/briefr-backend.service directly rewards close attention, because nearly every line is a security or reliability decision with its own comment explaining why, not a default left in place. ExecStart runs uvicorn main:app --workers 1 — and the file's own comment states plainly why this specific number is load-bearing rather than a starting point to tune upward: Chapter 12's rate-limit token buckets are in-memory per worker process; raising the worker count without also switching to the shared database-backed rate-limit store (BRIEFR_RATE_LIMIT_STORE=db) would silently multiply every configured limit by the worker count, exactly the failure mode that chapter described in the abstract, now confirmed as a real, named risk in the deployment config itself. TimeoutStopSec=15 exists for a similarly specific reason: the same comment notes that when the database pool is exhausted (Chapter 9's PoolExhaustedError), in-flight requests hang on pool acquisition and a graceful uvicorn shutdown would otherwise block for systemd's ~90-second default — capped at 15 seconds so a restart doesn't stall that long.

The security hardening block is worth reading as a checklist of what a compromised BRIEFR process would not be able to do: NoNewPrivileges=yes blocks privilege escalation via setuid binaries; ProtectSystem=strict makes the entire filesystem read-only to the process except explicitly listed paths; ReadWritePaths is a short, deliberate allowlist (the backend directory, the backup directory, and the embeddings model cache, the last one marked optional with a leading - so its absence doesn't block startup); ReadOnlyPaths covers the Python virtual environment itself, so even a fully compromised application process can't modify its own interpreter or installed packages on disk. This is the same "least privilege, allowlist everything" instinct you've now seen in the DB explorer (Chapter 9), the SSRF blocklist (Chapter 27), and the search-token scoping (Chapter 11) — applied one more time, at the operating-system level.

nginx — TLS termination, security headers, and a caching split that matters

deploy/nginx-briefr.conf sits in front of uvicorn and does three jobs. First, unconditional HTTP→HTTPS redirect plus certbot-managed TLS. Second, a layered set of security headers in addition to the ones FastAPI's own middleware already sets (Chapter 6) — defense in depth rather than relying on the application layer alone, including server_tokens off to stop nginx from advertising its own version in response headers. Third, and worth understanding precisely because getting it wrong breaks deploys in a confusing way: a deliberate caching split between two kinds of static asset. Hashed Vite build output under /assets/ gets Cache-Control: public, max-age=31536000, immutable — safe to cache essentially forever, because Vite's build process changes the filename itself whenever the content changes, so a stale cache simply can't serve wrong content. index.html — the SPA shell — gets the opposite treatment, explicitly never cached, because it's the one file that references the current build's hashed asset filenames; caching it would mean a browser could keep loading old references to asset files a fresh deploy already deleted, breaking the app in a way that only clears on a hard refresh.

Doctor, backup, update, compose

Beyond the systemd unit and nginx conf: deploy/briefr-doctor.sh runs health/import checks (and can fetch a support pack); briefr-backup.sh / timers and Postgres variants cover host backups; briefr-update.sh / briefr-restore.sh are the operator upgrade/restore path; docker-compose.postgres.yml is the local/dev Postgres+pgvector posture. Know the map even if you only run a subset on a given box.

Security posture, in full

Security posture · 1

Identity and session security

BRIEFR's authentication design (Chapter 11) rests on a genuinely coherent set of choices rather than a checklist of unrelated best practices bolted together. The two-token split — a stateless, fast, short-lived JWT paired with a database-backed, slower, fully-revocable refresh token — exists because "fast to check" and "instantly revocable" are in real tension, and rather than pick one property and accept the other's absence everywhere, BRIEFR picks the cheap option for routine requests and keeps the expensive-but-safe option in reserve for exactly the moment revocation matters. Bcrypt with a dummy-hash comparison closes a timing side-channel that a more naive login implementation would leave wide open; refresh-token hashing at rest means a database leak alone can't be replayed as a live session; rotation-with-reuse-detection means a stolen and replayed refresh token leaves a fingerprint rather than vanishing into ordinary-looking traffic. And require_admin's live database re-check of role on every request is the one place BRIEFR deliberately pays a real performance cost — an extra query per admin request — specifically because staleness in that one check is the highest-value target for a real attacker (a demoted or offboarded admin retaining elevated access).

The one tradeoff worth being able to state without hedging, because it's a genuine limitation rather than a mistake: an issued access token cannot be revoked before its 15-minute expiry, full stop, no matter what happens to the session it came from. A well-run incident response for a suspected token leak still has to account for that window.

Security posture · 2

Network trust boundaries

Two subsystems in this book deal directly with "can input from outside be trusted to shape a network request," and both get it right in ways worth naming specifically rather than vaguely. Chapter 27's webhook SSRF hardening does the full correct sequence — resolve, validate against a real blocklist, then connect to the pinned, already-validated IP while still presenting the correct hostname via SNI for TLS — closing the DNS-rebinding gap a naive "just check the hostname" mitigation would leave open. Chapter 12's rate-limiting client-key resolution applies the same underlying discipline to a different problem: forwarded headers (X-Forwarded-For, CF-Connecting-IP) are only ever trusted when the actual TCP peer is a known, trusted proxy — never trusted from a direct, untrusted connection, because trusting them unconditionally would let anyone mint unlimited fresh rate-limit buckets simply by lying in a header.

Both mechanisms share the same underlying principle, worth generalizing beyond just these two examples: never trust something an adversary can influence without independently verifying it through a channel they can't equally influence. A hostname can be manipulated via DNS; a header can be set to anything by whoever sends the request. A resolved-and-validated IP, and a raw TCP socket's actual peer address, can't be forged the same way — which is exactly why both mechanisms anchor their trust decision there instead.

Security posture · 3

Secrets, at rest and in logs

Chapter 7 and Chapter 13 together describe how BRIEFR protects sensitive values in two different states — stored, and logged — and the honest thing to notice is that neither protection is total, and both say so about themselves rather than overclaiming. Fernet encryption for operator secrets (Chapter 7) is genuinely additive and non-breaking, but its safety is entirely contingent on BRIEFR_SETTINGS_KEY actually being backed up somewhere separate from the database itself — lose that key and the encrypted secrets are, by the very definition of encryption working correctly, unrecoverable. Log redaction (Chapter 13) only ever inspects the keys of structured extra= fields, never a message string's interpolated content — a documented, deliberate boundary rather than an oversight, which places real weight on every developer's discipline never to write a secret directly into an f-string passed to a logger.

The unifying lesson, stated as plainly as possible: BRIEFR's security here comes from structure — a schema-typed secret field, a keyword argument passed correctly — not from a blanket scanner that catches mistakes regardless of how they're made. That's a real, deliberate design choice (a general-purpose secret-scanning system would be slower and noisier), and it means the actual security of any given piece of sensitive data depends on whether the code touching it followed the structural convention correctly. Auditing this codebase for a secret-handling issue means checking call sites against the convention, not just trusting that "redaction exists" as a blanket assurance.

Security posture · 4

Availability, and the request-path discipline underneath all of it

It would be easy to read Chapters 15, 16, and 20 as three unrelated stories — scheduler locking, outbound circuit breakers, and a correlation-engine performance incident — but they're really the same underlying architectural rule, enforced in three different places: heavy or unbounded work never runs on the request path. Chapter 20's ADR-004 is the clearest illustration of what happens when that rule gets violated even briefly — a 61-second query that silently broke an entire unrelated UI element (Operational Priority) simply because it shared a code path with the actual slow computation. Every subsystem built after that incident — precomputed correlation snapshots, the outbound queue's never-drop-a-request design, the scheduler's dual-lock protection against manual/scheduled collisions — is, in effect, institutional memory from that one production failure, generalized into a standing constraint the rest of the codebase now respects by default rather than by accident.

Rate limiting (Chapter 12) closes a more conventional availability gap — protecting BRIEFR's own endpoints from a client, human or automated, that simply sends too many requests — with an honestly-stated residual gap (the LAN-adjacent header-forging scenario) rather than a false claim of completeness.

What was tried, shipped, and later reversed

Real decisions this codebase made and then deliberately undid — the most honest way to understand a system is to see what it tried and walked back, not just what it currently does.

The legacy admin-key header, replaced by real accounts (Spec A0, decided 2026-07-05). What's next, what's parked, and what hasn't been considered yet

Pulled directly from the open backlog and the performance audit's own findings — the honest "not yet" list, not a guess at future features.

Explicitly parked, by the maintainer's own signal (not forgotten, just deprioritized): a STIX/Sigma bulk export feature planned for an earlier release phase; a full, production-grade docker-compose.yml covering the entire stack (today's compose file covers Postgres alone, per Chapter 9); and the remainder of one performance-hardening track beyond what's already shipped. These are recorded as deliberately paused, not abandoned — a distinction worth preserving when discussing them, since "parked" and "rejected" mean different things in this project's own vocabulary.

Explicitly out of scope for the resource-benchmarking program, by decision rather than oversight: synthetic load simulation, Prometheus/Grafana metrics export, per-endpoint latency histograms, and alerting on resource thresholds. What did ship in that same program is real and already covered in Chapter 30's territory: a resource-metrics table with a psutil-based collector job and retention policy, plus an admin-facing Resources page showing CPU/memory trends over 1/3/7/30-day windows. The gap between what shipped and what's out of scope is precise: BRIEFR can show an operator their own instance's resource trend, but does not (yet, by decision) simulate load, export to external monitoring stacks, or alert automatically when something crosses a threshold.

Genuinely not yet considered, per the performance audit's own words: a documented, recommended CPU/RAM/disk sizing envelope — the exact gap Chapter A2 discussed in detail, restated here as a concrete backlog item rather than an abstract observation. Alongside it, the same audit flags the connection-pool sizing defaults, the OFFSET-pagination default, and the unbounded frontend vendor chunk as measured-but-unaddressed findings — real, specific, and modest in scale today, but the first places load would show up if usage grew meaningfully beyond a single operator.

Near-term "next," in the project's own words from its most recent working sessions: admin-facing retrieval health monitoring and operator-tunable knobs for the semantic search system (Chapter 24), following directly on from the embeddings work covered in this book. This is the kind of "next" that's genuinely close — already scoped, waiting on the current program to close out — rather than a distant aspiration.

Glossary

Watermark
A saved checkpoint (timestamp, ID, or commit SHA) marking how far an incremental sync has progressed, so a resumed run knows exactly where to continue from.
Idempotent
An operation whose repeated application has the same effect as applying it once — the property that makes crash-and-retry safe.
Circuit breaker
After N consecutive failures calling a dependency, stop trying entirely for a cooldown period, rather than continuing to fail slowly and repeatedly.
Token bucket
A rate-limiting algorithm where a bucket refills with tokens at a fixed rate and each request consumes one, smoothing bursts while still permitting occasional spikes.
SSRF
Server-Side Request Forgery — tricking a server into making a request on an attacker's behalf, often reaching internal-only services.
CVSS
Common Vulnerability Scoring System — a static 0–10 technical severity score for a vulnerability.
EPSS
Exploit Prediction Scoring System — a live 0–1 probability of real-world exploitation in the next 30 days.
KEV
CISA's Known Exploited Vulnerabilities catalog — confirmed, not predicted, real-world exploitation.
CPE
Common Platform Enumeration — NVD's structured naming scheme for exactly which software/versions a CVE affects.
MITRE ATT&CK
A knowledge base of real-world adversary tactics and techniques, each with a stable ID like T1190.
Sigma rule
A vendor-neutral YAML detection-logic format, translatable into any SIEM's native query language.
Hub IOC / hub suppression
An indicator (often an IP) shared across so many unrelated threat-intel pulses that it carries no real distinguishing signal — excluded from BRIEFR's correlation expansion above a configured threshold.
Operational Priority
BRIEFR's P1–P4 band, derived from a fixed Threat Score × Environment Relevance lookup table, with an optional one-band bump from correlation escalation.
Connection pool
A set of already-open database connections handed out to requests as needed, avoiding the cost of opening a fresh connection per request.
Dependency injection
FastAPI's mechanism for declaring "this route needs X" as a function parameter, run automatically before the route handler.
