Part III · Chapter 15

The scheduler and its lock layer — a danger zone, verified line by line

Why APScheduler's own overlap protection isn't enough, and the exact coupling CLAUDE.md warns you never to let drift.

scheduler.pyscheduler_locks.pyrouters/admin.py

scheduler.py builds an APScheduler AsyncIOScheduler and registers roughly 28 jobs on it — one per feed sync, plus the nightly correlation engine, scheduled backups, session cleanup, and more — each identified by a stable string passed as id= to scheduler.add_job(...). Every job's coroutine is wrapped in job_log_context(id) so its log lines carry a consistent correlation ID back to Chapter 13's structured logging, and jobs are registered with max_instances=1, meaning APScheduler itself refuses to let a job overlap its own next scheduled run if the previous one is still executing.

The gap max_instances=1 doesn't cover

max_instances=1 only protects a job against colliding with its own next scheduled firing — it says nothing at all about a completely separate code path triggering the same underlying work. BRIEFR's admin UI has exactly such a path: an operator can click "sync NVD now" from routers/admin.py, invoking the same NVD sync function outside the scheduler's own timing entirely. Without additional protection, a manual "sync now" click could start running concurrently with a scheduled sync that happened to already be mid-flight — two processes racing to read the same watermark, fetch overlapping data, and write conflicting updates to the same rows at the same time.

scheduler_locks.py closes exactly this gap with a second, independent layer: a plain Python dictionary mapping each job's ID string to its own asyncio.Lock. Both the scheduled job function and the manual-trigger admin endpoint check the same lock before proceeding — whichever one gets there first acquires it and the other is turned away (the admin endpoint returns HTTP 409 Conflict) rather than both running at once.

# Keys must match the `id=` strings passed to scheduler.add_job() exactly.
# incident_feed_refresh, backup_deadman_check, session_cleanup,
# cache_retention_cleanup, watchlist_monitor_alerts, and api_key_health_check
# have no entry here — they run without a lock today (each job is registered
# with max_instances=1, so APScheduler itself prevents overlap; this module
# only consolidates locks that already existed, it doesn't add new ones).
_LOCKS: dict[str, asyncio.Lock] = {
    "nvd_incremental_sync": asyncio.Lock(),
    "kev_metadata_sync": asyncio.Lock(),
    "epss_score_sync": asyncio.Lock(),
    "nightly_correlation": asyncio.Lock(),
    "cvelistv5_incremental_sync": asyncio.Lock(),
    # ...16 more, one per lockable job...
}

scheduler_locks.py, real code and its own comment — note it documents which jobs are intentionally excluded, not just which ones are included

Checking this directly against scheduler.py's actual add_job(id=...) calls confirms the two files agree exactly — every locked job ID here matches a real registered job, with no drift as of this reading. routers/admin.py's own _JOB_RUN_MAP (which the manual "run now" endpoint uses to find each job's function) is a superset that also lists a handful of lock-free jobs — the file's own comment explains why that's fine rather than an inconsistency: those specific jobs rely on APScheduler's max_instances=1 alone, because they don't have a manual-trigger button in the admin UI that could race them, so the second layer of protection genuinely isn't needed for them.

Tracing a real request end to end

Follow POST /api/refresh/nvd concretely: the request passes require_admin (Chapter 6), then checks refresh_in_progress() — which ORs together the NVD, KEV, and EPSS locks — returning 409 immediately if any is held. If clear, it spawns the sync as a background task via task_registry.spawn_background_task, which holds a strong reference to the task specifically so Python's garbage collector can't silently collect and cancel it mid-flight (a real historical bug class, referenced again in Chapter 30). The spawned function re-checks and acquires its own lock, reads the current watermark (seeding one from the maximum modified timestamp already in the cves table if none exists yet and at least 10 CVEs are already present — a sane bootstrap for a database that already has data but no recorded watermark), fetches and upserts, advances the watermark only after the upsert has actually succeeded, and in a finally block always records the job's last-run time for the admin UI and releases the lock — regardless of whether the sync succeeded or raised partway through.

Self-check

  1. Why isn't APScheduler's max_instances=1 sufficient on its own, and what specific race does scheduler_locks.py close that it doesn't?
  2. If the process crashed mid-sync, right after reading the watermark but before writing the new one, what state would the database be left in — and why is that state safe to resume from?
  3. Why does task_registry.spawn_background_task need to hold a strong reference to a spawned task at all — what would silently go wrong without it?
