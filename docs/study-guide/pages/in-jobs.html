Part III · Chapter 17

Durable background jobs — a second job system, and why one wasn't enough

Procrastinate exists specifically for the one class of job where APScheduler's "just re-run it, it's idempotent" story genuinely isn't good enough.

jobs/__init__.pyjobs/app.pyjobs/tasks.pyjobs/worker.pyjobs/context.py

Every job discussed so far — NVD sync, KEV sync, correlation — shares a comfortable property: if the process crashes mid-run, the next scheduled run safely resumes from the last saved watermark, at worst redoing a small, harmless amount of already-completed work. That property holds because each of those jobs is a single, short-ish unit of work bounded by one watermark. It stops holding for a fundamentally different kind of job: the Tier-A stack backfill, a long-running, multi-step process (retroactively pulling every historical CVE matching a newly-declared software stack) that can span many separate ticks over an extended period. A crash halfway through that kind of job doesn't have one clean watermark to resume from in the same way — restarting from scratch would mean redoing potentially hours of already-completed work.

Rather than redesign APScheduler's entire model to handle this one case, BRIEFR added a second, narrower job system: Procrastinate, a Postgres-backed durable task queue, gated behind PROCRASTINATE_ENABLED=1 and a genuine Postgres DATABASE_URL — on SQLite, or with the flag off, every Procrastinate-related call silently no-ops. This is consistent with a pattern you'll see recur throughout this book: rather than force a big migration onto the whole system to solve one narrow problem, add a small, explicitly-scoped, opt-in mechanism next to the existing one, additive rather than a replacement.

jobs/tasks.py defines the actual task functions on a Procrastinate Blueprint() — a health_ping task that exists purely to prove the defer-run-succeed round trip survives a process restart (useful as a smoke test in itself), and stack_backfill_tick, which advances one increment of a backfill run and delegates the real work to services/stack_backfill_worker.py (Chapter 29). jobs/worker.py runs an in-process worker as its own asyncio task, registered with task_registry (Chapter 15's strong-reference pattern, reused here) so it participates in the same graceful-shutdown drain as everything else. jobs/context.py's outbound_context() uses Python contextvars to let any outbound HTTP call made from inside a Procrastinate task be correctly attributed back to "which job triggered this" in the usage-metering system — necessary because the metering code (Chapter 16) has no direct call-stack link back to whichever job runner happened to invoke it.

Self-check

  1. Why does BRIEFR run two separate job systems (APScheduler and Procrastinate) instead of migrating everything onto whichever one is more capable?
  2. What specific property does the Tier-A stack backfill lack that every other scheduled job in this book has, and why does that property matter after a crash?
  3. Why is Procrastinate gated to Postgres only, with no SQLite equivalent — connect this back to what you learned about SQLite's limitations in Chapter 9.
