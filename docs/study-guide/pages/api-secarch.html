Part V · Chapter 26

security_architecture/ — the tool documenting its own posture

Not exploit tracking, not a diagramming feature — BRIEFR turning its own threat model into a living, evidence-gated artifact instead of a document that goes stale the moment it's written.

security_architecture/*.py — 12 files

The name is genuinely ambiguous on first encounter, so it's worth stating plainly what this module actually is, confirmed by reading the code rather than guessing from the directory name: BRIEFR introspectively documenting its own architecture, trust boundaries, security controls, and threat model — mounted at /api/security-architecture/*, gated behind session auth for analyst-and-above roles. The underlying data is a structured YAML corpus split cleanly into two categories with very different trust levels: generated facts (components, the API inventory, scheduler job list, database table list, BRIEFR's own detected tech-stack terms — all regenerated automatically by scripts/generate_security_corpus.py directly from the codebase) and curated judgment (trust boundaries, security controls, abuse-case scenarios, documented security decisions, known risks, and their review history — each curated record requires an explicit review_date and supporting evidence, not just an assertion).

The design principle stated directly in the module's own code is the single most important thing to understand about it: "no new matching/scoring code." Every view in this feature deliberately reuses logic that already exists and already ships in the real product — the stack-match clause from routers/cves.py, the coverage-map builder from routers/forge.py, the threat-scenario generator from Chapter 23 — rather than computing its own independent version of anything. This is a genuinely clever piece of engineering discipline: it guarantees, by construction, that the security-architecture view can never silently drift out of sync with what the product actually does, because it has no separate code path capable of drifting in the first place. A less careful implementation might reimplement "does this CVE match our stack" a second time for this feature specifically — and the two implementations could quietly diverge the moment one of them gets updated and the other doesn't.

A staleness mechanism keeps the curated half honest over time: any curated record whose review_date is more than 90 days old renders as explicitly STALE in the UI and is excluded from the feature's aggregate ratio calculations (like "percentage of controls actively verified"). Without this, a security review written once could sit unchanged for years, silently presenting a snapshot of a system that has since changed underneath it as if it were still current — the 90-day cutoff forces the curated content to be periodically re-attested or visibly marked as no longer trustworthy, rather than aging silently into a false sense of assurance.

Beyond the merge logic, a few sub-modules are worth naming individually. Three files split the "four lenses" work cleanly by responsibility: frameworks/scope.py runs the one live, CWE-scoped CVE query every lens is a projection of, honestly reporting when a requested scope (like "my stack") can't be satisfied rather than silently falling back to the whole corpus; frameworks/reference.py is pure static reference data — CWE names, the OWASP Top 10 2021 list, a documented-as-heuristic STRIDE mapping, and a CWE-to-CAPEC lookup — with no logic beyond dictionary lookups; frameworks/aggregate.py buckets the scoped rows from scope.py into per-category counts using reference.py's mappings, counting each CVE once per category even if it carries multiple CWEs, with an honest "unmapped" bucket for CVEs that don't cleanly fit any known category in that framework, rather than silently dropping unclassifiable CVEs from the count and quietly overstating coverage. graphs.py computes an "attack surface" figure purely at read time, as a count of endpoint inventory crossed with linked controls — explicitly a count, not an invented score, consistent with the whole feature's evidence-first ethos. All of this is exposed through exactly one router, security_architecture/routers/security_architecture.py, mounted at /api/security-architecture and gated by the same session-auth middleware as every other analyst-facing route — there is no separate, weaker auth path for this feature just because it's introspective.

Worth heading off directly: this is not the tool being paranoid about its own supply chain, and it's not a marketing feature dressed up as security theater. Every number it shows traces to either a piece of committed YAML with a review date and cited evidence, or a live query against real product data — never an invented or estimated score. If you're evaluating whether to trust a given figure in this feature, the honest question to ask is "is this generated from code, or curated by a human with a review date" — and the UI is built to make that distinction visible rather than blur it.

What "drift detection" precisely means, verified against the code

"Drift detection" is a claim easy to leave vague, so it's worth being exact about what corpus_drift.py actually compares. It imports the generator script (scripts/generate_security_corpus.py) directly, runs it into a fresh temporary directory, and does a parsed-value equality comparison — not a byte-for-byte text diff — between each committed generated YAML file and its freshly-regenerated counterpart. Concretely, this is a check of "does re-running the static-analysis generator right now produce the same answer as what's committed to git," not a check against a live runtime snapshot or a historical baseline. If a router was added and the generator wasn't re-run afterward, this is exactly what would flag it: the corpus's api_inventory.yaml would no longer match what generating it fresh right now would produce, and check_corpus_drift() reports precisely which files disagree plus the exact command (python scripts/generate_security_corpus.py) to fix it.

corpus_loader.py is the read side of the same corpus, worth knowing has a real integrity check built in beyond just parsing YAML: _validate_record() requires every curated record's related_ids field to resolve to an ID that actually exists somewhere else in the corpus — a dangling cross-reference (a control that claims to relate to a risk ID that was since deleted or renamed) raises a hard validation error rather than silently rendering a broken link. Loading is cached and invalidated by the maximum modification time across every corpus file, so an edit to any one YAML file correctly busts the cache for the whole merged corpus, not just that file.

merge.py's "merge" is entirely read-time glue, never new logic — worth naming its actual pieces precisely: resolve_control_active() checks a control's real runtime env-var flag to report whether it's actually enabled right now (a control with no flag defined is treated as structurally always-on); self_stack_terms() reads BRIEFR's own dependency list (from its own requirements.txt/package.json, captured by the generator) and self_cve_exposure_summary() runs that list back through the same stack-match logic every operator's own asset stack uses — literally BRIEFR checking whether any of its own dependencies are KEV-listed or critical, using no code path other than the one every operator already relies on. security_audit_log_events() filters the real audit log down to a fixed prefix allowlist (auth., backup., database., config.apply, system.restart, and a few others) — a further instance of the "read real data through an allowlist, never invent a number" discipline running through this entire module.

Self-check

  1. Explain precisely how "no new matching/scoring code" prevents this feature from silently drifting out of sync with the actual product — what would a less disciplined implementation have done differently, and what risk would that introduce?
  2. Why does a curated security-control record become STALE after 90 days rather than remaining valid indefinitely once written?
  3. Why do the CWE/OWASP/STRIDE/CAPEC lenses each maintain an explicit "unmapped" bucket instead of silently excluding CVEs that don't fit?
  4. "Drift detection" compares generator-output-now against generator-output-committed. What kind of real-world drift would this not catch — say, a manual hand-edit to the committed YAML that happens to still match what the generator currently produces?
  5. Why does corpus_loader.py treat a dangling related_ids reference as a hard error rather than silently dropping the broken link?
  6. self_cve_exposure_summary() checks BRIEFR's own dependencies against KEV using the exact same code path an operator's asset-stack check uses. What would be lost if this feature had instead written its own, separate self-check logic?
