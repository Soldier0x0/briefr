Part II · Chapter 9

The data layer — BRIEFR's most important module

Dual-backend, no ORM, hand-paired SQL. This chapter is longer than the others on purpose — the project's own internal learning path calls this "the most important module," and after reading it you'll see why.

db/connection.pydb/pg_adapt.pydb/config.pydb/init.pydb/errors.pydb/*.py — 34 files

Why no ORM, revisited concretely

Part 0 introduced the ORM-vs-raw-SQL tradeoff in the abstract; here's what "no ORM" actually looks like in a real query module. db/app_settings.py defines its queries as paired string constants, one per database dialect, sitting side by side:

_SELECT_VALUE_SQLITE = "SELECT value FROM app_settings WHERE key = ?"
_SELECT_VALUE_PG     = "SELECT value FROM app_settings WHERE key = $1"

_UPSERT_SQLITE = """
INSERT INTO app_settings (key, value, updated_at)
VALUES (?, ?, ?)
ON CONFLICT(key) DO UPDATE SET
    value = excluded.value, ..."""

_UPSERT_PG = """
INSERT INTO app_settings (key, value, updated_at)
VALUES ($1, $2, $3)
ON CONFLICT(key) DO UPDATE SET
    value = excluded.value, ..."""

db/app_settings.py — the exact _SQLITE / _PG pairing CLAUDE.md's danger zone describes

Notice the two dialects aren't subtly different for no reason: SQLite uses positional ? placeholders, Postgres uses numbered $1/$2 placeholders — a real driver-level difference neither aiosqlite nor asyncpg will paper over for you. Every query module in db/ follows this same shape: write the SQLite version, write the Postgres version, and a small dispatch function (_is_postgres_connection(db)) picks the right one at call time. There is no automatic translation between them for new code — this is the exact meaning of the project's own rule that a new query has to be written twice, deliberately, by a human who understands both dialects' behavior for that specific query.

What pg_adapt.py actually is (and, importantly, isn't)

It would be easy to assume pg_adapt.py is a general SQLite-to-Postgres translation layer that saves you from writing dialect-specific SQL — that assumption would be wrong, and CLAUDE.md is explicit about it: db/dialect.py, an earlier general-purpose translator, was deleted entirely in a refactor referred to internally as "Post-B" (2026-07). Checking the current repository confirms that file no longer exists. What remains, pg_adapt.py, is scoped much more narrowly: it's internal machinery inside PostgresConnection that exists only to translate legacy SQLite-flavored SQL still being emitted by code outside the db/ package — older router and auth-layer queries written with SQLite idioms (? placeholders, datetime('now')) before the Postgres-native convention was established. Its regex-based _postgres_translate_sql() rewrites those specific patterns (datetime()/date()/julianday() calls, INSERT OR REPLACE/INSERT OR IGNORE into ON CONFLICT equivalents, placeholder renumbering) at the connection boundary, as a compatibility bridge for legacy call sites — not as a general-purpose feature new code is meant to rely on. Writing a brand-new query and hoping pg_adapt.py will make your SQLite SQL "just work" on Postgres is precisely the mistake this file's own docstring warns against.

The connection abstraction: one protocol, two real implementations

db/types.py defines a shared DbConnection protocol — an interface both backends implement identically from the caller's point of view, so query-module code doesn't need an if is_postgres() branch scattered through every function; the branch happens once, inside get_connection(). SqliteConnection wraps aiosqlite, opened in WAL (write-ahead logging) mode with a 30-second busy timeout and foreign keys enforced — WAL mode specifically because it lets readers and a single writer proceed concurrently rather than SQLite's default fully-serialized locking, which matters for a dev/test environment where the scheduler and an interactive request might touch the database at nearly the same moment. PostgresConnection wraps a pooled asyncpg connection, opening a transaction lazily on the first execute() call and leaving commit/rollback entirely to the caller — the connection layer doesn't guess when a logical unit of work ends, the code using it says so explicitly.

Connection pooling, made concrete

Part 0 defined a connection pool abstractly; here's the concrete shape. init_pool() opens a process-global asyncpg pool sized between 1 and settings.database_pool_size connections. get_connection() acquires one from the pool with a timeout — if every pooled connection is already checked out and the timeout expires, it raises a specific PoolExhaustedError, which main.py's exception handler turns into an HTTP 503 (Service Unavailable) rather than a generic crash. This is a meaningfully better failure mode than either silently queuing forever (a request that never returns) or a raw unhandled exception (a 500 with no useful signal) — the client gets a clear, actionable "the server is overloaded, retry" response instead of either extreme. SQLite, by contrast, has no pool at all: each call opens a fresh aiosqlite connection, which is fine for the low-concurrency dev/test use case it's meant for, but is a real, deliberate limitation you should be able to name if asked "does SQLite scale here" — it doesn't, and it isn't meant to.

Why the schema itself is still one database, not split (ADR-001)

ADR-001 documents a genuine tension in BRIEFR's roadmap: the project has an open-core plan to publish a monthly public CVE/correlation snapshot, but a raw pg_dump of the live production database today would leak operator data alongside it — user accounts, session tokens, IOC watchlist entries, webhook destination URLs. The obvious-looking fix is a physical schema split (an intel schema containing only exportable data, an app schema containing everything operator-specific) so a dump of one schema is safe by construction. ADR-001 explicitly considers and defers that split — it would double the migration and test surface immediately, in exchange for a benefit (safe automated exports) the project doesn't need yet, since the public snapshot feature hasn't shipped. Instead, the boundary between "safe to export" and "not safe to export" is enforced today by an allowlist export script (scripts/export_intel_snapshot.py) that only touches tables it's been told are safe, with the physical split explicitly left as a decision to revisit in a later ADR once the open-core feature actually ships. This is worth noticing as a pattern in its own right: sometimes the architecturally "correct" fix is deliberately deferred because the feature that would justify its cost doesn't exist yet, and a narrower, additive mitigation covers the present risk well enough.

Error normalization across two very different drivers

SQLite and Postgres drivers raise entirely different exception hierarchies for the same logical failure (a locked database, a constraint violation). db/errors.py catches both sqlite3.* and asyncpg.* exceptions at the connection boundary and re-raises them as BRIEFR's own dialect-neutral types — DatabaseError, DatabaseLockedError — so that code outside the db/ package (routers, business logic) can catch one exception type regardless of which database is actually running underneath. This is the payoff of the whole dual-backend design done right: the abstraction boundary is drawn at exactly the right place — dialect differences are absorbed inside db/, and everything outside it can pretend there's only one database.

The trap this whole architecture exists to prevent, stated plainly: the default test suite runs against SQLite. A query can pass every test in that suite and still break in production, because SQLite silently tolerates things Postgres rejects outright (type coercion is far looser; CAST(x AS REAL) on a non-numeric string is forgiving in SQLite and an error in Postgres — you'll meet this exact example again in Chapter 22's morning-brief chapter). Any change to the data layer needs to be run against both backends before you can trust it — the project's own tooling for that is a disposable Postgres container on port 5433, specifically to avoid colliding with a developer's own local Postgres on 5432.

The other 26 query modules, grouped by what they back

db/ has 34 files total; six (connection.py, pg_adapt.py, config.py, init.py, errors.py, app_settings.py) carry the architecture lessons above. The remaining 26 are ordinary query modules, each following the same paired-constant pattern — worth knowing what each one actually backs, since "the data layer" isn't one undifferentiated thing.

Core CVE/ingest data: cve.py is the biggest and most central of all of them — it holds upsert_cves, the literal function every feed in Chapter 14 eventually calls, plus the change-history diffing that powers Chapter 22's "EPSS movers" and a provenance-tagging system that protects LLM-derived product data from ever being silently blanked by an empty incoming enrichment batch. It also exports small shared helpers (chunked IN-clause building, batched change-history inserts) that cache.py, metadata.py, and correlation.py all import — making it the de facto utility module for the whole CVE domain, not just CRUD. cache.py holds the IOC/feed/exploit caches Chapters 14 and 23 both lean on; cache_retention.py is its sweep counterpart — the scheduled cleanup that expires stale rows out of every one of those caches (plus change-history, OTX mirror tables, the AI-operations audit trail, and webhook/audit logs) on their own per-table retention windows, including one genuinely subtle correctness fix worth naming: a webhook dedupe-claim row is written before delivery is attempted, so a worker that crashes between the claim and the actual send would otherwise leave a stranded claim that permanently (and wrongly) suppresses that alert forever — the sweep removes only claims old enough to be safely considered abandoned, without touching ones that are still legitimately in flight. enrichment.py is the write-side counterpart to Chapter 14's feed modules — the actual upsert functions that apply vulnrichment/CIRCL/CAPEC and similar secondary-source data onto existing CVE rows, following the same additive, never-downgrade discipline as cve.py's own enrichment path. sync_state.py is the watermark mechanism this book has referenced in the abstract since Chapter 14 — it holds the actual NVD watermark read/write functions, including a self-healing seed from the CVE table's own max-modified date when a watermark is missing but real data already exists. metadata.py holds the full MITRE/ATLAS technique and case-study tables, including a join between two taxonomies (ATLAS case studies and ATT&CK techniques) that's deliberately done in Python rather than SQL, because the two datasets share no foreign key and only connect through common CVE IDs — doing that join in the database would mean an expensive N+1 pattern across roughly a hundred Forge coverage rows. software_catalog.py backs the stack-autocomplete feature, with a genuinely different aggregation query per backend (Postgres's ARRAY_AGG(DISTINCT ...) vs. SQLite's GROUP_CONCAT — not just placeholder syntax, a different SQL feature entirely). timeutil.py is the one place the SQLite-string-vs-Postgres-TIMESTAMPTZ divergence in timestamp handling is centralized, so every other module can import one shared function instead of re-solving the same problem.

Embeddings and search (Chapter 24's actual storage layer): embeddings_pgvector.py is pure Python with no SQL at all — the shared math and rich-text-construction helpers both writer and reader modules call into, including the content-hash function that makes a model swap automatically invalidate every stored vector. embeddings_store.py is the writer, with a real per-backend branch worth knowing: Postgres casts the vector literal directly in SQL (CAST($5 AS vector)), while SQLite stores the raw float bytes as a BLOB — genuinely different write paths, not a placeholder swap. embeddings_search.py is the reader — and this is where "ANN on Postgres, brute-force on SQLite" from Chapter 24 becomes concrete: it uses pgvector's cosine-distance operator on Postgres, but a plain NumPy dot-product scan over BLOBs on SQLite, genuinely different algorithms selected by backend, plus the Reciprocal Rank Fusion math that merges keyword and vector results with query-shape-adaptive weighting (a short query weights keyword matching higher; a longer, more descriptive query weights vector similarity higher). search_tokens.py backs the separate scoped bearer-token auth from Chapter 11 — tokens are bcrypt-hashed at rest exactly like passwords, looked up by a stored prefix for speed, then verified in full.

Correlation support: correlation.py is the biggest file in this entire pass (over a thousand lines) — it holds the OTX pulse/IOC mirror tables, a tiered CVE-prioritization query deciding which CVEs get scarce OTX API budget first (KEV and watchlist-pinned CVEs always win that budget first), and the hub-degree table Chapter 20's confidence scoring reads from. Worth flagging directly: correlation_campaigns and three sibling tables are readable through the admin DB explorer (below) but are not written by anything in this file — they're written directly by correlation/campaigns.py and correlation/metrics.py in the correlation package itself, which issue their own raw SQL rather than going through a db/-layer module — worth knowing if you ever go looking for where a campaign row actually gets written and find nothing in db/correlation.py. threatfox.py is worth flagging as a genuine, singular exception to this book's paired-constant rule: it has SQLite-shaped SQL with bare ? placeholders and no Postgres variant at all, despite living inside a package CLAUDE.md documents as Postgres-native — a real gap, not a stylistic choice, worth confirming before this feed is exercised hard against Postgres in production.

Operator and admin features: explorer.py and explorer_registry.py together are the actual read-only DB explorer mechanism referenced earlier in this book as "deny-by-default, no arbitrary SQL" — worth verifying that claim precisely rather than taking it on faith, since it's exactly the kind of admin feature that could quietly become a SQL-injection surface if built carelessly. The registry hardcodes, per allowed table, an exact column list, a fixed ORDER BY, and which columns are filterable at all — a table not in this static Python dictionary simply can't be queried, full stop, no fallback path exists. The only user-supplied strings that ever reach a query are a filter column name (checked against that table's specific whitelist) and a filter value (always passed as a bound parameter, never string-concatenated) — and the single most sensitive table, cves, additionally requires a filter and validates it against a strict CVE-ID regex, so it can never be browsed unfiltered. This is a genuine allowlist, confirmed by reading the code, not an assertion taken on trust. integrity.py backs the database health-check feature with a real per-backend split: SQLite gets a built-in PRAGMA foreign_key_check, but Postgres has no equivalent, so this module hand-builds a dynamic query introspecting pg_constraint to count actual orphaned foreign-key rows itself — a case where the two backends need genuinely different engineering, not just different SQL syntax for the same idea. resource_metrics.py, ai_operations.py, and api_metering.py (this one distinct from the top-level file of the same name in Chapter 31) back the admin observability surfaces from Chapters 24B and 30. outbound_jobs.py is Postgres-only by explicit design (Procrastinate, Chapter 17, has no SQLite equivalent to read). stack_backfill.py backs the Tier-A backfill feature and includes a genuinely careful concurrency-safe "claim" operation so a crashed worker's in-progress run can be safely reclaimed by a fresh one rather than leaving two workers racing the same backfill.

User-facing tables: watchlist.py (CVE pin/snooze — still genuinely single-user, unlike almost everything else in this book) and ioc_watchlist.py (the separate, per-user IOC watchlist from Chapter 23) are easy to conflate by name but back two different features. webhooks.py holds the full delivery-log, destination-management, and the atomic dedupe-claim mechanism Chapter 27 depends on to prevent double-sending an alert. user_notifications.py backs the in-app notification inbox from Chapter 28, with a badge-count rule worth knowing precisely: only critical and high severity notifications increment the unread badge — a lower-severity notification is still recorded and visible, it just doesn't compete for the analyst's attention the same way.

Self-check

  1. A new query needs to run correctly in both the SQLite test suite and Postgres production. Where does the SQL text actually live — one string, or two — and why doesn't pg_adapt.py save you from writing the Postgres version yourself?
  2. What specific problem does WAL mode solve for SQLite in this codebase, and why doesn't Postgres need an equivalent setting?
  3. Explain PoolExhaustedError's role in the request lifecycle: what would happen to a request under heavy load if this exception type didn't exist and pool acquisition just blocked indefinitely instead?
  4. ADR-001 rejected a physical intel/app schema split "for now." What specific future event would make revisiting that decision necessary?
  5. Walk through the DB explorer's allowlist mechanism precisely: name the two places user input is allowed to reach a query at all, and explain why neither one constitutes a SQL-injection risk.
  6. Why does db/integrity.py need an entirely different implementation strategy per backend, rather than just two versions of the same query?
  7. If you went looking for where a row in correlation_campaigns actually gets written, why would you find nothing in db/correlation.py?
