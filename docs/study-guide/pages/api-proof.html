Part V · Chapter 29

Proof, services, and templates — three more names worth clarifying precisely

"Proof" here means rule-testing, not exploit tracking. Getting that wrong would genuinely misdirect a security review of this codebase.

proof/bench.pyservices/semantic_search.pyservices/stack_backfill_worker.pytemplates/intelligence.py

Worth stating directly, because the directory name genuinely invites the wrong guess: proof/ is a rule-proof bench, not exploit proof-of-concept tracking or storage of any kind. POST /api/proof/run takes pasted log lines alongside either a Sigma rule (Chapter 21) or explicit match patterns, extracts the actual match/keyword conditions from the Sigma detection block, and reports which log lines hit and which missed — a lightweight way for an analyst to sanity-check a detection rule against real or sample log data without needing a live SIEM connection to test against. Confirmed directly by reading the code: there is no exploit code and no proof-of-concept database anywhere in this module. It's purely a rule-testing sandbox, and the name refers to "proving" a detection rule works, not to offensive tooling.

services/semantic_search.py orchestrates the hybrid keyword-plus-vector search introduced in Chapter 24, gracefully degrading to keyword-only matching whenever embeddings are disabled or unavailable — and, notably, always reporting which method actually served a given request (meta.method in the response) rather than silently returning keyword-only results labeled as if they were semantic. services/stack_backfill_worker.py is the actual work behind Chapter 17's Procrastinate-driven Tier-A backfill: paginated NVD keyword fetching, upserting, and EPSS/KEV enrichment application, resumable via checkpoints — and it deliberately never calls OTX, exploit-availability feeds, or the correlation engine, deferring all of that to the ordinary background jobs that already cover it, rather than duplicating that work inside the backfill path itself.

templates/intelligence.py is template-based English-sentence generation — deliberately no LLM involved — for the CVE detail drawer: severity_sentence, epss_sentence, kev_sentence, patch_sentence, exploit_sentence, plus classification of reference URLs into recognizable exploit-source categories (Metasploit, Exploit-DB, GitHub, PacketStorm). This is the actual mechanism behind something you might otherwise assume required an LLM call: CVE summaries in the detail view read as fluent, natural prose without any request-path AI call at all — every sentence is assembled from a fixed template filled in with real data, an approach consistent with the whole product's "explainable, deterministic where it can be" posture running all the way through to the sentence level.

enrichment/ — the plain, deterministic tier this book has referenced but not yet named

Chapter 24 already described this tier conceptually as "no ML, no LLM" — here are the actual three files. enrichment/cve.py is rule-based display-field derivation: it regex-extracts MITRE technique IDs from NVD's own reference-link tags, heuristically flags whether a CVE has a public PoC by matching reference-tag text and known exploit-hosting domains, and builds a plain-English summary preferring CISA KEV's short description, then OSV's, and only falling back to an auto-truncated first sentence of the raw NVD description if neither richer source exists — with a companion function that can tell whether a stored summary is genuinely enriched or just that auto-truncated fallback, by re-deriving it and comparing. enrichment/domain_validation.py is a single, careful function backing IOC lookup input validation: it IDNA/punycode-encodes for proper international domain support, validates real DNS label structure, and explicitly rejects a bare IP address as not being a "domain" — this is the exact function Chapter 23's IOC lookup calls to return a clean 422 rather than silently mishandling a malformed input. enrichment/ioc.py is the actual multi-source orchestrator behind IOC lookup: it deliberately sets retries to zero on every quota-billed API call (VirusTotal, AbuseIPDB — both hard-capped daily quotas where an automatic retry would waste a scarce budget on a request that's already failed), and layers VirusTotal plus a type-appropriate second source (AbuseIPDB for IPs, MalwareBazaar for hashes, URLhaus for domains) with GreyNoise and OTX as further optional enrichment on top.

Self-check

  1. Why does semantic_search.py report its own fallback method in the response instead of silently returning keyword-only results labeled as semantic?
  2. Why does the stack backfill worker deliberately avoid calling OTX or the correlation engine directly, deferring to the ordinary scheduled jobs instead?
  3. What would you have assumed proof/ did from its directory name alone, and why does that assumption matter for someone auditing this codebase's security posture?
  4. Why does enrichment/ioc.py set retries to zero specifically for VirusTotal and AbuseIPDB calls, when Chapter 16's outbound queue elsewhere in this book insists on retrying rather than dropping requests?
  5. Why does enrichment/domain_validation.py explicitly reject a bare IP address as an invalid "domain," rather than accepting it as a trivial special case?
