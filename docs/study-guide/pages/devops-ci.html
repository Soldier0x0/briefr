Part V-B · Chapter 33

CI/CD and testing — the pipeline that's been running in the background of this very book

Two workflow files, four backend-test jobs, 207 backend test files, 56 frontend test files — and the two jobs that are red on every run, by policy, not by accident.

.github/workflows/backend-tests.yml.github/workflows/gitleaks.ymlbackend/tests/

If you've been watching this document's own pull request, you've already seen this chapter's subject matter fire, repeatedly, as live CI events. backend-tests.yml ("Backend tests") defines four jobs: test (the default suite against SQLite — the zero-config path, matching Chapter 9's dev/test story exactly), test-postgres (the same suite, run again against a real Postgres instance — the concrete enforcement mechanism behind Chapter 9's warning that a query can pass the SQLite suite and still break in production), dependency-audit, and playwright-smoke (a thin browser smoke test using the same Playwright/Chromium setup Chapter 5 covers). A second, separate workflow, gitleaks.yml ("Secret scan"), runs an independent secret-scanning pass over every commit. Two of these five jobs — dependency-audit and gitleaks — are documented project-wide as known-red on every run, a deliberate, explicit decision (not silently broken CI) that keeps them visible without treating them as merge blockers until someone specifically prioritizes fixing their underlying findings.

The test suite itself is substantial enough to be a real subject in its own right: 207 backend test files exercise everything from admin config to Alembic revision integrity to AI quota tracking, and 56 frontend test files run through Node's built-in node:test (Chapter 5). The test-postgres job is the single most direct piece of evidence in this entire repository for why Chapter 9 spends as long as it does on the SQLite/Postgres split: it exists purely because relying on the default suite alone was judged insufficient to trust a data-layer change, and running the identical test files against a fundamentally different database engine is the actual mechanism that catches the class of bug (looser SQLite type coercion, different aggregate-function syntax) this book has named specifically in Chapters 9 and 22.

Self-check

  1. Why does a project deliberately keep two CI jobs (dependency-audit, gitleaks) permanently red rather than either fixing them immediately or removing them from CI entirely?
  2. What specific class of bug does test-postgres catch that the default test job structurally cannot, no matter how thorough the SQLite-side test suite is?
  3. If you were reviewing this exact PR's CI output and saw dependency-audit and gitleaks fail alongside a genuinely new failure in test-postgres, how would you tell which one actually needs your attention?
