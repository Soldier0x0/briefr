Part V · Chapter 25

Routers — 23 files, and the provenance that explains their shape

Why one file still holds four logically separate sub-routers, and what that tells you about respecting a refactor's history.

routers/cves.pyrouters/admin.pyrouters/auth.py+20 more

The 23 router files group naturally by feature area. CVE core (cves.py — itself containing four distinct sub-routers: changes, list, detail, intel — plus atlas.py, correlation.py, and a small shared _validators.py holding the one require_cve_id helper every one of those sub-routers imports rather than re-validating CVE ID shape independently) covers listing, filtering, exporting, and the full per-CVE detail view: sentences, EPSS history, related CVEs, the "drawer" bundle, risk, momentum, detection, correlation — most of it read-heavy, with on-demand enrichment calls fanned out concurrently via asyncio.gather so a detail view stays responsive even while quietly checking several external sources at once. Admin (admin.py, 2,667 lines — the single largest file in the entire backend) is the full operator control plane: system health, scheduler introspection and manual triggers (Chapter 15), backup management, a deliberately read-only, allowlisted database explorer (deny-by-default — there is no arbitrary-SQL box anywhere in this UI, on purpose), and the entire runtime configuration surface from Chapter 7. Auth (auth.py, me.py, notifications_me.py) covers the whole login lifecycle plus per-user preferences and the notification inbox. Detection engineering (forge.py, detection_backlog.py, proof.py, threat_model.py) exposes the MITRE coverage map, hunt-pack generation, rule testing, and scenario narratives from Part IV. The remainder — IOC/search, wallboard/brief/health, refresh/watchlist — round out the surface.

The detail worth understanding, not just noting in passing: cves.py still contains four sub-routers rather than being split cleanly into four files, and the code carries explicit "moved verbatim from main.py" provenance comments explaining why. Before an earlier router-split refactor, these four concerns were interleaved with ATLAS and IOC routes in one large monolithic main.py, and — recall Chapter 6's lesson about frozen route registration order — reordering or restructuring those routes risks the exact same silent-route-shadowing bug that snapshot test exists to catch. The refactor prioritized "move code into logical modules without changing observable behavior" over "achieve the cleanest possible file boundaries" — a reasonable trade when the alternative risk is a subtle, hard-to-detect routing regression in a security-relevant surface.

The ten routers behind "the remainder," named precisely

config.py is small but worth knowing exactly: its one endpoint returns the Risk Score weight constants purely for frontend display, reading from the same single source of truth (scoring/risk.py) Chapter 18 covers — the actual score is always computed server-side, this route can never itself change a score, only describe one. stack_catalog.py is the real implementation behind the "My Stack" autocomplete and Tier-A backfill feature: it prefers Procrastinate (Chapter 17) for the backfill dispatch, catching an "already enqueued" condition gracefully, and falls back to an in-process background task if Procrastinate isn't available — a concrete instance of the dual-dispatch pattern this book has described in the abstract. wallboard.py implements exactly the cookie-exchange design Chapter 30 describes: one endpoint trades the raw WALLBOARD_TOKEN for a signed session cookie, a second endpoint reads the kiosk payload gated on that cookie — the raw token itself is never handed to a browser tab that stays open. brief.py is a single, notably auth-free endpoint (the morning brief has no session requirement) delegating straight to Chapter 22's service module. health.py backs /api/health and the true liveness probe, both read through the 45-second cache from Chapter 31. meta.py is a small grab-bag: build-version info, a timezone-aware clock, IOC usage counters, and the PDF/investigation summary endpoints that call into Chapter 24B's ai/summary.py. ioc.py is the router surface for Chapter 23's IOC lookup and per-user IOC watchlist. search.py is the one-endpoint surface for Chapter 24's hybrid semantic search. refresh.py is entirely admin-gated — every manual "sync now" trigger from Chapter 15 lives here, each one auditing itself before spawning, and the full daily-ingest route returns 409 if a sync is already in flight while, notably, the MITRE-refresh route does not, since it can't collide with the same lock. watchlist.py is the CVE pin/snooze feature — worth flagging directly as one of the few genuinely single-user (not per-account) tables left in the schema, a fact the router's own docstring acknowledges as a known scope gap rather than an oversight.

Self-check

  1. How do you add a second admin account to a running BRIEFR instance? Why is that path deliberately not exposed over HTTP at all?
  2. Why does cves.py still contain four logically separate sub-routers instead of being split into four files — connect this back to Chapter 6's route-ordering lesson.
  3. Why is the admin database explorer read-only and allowlisted rather than a general SQL query box, given that it's already gated behind require_admin?
  4. Why does refresh.py's full-ingest route return 409 when a sync is already running, while its MITRE-refresh route doesn't need that same guard?
  5. watchlist.py's CVE pin/snooze feature is still single-user, unlike ioc.py's IOC watchlist. What would have to change in the schema to make it per-user, and why hasn't that happened yet?
